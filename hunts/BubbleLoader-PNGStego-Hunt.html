Executive Summary

BubbleLoader is a loader/packer that ReversingLabs (author Robert Simmons) analysed in a Threat Researcher's Notebook published 2026-11-17. It takes a benign Windows program, patches a short sequence of instructions at the host's entry point and appends two PNG files to the binary. The patched program then becomes a delivery mechanism for a secondary payload. Hosts named in the report are tampered copies of WinRAR, x64dbg, Windows Media Player, the Firefox launcher and virtiofs. The earliest examples date to February 2026, and ReversingLabs describes activity clusters in mid-September and early October 2026.

There are four stages. The entry point patch resolves kernel32 through a call/pop trick and the host's own import table (trying GetModuleHandleA and then GetModuleHandleW so one shellcode works across hosts), resolves GetProcAddress through an obfuscated jump-based call, allocates executable memory with VirtualAlloc and jumps into the second PNG. The first PNG is a real red-to-blue gradient image used as a rolling XOR key. The second PNG has a valid signature and a truncated IHDR chunk, cut off where the width field belongs, followed by second-stage shellcode and the encrypted third stage. The third stage performs a manual PE load of the final payload, registers its .pdata with RtlAddFunctionTable and writes an inline hook over the start of RtlPcToFileHeader in the loaded ntdll.dll. The final payload varies by malware family and the report names none. The report describes no persistence mechanism, so this pack does not claim one.

This pack is behavior-led by design. The report's only indicators are 24 SHA-256 hashes of BubbleLoader samples: no domains, IPs, URLs, registry keys or mutexes. The report also states that runtime polymorphism makes the unpacked payload's in-memory hash differ on every execution, and that responders should pivot toward behavioral memory analysis and entry-point integrity checks. Most of the in-process behavior (RWX allocation, the ntdll hook, the PNG structure) is not visible in endpoint process, file and network telemetry, and the Coverage Map says so. The hunt queries therefore target what endpoint telemetry can see: a host program running or being written from a user-writable path, a host program making outbound connections or spawning shells, and a host-program hash that is rare in the fleet.

The hosts are legitimate software. WinRAR, x64dbg, Windows Media Player, the Firefox launcher and virtiofs are real products. No query here alerts on their presence, and no IOC row blocks any of them. All 24 hash rows ship as detect because they are single-sourced.

Defender priority: retro-hunt the 24 hashes (Q1) once, then spend the effort on tampered-host behavior (Q2, Q3, Q4, Q5, Q6) and on application allowlisting with code-signing verification, the control the report itself recommends first.

Native Audit-Log Hunts

Most of what makes BubbleLoader distinctive happens inside one process and inside appended file data. These checks cover what endpoint hunt queries cannot.

  • Signature and integrity of host programs: run the read-only audit in section 10 across install and user-writable paths. A patched entry point and appended data invalidate the Authenticode signature of a signed host, so a host program that reports HashMismatch or NotSigned where the vendor ships it signed is a lead. Confirm the vendor signs that program before acting.
  • Memory-protection telemetry: the report calls executable memory from VirtualAlloc a detection opportunity and recommends alerting on VirtualProtect against ntdll exception-handling routines such as RtlPcToFileHeader. If your EDR or Defender tenant exposes memory API telemetry (Defender advanced hunting records some ETW threat-intelligence memory ActionTypes), search for a legitimate-program image allocating RWX and then changing protection inside ntdll. Treat this as validate-in-tenant: this pack could not confirm the field or action names for your tenants.
  • Static scan for the malformed PNG: the report's heuristic is that a real PNG width begins with byte 0x00 and the BubbleLoader fake has 0x55 there. The YARA sketch below encodes that. It assumes the width field sits 16 bytes after the PNG signature, which is where a standard IHDR chunk puts it and where the report says the field "would have been". It was not tested against the samples: validate on known samples and a clean PNG corpus before deploying, and expect it to need adjustment.
  • Entry-point integrity: compare the entry point bytes of a host program against a known-good copy of the same version from the vendor. A diff at the entry point, as in the report's figure 9, is the strongest static indicator.
  • Application control audit log: WDAC audit events (Microsoft-Windows-CodeIntegrity/Operational, event 3076) and AppLocker audit events (EXE and DLL log, event 8003) show host programs that would not have been allowed to run. See playbook P1.
// YARA sketch, defensive scanning only. UNVALIDATED: test on known samples and a clean PNG corpus first.
rule bubbleloader_fake_png_width_msb
{
    meta:
        description = "PE with an embedded PNG signature whose width field begins 0x55 instead of 0x00 (ReversingLabs heuristic)"
        status = "unvalidated"
    strings:
        $png = { 89 50 4E 47 0D 0A 1A 0A }
    condition:
        uint16(0) == 0x5A4D and
        for any i in (1..#png) : ( uint8(@png[i] + 16) == 0x55 )
}

Detection Validation Gates

  1. Telemetry ready: confirm process creation with image path, hash and parent is flowing (CrowdStrike: ProcessRollup2. SentinelOne: Process Creation. Defender: DeviceProcessEvents), PE file write telemetry (CrowdStrike: PeFileWritten, NewExecutableWritten. SentinelOne: File Creation. Defender: DeviceFileEvents) and network connection with owning process (CrowdStrike: NetworkConnectIP4. SentinelOne: Network Connection. Defender: DeviceNetworkEvents). Check whether your platform exposes memory-protection API telemetry at all.
  2. Benign baseline: run Q2 to Q6 for 14 to 30 days. Record every portable tool folder, symbol-server and update destination, and every installer that stages the host program names, then write exclusions by hash or destination.
  3. Positive tests (lab hosts only): copy a legitimate x64dbg or WinRAR build to a user profile folder on an isolated VM and confirm Q2 and Q6 fire. Launch a shell from it and confirm Q4. Do not execute any BubbleLoader sample outside an isolated analysis environment.
  4. Promotion: Q2 and Q4 to detect-mode IOAs after a clean baseline. Q1, Q3, Q5 and Q6 remain hunt content until each has produced a reviewed week of results.

The automated gates (structure, Falcon field names, CQL syntax, IOC provenance) prove the file is well-formed and that every hash appears in the saved report. They cannot prove that a host program actually shows these behaviors in your fleet. SignInfoFlags and AuthenticodeHashData in Q2 are projected only; validate their values in your tenant.

Hardening: Tiered and Deployable

All controls target Windows. Authority: MITRE mitigations (the why) plus Microsoft App Control for Business (WDAC), AppLocker and Defender attack surface reduction documentation (the what). The report's own first recommendation is strict application allowlisting and code-signing verification.

Immediate (this week)
  • Run the signature audit on host-program binaries (M1045 Code Signing, T1554). Read-only. Section 10 audit block and playbook P3. A signed vendor program reporting a bad signature is a tampered copy.
  • Source host programs only from the vendor or your software distribution point (M1033 Limit Software Installation, T1554). Inventory where WinRAR, x64dbg, Windows Media Player, Firefox and virtiofs are installed and remove copies in user-writable paths.
  • Turn on audit-mode application control and read its events (M1038 Execution Prevention). Playbook P1. Audit mode logs would-block events without stopping anything.
Near term (1 to 4 weeks, pilot first)
  • ASR rule "Block executable files from running unless they meet a prevalence, age, or trusted list criterion" in audit, then block (M1040 Behavior Prevention on Endpoint). Microsoft Defender documentation. A per-sample patched copy of a program is a low-prevalence file. Playbook P2.
  • Enforce a WDAC or AppLocker policy for user-writable paths (M1038). Publisher or hash rules for sanctioned tools, deny the rest, starting with workstations that do not need portable executables.
  • Static scan of download and share locations with the PNG-structure rule (M1049 Antivirus/Antimalware). Section 7. Validate on samples first. best-practice, no formal benchmark
Strategic (1 to 3 months)
  • Full allowlisting with code-signing verification fleet-wide (M1038, M1045), as the report recommends. Plan a managed installer or signed-publisher trust model so updates do not break.
  • Entry-point integrity and memory-behavior monitoring in the EDR or a dedicated memory-analysis tool (M1040), as the report recommends instead of relying on payload signatures. best-practice, no formal benchmark
  • Restrict debugger and analysis tools (x64dbg) to analyst machines (M1038). A debugger on a general user endpoint is both a hijack target and a risk on its own.

Deployable Playbooks

Each step lists prerequisites, whether a reboot is needed, and how to undo it. Test on a pilot ring.

P1 · App Control for Business (WDAC) policy in audit mode

Prerequisites: Windows 11 or Windows Server 2022 or later for CiTool; an admin workstation with a reference image. Audit mode blocks nothing but logs would-block events. Run on a pilot ring.
Reboot required: No (CiTool applies multiple-policy-format policies without restart)

# Build a policy from a reference scan, then force Audit Mode (option 3)
New-CIPolicy -Level Publisher -Fallback Hash -FilePath C:\WDAC\BubbleLoader-audit.xml -UserPEs -ScanPath 'C:\Program Files'
Set-RuleOption -FilePath C:\WDAC\BubbleLoader-audit.xml -Option 3
ConvertFrom-CIPolicy -XmlFilePath C:\WDAC\BubbleLoader-audit.xml -BinaryFilePath C:\WDAC\BubbleLoader-audit.cip
CiTool.exe --update-policy C:\WDAC\BubbleLoader-audit.cip
CiTool.exe --list-policies

Rollback: CiTool.exe --remove-policy {PolicyGUID} using the GUID shown by --list-policies. Audit mode never blocks, so removal is only needed to stop the logging.

P2 · ASR prevalence rule, audit mode first

Prerequisites: Microsoft Defender Antivirus active with cloud protection on. Run on a pilot ring and review audit events before blocking.
Reboot required: No

# AuditMode first. Move to Enabled only after reviewing the audit events.
Add-MpPreference -AttackSurfaceReductionRules_Ids 01443614-cd74-433a-b99e-2ecdc07bfc25 -AttackSurfaceReductionRules_Actions AuditMode
Get-MpPreference | Select-Object -ExpandProperty AttackSurfaceReductionRules_Ids

Rollback: Remove-MpPreference -AttackSurfaceReductionRules_Ids 01443614-cd74-433a-b99e-2ecdc07bfc25, or set the action to Disabled. Takes effect without restart.

P3 · Signature audit of host-program binaries (read-only)

Prerequisites: PowerShell 5.1 or later and read access to the scanned paths. Reading large profile trees takes time; run off-hours.
Reboot required: No

Get-ChildItem -Path "$env:ProgramFiles","${env:ProgramFiles(x86)}","$env:USERPROFILE" -Include WinRAR.exe,x64dbg.exe,x32dbg.exe,wmplayer.exe,firefox.exe -Recurse -ErrorAction SilentlyContinue |
  ForEach-Object { Get-AuthenticodeSignature $_.FullName } |
  Where-Object { $_.Status -ne 'Valid' } | Select-Object Path, Status

Rollback: none required. The step only reads files and changes no system state. Confirm that the vendor signs a given program before treating a non-Valid result as tampering.
