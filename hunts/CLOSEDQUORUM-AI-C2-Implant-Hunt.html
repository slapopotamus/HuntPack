01

Executive Summary

CLOSEDQUORUM is a 16.4MB, 64-bit Windows implant written in Go (CGO-enabled) that Cisco Talos disclosed on 2026-09-22 through its new CAIRN research toolkit. Its distinguishing feature is architectural, not technical: instead of phoning home to attacker-run C2 infrastructure, it queries up to four commercial LLM providers (DeepSeek, Qwen via OpenRouter, Mistral, and Google Gemini) with structured host-context prompts, tallies their independent votes by plurality, and autonomously executes whichever of four actions wins — steal (LSASS dump + browser credential theft + crypto wallet extraction, all three simultaneously), inject (Early Bird APC injection by default, process hollowing if the model selects it), persist (Registry Run key + scheduled task + WMI event subscription, all three), or move (defined in the decision schema but not implemented in the distribution build). Ties are broken in a fixed order: DeepSeek, then Qwen, then Mistral, then Gemini. The attacker never issues commands once the implant is running — the LLM panel does.

Read this before anything else in this pack. Cisco Talos explicitly states it has not confirmed in-the-wild deployment. The publicly analyzed distribution binary ships with placeholder API keys (dummy_api_key) and a non-functional Discord webhook (dummy_webhook_url) — it cannot reach any LLM provider or exfiltrate anything as distributed. Talos observed the full architecture only through static analysis of development builds; it did not observe a complete end-to-end live execution. The six SHA256 hashes in this pack are development build hashes from the malware's own build chain, not samples recovered from a victim environment. Everything in this pack should be treated as hunting for a credible, technically-confirmed but not-yet-observed-active threat model — not as an active campaign. The one piece of real-world attribution Talos offers is that artifacts in the binary tie the developer to carding-forum posts dating back to 2025, consistent with an operator-configured credentials-as-a-service offering rather than a deployed campaign.

The attacker's objective, per Talos, is straightforward credential and cryptocurrency theft — there is nothing novel about what CLOSEDQUORUM steals. What is novel is effort displacement: an entire post-compromise decision phase (which action to take next, against which process, with which technique) is delegated from a human operator to a model panel that keeps running whether or not the attacker is at a keyboard. Traditional C2 requires attacker-run infrastructure — a domain, an IP, a listener — that defenders can track, block, and see rotate. CLOSEDQUORUM instead rides four commercial API endpoints that thousands of legitimate applications call every day, plus a Discord webhook, which is exactly why Talos and every outlet that covered this story land on the same recommendation: this is a behavioral-correlation hunt, not a domain-blocking exercise. DeepSeek, OpenRouter, Mistral, and Gemini API traffic is not inherently suspicious and must never be treated as a block candidate on this intelligence alone.

Highest-value defensive angle: no single indicator in this threat model is reliable in isolation. The combination is what's distinct — one non-browser process reaching two or more LLM provider APIs, correlated on the same host or same process with LSASS access, suspended-process injection precursors, a "WindowsUpdate" Run-key write, scheduled-task creation, the C:\Windows\Temp\wmi.ps1 forensic artifact, or Discord webhook egress. Section 8, Q7 builds that correlation directly; every other query in this pack is a component signal meant to feed it.

07

Native Audit-Log Hunts

These checks cover ground the CQL queries in Section 8 cannot reach with the Falcon data model referenced by this pack — either because the telemetry isn't exposed as a queryable field, or because the technique targets the telemetry pipeline itself. Run them as Falcon Real Time Response (RTR) scripts, scheduled PowerShell via GPO/RMM, or native Windows tooling, not as CQL.

1. On-disk LSASS dump / staging artifact sweep (RTR)

CLOSEDQUORUM stages LSASS dumps, browser databases, and wallet files under C:\Windows\Temp\ before transmission. Falcon's referenced data model has no dedicated event for arbitrary non-PE file writes, so this is a point-in-time filesystem sweep rather than a continuous query:

Get-ChildItem -Path 'C:\Windows\Temp\' -File -ErrorAction SilentlyContinue |
  Where-Object { $_.Extension -in '.dmp','.tmp' -or $_.Name -match '^(lsass|wallet|login|creds?)' } |
  Select-Object FullName, Length, CreationTimeUtc, LastWriteTimeUtc

Caveat: a positive hit only means a suspicious file existed at scan time — the implant does not persist these files (they are staged for transmission, then presumably cleaned up), so absence of a hit on a scheduled sweep does not clear a host. Treat this as a secondary corroboration check, not a primary detection.

2. WMI permanent event subscription audit (RTR / scheduled PowerShell)

Falcon's referenced event model does not expose WMI __EventFilter / __EventConsumer / __FilterToConsumerBinding objects as first-class CQL fields, so the persistence mechanism itself (not just its wmi.ps1 side effect, covered by Q4) needs a native query:

Get-CimInstance -Namespace root\subscription -ClassName __EventFilter |
  Where-Object { $_.Name -match 'Windows ?Update' -or $_.Query -match 'Win32_PerfFormattedData' } |
  Select-Object Name, Query
Get-CimInstance -Namespace root\subscription -ClassName __EventConsumer |
  Where-Object { $_.Name -match 'Windows ?Update' } |
  Select-Object Name, CommandLineTemplate
Get-CimInstance -Namespace root\subscription -ClassName __FilterToConsumerBinding

Also enable and forward the Microsoft-Windows-WMI-Activity/Operational event log (disabled by default on many builds) — it is the durable, native audit trail for WMI subscription creation and is not dependent on the Falcon sensor's own event model.

3. ETW tamper detection (compensating control, not a query)

CLOSEDQUORUM suppresses ETW by overwriting EtwEventWrite in its own process's memory with a single RET instruction. This is a self-blinding technique: the telemetry pipeline used to observe the tampered process may itself go dark for that process at the moment of tampering. No CQL query against post-hoc log data can reliably catch the instant of patching. Compensating controls, not queries: (a) rely on your EDR vendor's kernel-mode sensor components and anti-tamper protections, which are not solely dependent on user-mode ETW providers — validate this claim with your specific vendor rather than assuming it; (b) enable Protected Process Light (PPL) / HVCI where your EDR supports registering as a protected process, which raises the bar for a user-mode implant to patch the sensor's own hooks; (c) treat any host where CLOSEDQUORUM's OTHER behavioral signals (Section 8) go silent mid-session, after having fired once, as higher priority for manual triage — a telemetry gap immediately following a partial hit is itself a signal.

4. TLS-inspected proxy log review for LLM-prompt content and Discord webhook payloads

Both Talos and The Hacker News note that the structured prompts (host context, offensive capability language) and the Discord webhook payload content are visible only through TLS inspection or provider-side telemetry, not through Falcon network metadata alone. Talos's Snort rule 1:66984 matches on the implant's prompts to the AI services and requires TLS inspection to fire. If your environment performs TLS interception, review proxy logs for: (a) POST bodies to the four LLM provider API endpoints containing structured JSON with fields resembling target_process, exploit_type, evasion_method, or payload_config; (b) POST bodies to discord.com/api/webhooks/... containing Base64 code blocks in ~1,900-byte segments at roughly 1-second intervals.

Q1 · Single Non-Browser Process Contacting Multiple Commercial LLM Provider APIs
CONF HIGHFP MEDIUMCOST MEDIUM IOA CANDIDATE

Looks for: A single non-browser process resolving two or more of the four commercial LLM provider domains CLOSEDQUORUM's ModelOrchestrator queries in sequence (DeepSeek, OpenRouter/Qwen, Mistral, Google Gemini) within the lookback window. This is the headline behavioral correlation Talos frames as the strongest available signal: no single provider domain is suspicious on its own, but the fan-out pattern from one unexpected process is rare.

FP: AI-enabled IDEs, LLM gateway/proxy software, and browser extensions that intentionally call more than one provider.

// HUNT: Single Non-Browser Process Contacting Multiple Commercial LLM Provider APIs
// MITRE: TA0011 Command and Control / T1102 - Web Service
// CONF: high  FP: medium  COST: medium | REQUIRES: DnsRequest, ProcessRollup2
// FALSE POSITIVES: AI-enabled IDEs, LLM gateway/proxy software, and browser extensions that intentionally call more than one provider.
// TUNING: see the FP note above -- scope exclusions to your environment's approved tooling before promoting to an alert
// LOOKBACK: 24h (set in the Falcon time picker -- no in-query time filter)
#event_simpleName=DnsRequest
| DomainName=/^(api\.deepseek\.com|openrouter\.ai|api\.mistral\.ai|generativelanguage\.googleapis\.com)$/i
| rename(field=ContextProcessId_decimal, as=TargetProcessId_decimal)
| join(query={#event_simpleName=ProcessRollup2}, field=TargetProcessId_decimal, include=[ImageFileName, FileName, CommandLine, ComputerName, UserName])
| !in(FileName, values=["chrome.exe","msedge.exe","firefox.exe","brave.exe","opera.exe","Code.exe","Cursor.exe","iexplore.exe"])
| groupBy([aid, ComputerName, TargetProcessId_decimal, ImageFileName], function=[collect(DomainName, limit=10), count(DomainName, distinct=true, as=DistinctProviders)], limit=20000)
| DistinctProviders >= 2
| table([ComputerName, ImageFileName, TargetProcessId_decimal, DistinctProviders, DomainName])

Hardening — Tiered & Deployable

Platform scope

CLOSEDQUORUM is a Windows-only implant (64-bit Go/CGO executable targeting Win32 APIs). All hardening below is Windows/AD-focused; no Linux, macOS, cloud, or container surface is touched by this threat.

Immediate (this week — no compatibility risk, no user-visible change)
  • Enable LSA Protection (RunAsPPL) to block non-protected-process handles to lsass.exe, which directly stops MiniDumpWriteDump-based dumping. — M1043 (Credential Access Protection) / M1040 (Behavior Prevention on Endpoint). Authority: Microsoft Security Baseline & CIS Microsoft Windows 11 Benchmark, "Configure LSASS to run as a protected process." See Playbook 1.
  • Deploy the ASR rule "Block credential stealing from the Windows local security authority subsystem" (GUID 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2) in Block mode. — M1040. Authority: Microsoft Defender Attack Surface Reduction rules reference. See Playbook 2.
  • Confirm/enable Microsoft-Windows-WMI-Activity/Operational and TaskScheduler/Operational event logs, forwarded to your SIEM. — M1047 (Audit). Authority: CIS Microsoft Windows Benchmark, audit-policy section.
Near term (1–4 weeks — pilot on a ring first)
  • AppLocker or WDAC policy blocking script/executable launch from %TEMP% and %APPDATA% for standard users — directly targets the implant's own execution path and the wmi.ps1 drop location. — M1038 (Execution Prevention). Authority: CIS Microsoft Windows Benchmark, "Ensure execution from user-writable directories is restricted"; Microsoft AppLocker design guide. See Playbook 3.
  • Disable browser saved-password storage via policy (Chrome/Edge PasswordManagerEnabled=false), pushing users to a dedicated password manager with hardware-backed encryption. — M1041 (Encrypt Sensitive Information) / M1017 (User Training). Authority: CIS Google Chrome Benchmark & CIS Microsoft Edge Benchmark, password-manager controls.
  • Restrict WMI namespace permissions on root\subscription to admins only on endpoints where standard users have no legitimate need to create permanent event subscriptions. — M1018 (User Account Management). Authority: Microsoft WMI security documentation.
Strategic (1–3 months — architectural change, vendor coordination, or budget)
  • Enable Credential Guard (Windows 11 Enterprise / Server 2019+) to isolate LSA secrets in a virtualization-based security container, independent of RunAsPPL. — M1043. Authority: Microsoft Credential Guard deployment guide; CIS Benchmark VBS/HVCI section. Requires hardware virtualization support and compatibility testing against any LSA-plugin-dependent legacy authentication software.
  • SaaS/AI-tool egress visibility program: deploy a forward proxy or CASB capable of identifying which processes talk to which SaaS/AI APIs (not blocking the APIs — visibility). This is what makes Q1/Q8's baseline sustainable at scale instead of a one-time exercise. — M1037 (Filter Network Traffic) / M1031 (Network Intrusion Prevention, for the TLS-inspection component Talos and The Hacker News both flag as necessary to see prompt content). Authority: NIST SP 800-41 (firewall/segmentation guidance); vendor SaaS-application-control documentation (e.g., CrowdStrike Falcon Firewall Management, or your existing SWG/CASB).
  • EDR/sensor tamper-resistance review against the EtwEventWrite-patching technique specifically — confirm with your EDR vendor (in writing) which of their detection components depend on user-mode ETW versus kernel-mode hooks, and whether PPL/anti-tamper protections cover the sensor process itself. — M1040. Authority: vendor-specific; no generic CIS/NIST control covers this, ⚠ best-practice, no formal benchmark — do not drop this control for lack of one.

Deployable Playbooks

Playbook 1 — Enable LSA Protection (RunAsPPL)

Blocks non-PPL processes (including an unsigned Go implant) from opening the handle to lsass.exe that MiniDumpWriteDump requires. Directly stops CLOSEDQUORUM's steal/lsassDump() capability.

Step 1 -- Set the registry value (deploy via GPO Preferences or your RMM, not manually per-host):
  reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" /v RunAsPPL /t REG_DWORD /d 1 /f

Prerequisites: Windows 8.1/Server 2012 R2 or later. Inventory any third-party LSA plugins/credential
  providers (some smartcard middleware, legacy VPN clients, and older AV credential providers are NOT PPL-
  compatible and will fail to load) BEFORE fleet-wide rollout; pilot on a representative ring first.
Reboot required: YES -- LSASS re-reads this value only at boot.
Rollback: reg add "HKLM\SYSTEM\CurrentControlSet\Control\Lsa" /v RunAsPPL /t REG_DWORD /d 0 /f
  then reboot. If a host becomes unbootable due to an incompatible LSA plugin, boot into Safe Mode or WinRE
  and delete/zero the RunAsPPL value via offline registry edit, then reboot normally.

Playbook 2 — Deploy the LSASS-credential-theft ASR rule

Microsoft Defender's Attack Surface Reduction rule for LSASS credential theft blocks common credential-dumping techniques (including MiniDumpWriteDump-style access from non-allow-listed processes) at the OS level, independent of RunAsPPL.

Step 1 -- Audit first (always -- ASR rules can break legitimate LSASS-adjacent tooling):
  Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 `
    -AttackSurfaceReductionRules_Actions AuditMode

Step 2 -- Review Defender ASR audit events (Event ID 1122, Microsoft-Windows-Windows Defender/Operational)
  for 1-2 weeks; identify and allow-list any legitimate tooling that triggers (some backup/EDR/diagnostic
  tools legitimately touch LSASS).

Step 3 -- Move to Block mode once the audit period is clean:
  Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 `
    -AttackSurfaceReductionRules_Actions Enabled

Prerequisites: Microsoft Defender Antivirus must be the active AV engine (ASR rules do not function in
  passive/EDR-only mode on some configurations -- verify with Get-MpComputerStatus). Requires E5/Defender for
  Endpoint Plan 1+ licensing for centralized reporting (the rule itself works without it).
Reboot required: NO.
Rollback: Set-MpPreference -AttackSurfaceReductionRules_Ids 9e6c4e1f-7d60-472f-ba1a-a39ef669e4b2 `
  -AttackSurfaceReductionRules_Actions Disabled

Playbook 3 — AppLocker path rule blocking execution from %TEMP% / %APPDATA%

Targets the implant's own launch path and the wmi.ps1 drop location under C:\Windows\Temp\ specifically.

Step 1 -- Build and test in Audit mode first (New-AppLockerPolicy / Set-AppLockerPolicy):
  $rule = New-AppLockerPolicy -RuleType Path -User Everyone -RuleNamesToGenerate `
    -PathConditions "%OSDRIVE%\Users\*\AppData\Local\Temp\*","%OSDRIVE%\Windows\Temp\*" -Deny
  Set-AppLockerPolicy -PolicyObject $rule -Merge

Step 2 -- Deploy via GPO in Audit-only enforcement mode for 2-4 weeks; review
  Microsoft-Windows-AppLocker/EXE and DLL + Microsoft-Windows-AppLocker/MSI and Script logs for legitimate
  software that launches from Temp/AppData (many installers do -- expect a real allow-list burden here).

Step 3 -- Add allow-list exceptions for confirmed-legitimate installers/updaters, then switch enforcement
  from Audit to Enforce.

Prerequisites: Windows 10/11 Enterprise or Education edition (AppLocker enforcement requires these SKUs;
  Pro/Home cannot enforce, only audit via limited functionality). Application Identity service must be running.
  WDAC is the modern equivalent if you are not on Enterprise/Education licensing.
Reboot required: NO (policy applies at next Group Policy refresh / gpupdate /force).
Rollback: remove the GPO link, or set the rule collection back to "Not Configured" and run gpupdate /force.
  No reboot needed to roll back.

Playbook 4 — Disable browser saved-password storage (Chrome/Edge policy)

Step 1 -- GPO / registry (Chrome, via ADMX or direct registry under HKLM\SOFTWARE\Policies\Google\Chrome):
  reg add "HKLM\SOFTWARE\Policies\Google\Chrome" /v PasswordManagerEnabled /t REG_DWORD /d 0 /f

Step 2 -- Edge (HKLM\SOFTWARE\Policies\Microsoft\Edge):
  reg add "HKLM\SOFTWARE\Policies\Microsoft\Edge" /v PasswordManagerEnabled /t REG_DWORD /d 0 /f

Prerequisites: an approved enterprise password manager must already be deployed and communicated to users
  BEFORE this rolls out, or you will generate a support-ticket spike and users will route around the policy
  with personal browser profiles.
Reboot required: NO -- takes effect on next browser policy refresh / browser restart.
Rollback: set PasswordManagerEnabled back to 1 (or remove the registry value) and restart the browser.
