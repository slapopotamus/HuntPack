Executive Summary

CARBONATO is a Linux Docker botnet first documented by ThreatDown (Malwarebytes) on 2026-09-22, with corroborating reporting from BleepingComputer, The Hacker News, DarkReading, and SC World. The attacker's objective is dual: build a persistent, self-propagating foothold across internet-exposed Docker hosts, and use that foothold to run the open-source Hermes Agent AI framework (Nous Research, MIT-licensed, installed unmodified) as an interactive, Telegram-operated post-exploitation tool under the persona GH0ST. The agent's persona file (SOUL.md) is overwritten with a 39-line malicious prompt whose stated top priority is harvesting AI provider API keys — ranked above SSH credentials, access tokens, and databases — because the operator's own LLM gateway runs on free-tier capacity and needs more keys to keep operating.

The highest-value defensive angle is the single exposure the entire chain depends on: an unauthenticated Docker daemon API reachable on tcp/2375. Every phase — privileged container creation, host filesystem access via bind mount, the nsenter escape to host PID 1, persistence, agent installation, and propagation to the next /24 — is downstream of that one misconfiguration. Closing it (bind the daemon to the Unix socket, never expose 2375, require TLS mutual auth for any remote API) removes the entire attack chain at its root; every other control in this pack is defense-in-depth for hosts that are already exposed or already compromised.

Operational evidence recovered from an unauthenticated CARBONATO Docker registry (itself exposed since May 2026) spans October 2024 through August 2026, and six of seven known registries plus the LLM gateway were confirmed live as of September 3, 2026 — this is an active, ongoing operation, not a historical curiosity. Attribution signals (voseo Spanish in deployment reports, UTC-06:00 timestamps, the Telegram handle "Carbo506", and a Costa Rica-based reverse-tunnel sink) point to a Costa Rica-based operator, though ThreatDown does not attribute this to a named group.

Defender priority: if you run Docker anywhere with a network-reachable daemon API, verify TODAY that tcp/2375 (and 2376 without mutual TLS) is not reachable from any network the daemon does not explicitly trust — including from other hosts inside your own environment. This single check, run in Section 7, is worth more than every CQL query in Section 8 combined.

07

Native Audit-Log Hunts

These checks run directly on Docker hosts (or via fleet config-management) and cover ground CQL cannot reach — especially confirming the Docker API's own metadata (Privileged/Binds) and reading SOUL.md's actual content.

Docker daemon exposure & live privileged containers

cat /etc/docker/daemon.json 2>/dev/null; ps aux | grep -F dockerd
ss -tlnp | grep -E ':(2375|2376)\b'

docker ps -q | xargs -r docker inspect \
  --format '{{.Id}} Privileged={{.HostConfig.Privileged}} Binds={{.HostConfig.Binds}} PidMode={{.HostConfig.PidMode}}' \
  | awk -F'Privileged=' '$2 ~ /^true/'

Hermes Agent persona file — authoritative content check

test -f /root/.hermes/SOUL.md && grep -l "GH0ST" /root/.hermes/SOUL.md
grep -RIl "CARBONATO_API_KEY" /root/*/.env /etc/environment 2>/dev/null

Immutable-attribute sweep on known implant paths

lsattr -d /opt/gh0st /usr/local/bin/.docker-network-monitor /usr/sbin/systemd-logind 2>/dev/null | grep -- '-i-'

Persistence surface review

crontab -l 2>/dev/null; ls -la /etc/cron.d/
systemctl list-timers --all
cat /etc/rc.local 2>/dev/null
rc-status 2>/dev/null   # OpenRC

Suggested auditd rules (see Section 13 for the full playbook)

-w /var/run/docker.sock -p rwxa -k docker_socket_watch
-a always,exit -F arch=b64 -S execve -F path=/usr/bin/nsenter -k container_escape
-a always,exit -F arch=b64 -S execve -F path=/usr/bin/chattr -k immutable_attr_change

Telegram egress (firewall / proxy logs)

On server workloads with no legitimate reason to reach Telegram, review firewall/proxy logs for outbound connections to api.telegram.org — Falcon-side coverage of this is limited to DNS/IP contact (see Coverage Map); proxy/firewall logs are the more complete source for this specific channel.

Q1 · Outbound Docker API Privileged-Container Exploitation (propagation behavior)
CONF HIGHFP MEDCOST LOW

// HUNT: CARBONATO - T1190 Exploit Public-Facing Application + T1610 Deploy Container (outbound propagation)

//   outbound HTTP calls against a target's Docker API on :2375 to create a privileged,
//   host-mounted container. If this fires, the ALERTING HOST is the attacker/source,
//   not (necessarily) the victim -- treat it as an active-infection indicator.
// MITRE: T1190, T1610 | CONF: high  FP: medium  COST: low | REQUIRES: process execution telemetry
// TUNING: exclude hosts running legitimate Docker orchestration/CI tooling (Portainer,

Q6 · Kernel-Worker Process Argument Spoofing ([kworker/u2:0])

// MITRE: T1036.004 | CONF: high  FP: low  COST: low | REQUIRES: process execution telemetry

#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| CommandLine=/kworker/i
| table([@timestamp, aid, ComputerName, UserName, ImageFileName, FileName, CommandLine, ParentBaseFileName])

Hardening — Tiered

Immediate — deploy this week
  • Bind the Docker daemon to the local Unix socket only; remove any tcp:// entry from daemon.json "hosts". If a remote API is genuinely required, mutual TLS is mandatory, never plaintext TCP. MITRE M1042; CIS Docker Benchmark 2.1, 2.6; Docker Engine security docs — "Protect the Docker daemon socket."
  • Default-deny inbound tcp/2375 and tcp/2376 (without mutual TLS) at the firewall/security-group layer from every network except an explicit management CIDR. MITRE M1030; CIS Docker Benchmark 2.6.
  • Disable --privileged container creation fleet-wide unless explicitly whitelisted per workload; immediately audit and terminate any running privileged container with a host filesystem bind mount. MITRE M1026; CIS Docker Benchmark 5.4 "Ensure privileged containers are not used", 5.5 "Ensure sensitive host system directories are not mounted on containers."
  • Require authentication on every private Docker registry — no anonymous pull or push. MITRE M1047; Docker Engine security docs — registry access control.
Near term — 1 to 4 weeks
  • Roll out seccomp and AppArmor/SELinux profiles fleet-wide; never run with --security-opt seccomp=unconfined. MITRE M1022; CIS Docker Benchmark 5.21, 5.28.
  • Migrate eligible workloads to rootless Docker so a daemon compromise does not equal root-on-host. MITRE M1026; Docker Engine security docs — "Rootless mode."
  • Deploy egress filtering / proxy allowlisting blocking direct outbound to api.telegram.org from server workloads with no legitimate need for it, and block outbound SSH from container hosts to non-approved destinations. MITRE M1037; CIS Docker Benchmark 2.1.
  • Alert on chattr +i outside an approved baseline (auditd rule in Section 13). MITRE M1022.
Strategic — 1 to 3 months
  • Move AI provider API keys (OpenAI, Anthropic, Google/Gemini, OpenRouter, Together, Groq, Mistral, Cohere, self-hosted LocalAI/Ollama/vLLM/LiteLLM/OneAPI) out of container environment variables and into a secrets manager issuing short-lived tokens; alert on key usage from unexpected source IPs. MITRE M1041; NIST SP 800-53 IA-5.
  • Run a recurring internal Docker-host exposure sweep (the same /24 logic the worm uses, pointed at your own estate) so a newly provisioned host can't sit exposed for months before enrollment. MITRE M1047.
  • Adopt container image/registry provenance and signing (Docker Content Trust / Notary, or Sigstore cosign) so an implant repository cannot be silently pulled and trusted. MITRE M1047; CIS Docker Benchmark 4.5, 4.6.

Honest coverage gaps

  • Inside-container visibility: any activity occurring strictly inside a container on infrastructure where no Falcon sensor is deployed (a managed/serverless container platform, or a Docker host where only a sidecar-less minimal runtime is present) is invisible to every query in this pack. All 15 queries assume a Falcon Linux sensor on the underlying host.
  • Unenrolled hosts: Docker hosts with no Falcon Linux sensor at all — including newly-provisioned cloud scratch VMs that are exactly the profile CARBONATO targets — have zero coverage until enrolled. Section 12's strategic "recurring exposure sweep" control exists specifically to find these before the worm does.
  • Docker API wire traffic: Falcon endpoint telemetry sees the resulting process activity, not the Docker Engine API HTTP request itself (the "Privileged":true / "Binds" JSON body). Confirming a container's actual privilege/mount configuration requires the native docker inspect check in Section 7, or network-layer (NDR/firewall) visibility.
  • Telegram C2 channel content: end-to-end within Telegram's own infrastructure. Falcon can only observe that a host contacted Telegram's IP/domain space generically — it cannot distinguish this operator's specific bot traffic from legitimate Telegram use on that host.
  • Arbitrary text file writes: the Falcon data model exposes typed file-write events (PE/ELF/Zip/Jar) but not a confirmed generic event for arbitrary text config writes. SOUL.md content changes, and the exact moment persistence files are written by an editor or heredoc, are hunted via process-execution proxies (Q4, Q15) rather than a native file-write event.

All queries assume telemetry is flowing and hosts have passed the validation gates in Section 11 before being trusted operationally.
