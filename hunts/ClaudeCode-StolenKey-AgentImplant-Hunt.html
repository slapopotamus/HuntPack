Executive Summary

What was shown. Darktrace Signal Labs (Moishe Tajtelbaum and Sam Lister, post dated 2026-11-12) demonstrated in a lab that an attacker holding a developer's stolen Claude Console credentials can drive the Claude Code agent already installed on that developer's machine as a remote-controlled implant. Claude memory stores carried the commands (a heartbeat file, an input file of jobs, an output file of results). The Claude Files API carried the stolen data: a 1 GB file split into three uploads. All of it went to api.anthropic.com, the endpoint the agent already uses for inference.

What it is not. This is not a vulnerability in the Claude platform, there is no malware family, no actor and no campaign, and Darktrace states it has not seen the technique in the wild. Nothing in this pack implies exploitation in the wild. The precondition is an already-compromised developer host with readable credentials, so initial access is out of scope here and the hunt starts at post-compromise credential abuse.

Separate finding, kept separate. Origin Technology's research on Claude Code's Remote Control feature found an undocumented --sdk-url option (named --sdk-server once in the post's introduction) that connects an instance to an arbitrary address. That is related attack surface, not part of the Darktrace demo, and is handled in its own query (Q4) and its own section rows.

Highest-value defensive angle. Destination controls cannot tell this traffic from sanctioned developer use. Agent processes running non-interactively with permission checks disabled, launched by a service manager, spawning reconnaissance tools, or run by an account with no development role are the detectable behaviors. Key hygiene (short-lived, workspace-scoped credentials, rotation, keeping keys out of dotfiles, history and environment) shrinks the precondition.

Defender priority: do not block api.anthropic.com or claude / claude.exe. They are legitimate and probably in sanctioned use. Inventory where Anthropic keys live, rotate exposed ones, list memory stores and Files API uploads in every workspace, disable bypass-permissions mode through managed settings, then run Q1, Q2, Q4 and Q7 first.

  • The --dangerously-skip-permissions attribution rests on Help Net Security (S01). Treat the flag as reported, not as primary-source verbatim, and note that the same arguments make Claude run non-interactively. Q2 therefore does not depend on the flag.

  • No in-the-wild use. Darktrace, CSA and Origin all frame this as demonstration or research. No other incident's indicators are imported.

Hypotheses

  1. H1 (high fidelity): an agent process launched with permission prompts disabled by a service manager or scheduler is the implant execution pattern. Q1, Q2.
  2. H2 (high fidelity): a Claude Code process started with --sdk-url or --sdk-server pointing outside the Anthropic list is a remote-controller redirect. Q4.
  3. H3 (medium): persistence commands naming the agent (systemd-run, cron, scheduled task, service) mark an implant surviving its first stage. Q7.
  4. H4 (medium): recon and share tooling spawned under an agent shell is the tasked-operator phase. Q5.
  5. H5 (low to medium): relaunch loops and non-agent processes handling keys or calling the API fit the implant, with heavy noise. Q3, Q6, Q8.

Q1 · Coding agent launched with tool-confirmation prompts disabled
CONF MEDIUMFP MEDIUMCOST LOW

Looks for: Any process whose command line carries --dangerously-skip-permissions (or the --allow- variant), classified by its parent. The Darktrace demo had a systemd unit relaunching Claude Code with this flag, per Help Net Security. Vendor documentation says this mode is intended for containers and VMs (source 07), so a hit on a developer host with a service_or_scheduler or shell parent is the lead; a hit inside a build container is expected. FP: Developers who run the flag on purpose in a disposable container or VM, CI jobs that run the agent headless. Group by ComputerName: hosts that never run it and suddenly do are the signal.

Q2 · Claude Code started by a service manager, scheduler or daemon parent
CONF MEDIUMFP MEDIUMCOST LOW

Looks for: The agent binary (claude / claude.exe, or node/bun running the Claude Code package) whose parent is systemd, cron, launchd, or a Windows service or task host. The demo used systemd-run to create a transient service, so the parent seen by the sensor is the service manager. FP: Sanctioned automation that runs the agent from a scheduler (nightly review bots, CI runners using a service account). Allowlist by ComputerName and UserName once the owning team confirms.

Hardening: Tiered

Immediate (this week)
  • Find and rotate exposed Anthropic keys. Inventory the credential file, ANTHROPIC_API_KEY in environment and dotfiles, and shell history on developer machines and CI runners (S02, S08). Rotate any key on a suspect host. Control: MITRE M1047 Audit, M1022 Restrict File and Directory Permissions (T1552.001). Verify: playbook P3 check script.   • Disable bypass-permissions mode in managed settings. Set permissions.disableBypassPermissionsMode to disable (S07). Control: M1042 Disable or Remove Feature or Program (T1059). Verify: N5, and confirm Q1 stays quiet. Playbook P1.
  • Audit memory stores and Files API uploads in every workspace (S02, S09). Control: M1047 Audit (T1102.002, T1567). Verify: N1.
Near term (1 to 4 weeks)
  • Short-lived, workspace-scoped credentials. Prefer OAuth or federated sign-in. Where static keys remain, scope each to one workspace and fetch it on demand with apiKeyHelper instead of storing it on disk (S01, S02, S08). Control: M1026 Privileged Account Management, M1027 Password Policies (T1552.001, T1528). Verify: key inventory shows no long-lived key in dotfiles.
  • Egress and volume monitoring, not domain blocking. Report bytes and path per host for api.anthropic.com, alert on upload volume far above a host's inference baseline and on server or service-account callers (S02, S03). Control: M1057 Data Loss Prevention (T1567). Flag: best-practice, no formal benchmark. Playbook P4.
  • Detect agent binaries running non-interactively. Deploy Q1, Q2, Q4, Q7 as IOA detect, plus auditd watches on transient units. Control: M1047 Audit (T1543.002, T1053). Playbook P2.
Strategic (1 to 3 months)
  • Isolate agents. Run agents in disposable VMs or containers with their own scoped credential, so a stolen key reaches little (S02). Control: M1038 Execution Prevention, M1018 User Account Management. Flag: best-practice, no formal benchmark.
  • Application control for where Claude Code may run (WDAC or AppLocker on Windows), including dormant installs (S04). Control: M1038 Execution Prevention (T1059).
  • Treat AI platform credentials as production credentials with ownership, rotation, scoping and monitoring, and ask the provider for alerts on new memory stores and large files and for exportable logs (S01, S02). Control: M1026 (T1078).
What not to do: do not block api.anthropic.com, and do not add claude or claude.exe to a blocklist or prevent rule. Both are legitimate and probably in sanctioned use, and the domain cannot separate attacker use from developer use anyway (S02, S03). Control the credential, the launch mode and the behavior.

Deployable Playbooks

P1. Disable bypass-permissions mode (managed settings)

P1. Disable bypass-permissions mode (managed settings)
Prerequisites: ability to deploy Claude Code managed settings to developer fleets; confirm teams that run agents headless in containers (they need an exception path).
Reboot required: no
Step 1. Add this key to the managed settings file your deployment uses:
{
  "permissions": {
    "disableBypassPermissionsMode": "disable"
  }
}
Step 2. Verify on a pilot ring: starting Claude Code with --dangerously-skip-permissions no longer enters bypass mode, and Q1 stops returning pilot hosts.
Rollback: remove the permissions.disableBypassPermissionsMode key from the managed settings file and redeploy. State change is a single key.

P2. Linux auditd watches for transient and persistent service units

P2. Linux auditd watches for transient and persistent service units
Prerequisites: auditd installed and running; root; review with your platform team before enabling on build hosts.
Reboot required: no (do not enable immutable mode -e 2 in this change)
Step 1. Create /etc/audit/rules.d/agent-persistence.rules:
-w /etc/systemd/system/ -p wa -k agent_unit_write
-w /run/systemd/transient/ -p wa -k agent_transient_unit
-w /var/spool/cron/ -p wa -k agent_cron_write
Step 2. Load: augenrules --load
Step 3. Verify: auditctl -l | grep agent_  then search events with: ausearch -k agent_transient_unit
Rollback: delete /etc/audit/rules.d/agent-persistence.rules and run augenrules --load. Events already written stay in the audit log.

P3. Anthropic key inventory (read-only) and file permission check

P3. Anthropic key inventory (read-only) and file permission check
Prerequisites: shell access to the host with the account that owns the home directory; run on a pilot host first.
Reboot required: no
Step 1. Check the agent credential file and its mode (expect 600):
ls -l ~/.claude/.credentials.json
Step 2. Find key-prefixed strings in dotfiles and history (prints file names only, not the key):
grep -rIl --exclude-dir=.git -E "sk-ant-" ~/.bashrc ~/.zshrc ~/.profile ~/.env ~/.bash_history ~/.zsh_history 2>/dev/null
Step 3. Check the environment of your own shell:
env | grep -c ANTHROPIC_API_KEY
Step 4. Rotate any key found in the Claude Console, then replace static storage with apiKeyHelper pointing at a vault fetch script:
{ "apiKeyHelper": "REPLACE_WITH_PATH_TO_YOUR_VAULT_FETCH_SCRIPT" }
Rollback: steps 1 to 3 change nothing. If apiKeyHelper is misconfigured, remove the setting and sign in again with /login. A rotated key cannot be restored, so update every consumer before revoking the old one.

P4. Windows verification and application control starting point

P4. Windows verification and application control starting point
Prerequisites: PowerShell with administrator rights for service queries; WDAC or AppLocker already in audit mode before enforcing anything.
Reboot required: no for the checks; WDAC policy deployment per your standard process
Step 1. List scheduled tasks and services that reference the agent:
Get-ScheduledTask | Where-Object { $_.Actions.Execute -match 'claude' } | Select-Object TaskName, TaskPath
Get-CimInstance Win32_Service | Where-Object { $_.PathName -match 'claude' } | Select-Object Name, PathName, StartName
Step 2. Add an allow rule for the sanctioned Claude Code install path in audit mode and review what else would be blocked before enforcing.
Step 3. Proxy: report bytes and path for api.anthropic.com per host. Alert on POST volume to /v1/files above your baseline. Do not add an allow-or-block rule for the domain.
Rollback: steps 1 and 3 change nothing blocking. For step 2, return the policy to audit mode or remove the supplemental policy. Disabling a scheduled task found in step 1 is reversed with Enable-ScheduledTask.
