Executive Summary

What happened. On 2026-10-29 a tampered copy of the Claude Code VS Code extension was served from Cursor's extension marketplace under the legitimate identifier anthropic.claude-code. Cursor's notice names versions 2.1.312 and 2.1.313, with modified builds identified for darwin-arm64 (macOS) and win32-x64 (Windows). Cursor puts the exposure window at about 2:27 am to 1:35 pm Pacific time (09:27 to 20:35 UTC) and the exposed population at no more than 5,000 users. The tampered file is extension.js, which carries a small self-contained Node.js loader inserted into the otherwise legitimate bundle.

What the loader does. Loading the module is enough: StepSecurity's sandbox analysis shows it runs under plain Node.js with no VS Code API, no Claude conversation and no package-manager lifecycle hook. Per Cursor and Microsoft it (1) collects host and user details, including the names (not values) of environment variables matching KEY, TOKEN, SECRET, PASS, AWS or GCP, (2) appends an attacker SSH public key labelled svc-telemetry to authorized_keys, (3) tries to enable the local SSH service, (4) opens a reverse SSH tunnel to a single server and (5) writes standalone persistence (a LaunchAgent on macOS, a scheduled task named SysMon with a Startup-folder fallback on Windows, a cron @reboot entry on Linux) that retries the tunnel about every 60 seconds. It then POSTs the reconnaissance over plain HTTP.

Scope and attribution, stated plainly. This was not a compromise of Anthropic's systems or employee laptops. Per Anthropic's statement as quoted by StepSecurity, a malicious actor used access to Cursor's marketplace to publish a tampered copy that Anthropic did not build or publish; Anthropic's official channels are unaffected. Version 2.1.313 was never published to Open VSX or the Microsoft Visual Studio Marketplace, and the Open VSX 2.1.312 and 2.1.314 builds were verified clean by StepSecurity. Cursor replaced the malicious 2.1.312 with clean bytes, and StepSecurity verified the build its marketplace serves today is clean. How the actor obtained publishing access has not been explained publicly. No source names an actor or campaign, and this pack does not either.

Impact was narrower than the payload suggests. Cursor reports that enabling the local SSH service needs administrator rights the extension does not normally have, so on most hosts the attacker could not log in through the tunnel. The key, the persistence and the reconnaissance beacon were still attempted. Cursor took the attacker server offline, so the beacon and tunnel no longer connect; artifacts already on a host are not removed by that.

Highest-value defensive angle. Hunt for what the loader leaves outside the extension folder, because uninstalling or updating the extension removes none of it: the svc-telemetry key in authorized_keys, the persistence objects, the hidden .smt, .smtk and .stk_* files and any ssh -N -R tunnel process. Then scope credential exposure by what the host could reach, since the beacon revealed which credential types were present.

Defender priority: on every machine where Cursor installed or auto-updated Claude Code between 2026-10-29 09:27 and 20:35 UTC, check authorized_keys for svc-telemetry first, preserve evidence, then remove the artifacts in Section 13 and rotate credentials from a known-clean machine. If the tunnel is confirmed to have connected, rebuild the host.

Decisions and source conflicts

  • Affected versions. Early reporting (OX Security, The Hacker News) names only 2.1.313. Cursor's updated notice (2026-10-30 11:30 am PT), Microsoft and StepSecurity name both 2.1.312 and 2.1.313, so both are hunted. The Open VSX 2.1.312 build shares the version number but is a different, clean artifact (verified by StepSecurity), which is why Query 8 is an exposure lead and not proof.
  • Platforms. Cursor identifies modified builds for macOS and Windows only (darwin-arm64 and win32-x64). The loader code also contains Linux cron logic (Microsoft), so Linux is hunted defensively, but no source confirms a malicious Linux build was served.
  • Stale VSIX hash. OX Security lists a different darwin-arm64 VSIX hash than Cursor's updated notice. This pack ships only the values in Cursor's updated notice, which StepSecurity repeats.
  • When the loader runs. The Hacker News describes activation after startup and when a webview opens. StepSecurity (sandbox) and Microsoft (code analysis) both show it executes as soon as the module loads. This pack follows the latter two.
  • Legitimate services are not indicators. The loader looks up its public IP through ifconfig.me and api.ipify.org. Both are legitimate services and are not shipped as indicators.
  • Per-host values are not indicators. StepSecurity lists a post-implant hash of the modified authorized_keys file. It depends on each user's prior key file, so it is excluded. Truncated clean-build hashes are also excluded.
  • Not used. The Hacker News article also mentions an unrelated CLI release-binary incident. It is a different campaign and contributes nothing here.
  • Fetched content treated as data. No fetched page contained instructions directed at an AI agent. Cursor's remediation scripts (remediate-macos.sh, remediate-windows.ps1) were not downloaded or run; Section 13 provides reviewable steps instead.

Hardening: Tiered

Immediate (this week)

1. Remove the trojanized versions and move to 2.1.314 or later. M1051 Update Software, addresses T1195.002. 2.1.314 supersedes both affected versions (StepSecurity, Cursor). Removing the extension alone does not remove the dropped persistence, so pair it with items 2 and 3. Verify: Section 7.3 shows no anthropic.claude-code-2.1.312-* or -2.1.313-* folder.

2. Remove the implant after evidence collection. M1047 Audit, M1018 User Account Management, addresses T1098.004, T1053, T1543.001. Delete the exact svc-telemetry authorized key, the persistence objects and the tunnel processes (Playbooks 1 and 2). Preserve unrelated keys and legitimate remote-development configuration (Microsoft). Verify with the Section 7.1, 7.2 and 7.4 checks.

3. Rotate credentials reachable from exposed hosts, from a known-clean machine. M1027 Password Policies, M1026 Privileged Account Management. Source-control and CI/CD tokens, cloud keys, SSH keys and package registry tokens (StepSecurity). Cursor notes the limited variable collection does not rule out later credential access over a working tunnel.

4. Block the attacker address at egress and search logs. M1037 Filter Network Traffic. Block 134.209.82.225 outbound on TCP 22 and 8099 and search history from 2026-10-29. The server is offline, so this is a tripwire and a scoping aid, not a control.

Near term (1 to 4 weeks)

5. Restrict Cursor to approved extension publishers and add an installation cooldown. M1054 Software Configuration, M1038 Execution Prevention. Microsoft recommends applying Cursor's security-hardening guidance: allow only approved publishers and delay installation of newly published versions. This incident arrived under the legitimate publisher name, so the cooldown is the control that would have helped here; a publisher allowlist alone would not. Confirm the exact setting names in Cursor's enterprise documentation (not fetched for this pack). Flagged best-practice, no formal benchmark.

6. Keep SSH servers off developer workstations unless needed. M1042 Disable or Remove Feature or Program. macOS: Remote Login off (systemsetup -getremotelogin to verify). Windows: OpenSSH Server capability not installed. Cursor reports the attack failed on most hosts precisely because enabling SSH needs administrator rights, so this control converts a persistent foothold into a failed attempt. CIS macOS and Windows benchmarks cover sharing services and optional features.

7. Run the editor without administrator rights. M1026. The loader's SSH enablement failed outside "highly unusual circumstances where Cursor was started with administrator privileges" (Cursor). Verify no developer launches Cursor elevated or as root.

8. Monitor authorized_keys and startup locations for change. M1047 Audit. File-integrity monitoring on ~/.ssh/authorized_keys, C:\ProgramData\ssh\administrators_authorized_keys, user LaunchAgents, user crontabs and the Startup folder closes the largest visibility gap in Section 15. Flagged best-practice, no formal benchmark for developer endpoints.

9. Disable automatic extension updates on managed developer machines. M1051, M1054. Anyone with auto-update enabled could receive the build within the window (OpenSourceMalware, via The Hacker News). Move to staged updates through a ring. Flagged best-practice.

Strategic (1 to 3 months)

10. Mirror and pin extensions internally. M1051, M1038. Serve a vetted set of extension versions from an internal mirror and verify package hashes on import, so a tampered upstream publish is not auto-consumed. Flagged best-practice, no formal benchmark.

11. Restrict outbound SSH from developer networks. M1037. Allow TCP 22 only to approved hosts; this would have broken the reverse tunnel. Keep exceptions for source-control hosts.

12. Remove long-lived secrets from developer environments. M1027, M1026. Prefer short-lived credentials from a credential helper or secrets manager over environment variables whose names match KEY, TOKEN, SECRET, PASS, AWS or GCP. Even this loader sent names only; a working tunnel exposes values.

13. Inventory editor extensions fleet-wide. M1047. Maintain a per-machine record of installed IDE extensions and versions, so the next marketplace incident is answered in minutes. Section 15 shows this question is currently outside endpoint telemetry.
