Executive Summary

What it is. QiAnXin XLab found a backdoor inside cwpsrv, the web server that serves the Control Web Panel (CWP) management interface on Linux hosting servers. XLab named it cwpdoor. It is not a separate program: the attacker added code to the cwpsrv source, recompiled it, and replaces the genuine binary at /usr/local/cwpsrv/bin/cwpsrv. Until it receives a trigger request it behaves like the normal panel server.

How it works. A shell script named cwpsrv_update.sh, posing as a version update, checks the installed cwpsrv version, downloads a matching build from 136.0.141[.]71, backs up the original, stops the service, overwrites the binary and restarts it. It handles only cwpsrv 1.15.10 and 1.24.0 and must run as root. It restores the file and parent-directory access and modification times and runs history -d, so ls and stat show nothing changed. The backdoor wakes only for a request carrying three headers whose names begin with X-Ngx-Integrity (Time, Data, Sig): a timestamp within 300 seconds, an AES-encrypted command and an RSA signature. A valid request runs the command through a helper process reached over the Unix socket ngx_http_integrity_helper, the reply returns in an HTTP 200 application/octet-stream response, and the request is kept out of the access log.

Scope, stated plainly. XLab captured the installer on 2026-06-29 and reports an archive uploaded to VirusTotal from Brazil on 2026-09-30 that held a cwpdoor sample, which XLab reads as evidence of real victims. No source gives a count of infected servers. The 340,000 figure is the number of CWP instances XLab saw exposed to the internet in the past month, a potential-target count. XLab reported zero detections (0 of 63) for the backdoored binary at test time.

Not the same cluster. The same archive also held a file XLab identified as the Ebury OpenSSH backdoor. XLab does not know whether Ebury and cwpdoor are related and notes different attackers may have implanted them on one server. Ebury indicators are a separate cluster and are not shipped here. If you find cwpdoor, hunt the host for Ebury too, but track it as its own finding.

Highest-value defensive angle. The attacker already has root, so the patched-version question is the wrong one: upgrading does not remove an attacker who holds credentials. Look for the live-host tells (the ngx_http_integrity_helper Unix socket, unexpected helper processes started by cwpsrv, the X-Ngx-Integrity strings in the binary), hash the running cwpsrv against the published values and against a fleet baseline, and treat any hit as a full host compromise.

Defender priority: on every CWP server run ss -axp | grep integrity and strings /usr/local/cwpsrv/bin/cwpsrv | grep X-Ngx-Integrity (XLab's own checks). A hit means treat the server as compromised: preserve evidence, restore or rebuild, and rotate every control panel credential. Do not rely on file timestamps, antivirus or the access log to clear a host.

Decisions and conflicts

  • One lineage, three outlets. The Hacker News and eSecurity Planet both derive their indicators from XLab. They corroborate the transcription, not the research, so every indicator ships detect, never prevent.
  • Atomic values were re-read from the saved snapshots and copied character for character: three MD5 hashes, one IPv4 and three URLs. XLab publishes no SHA-256, so the hash rows are MD5 and the hunt uses MD5HashData.
  • URL scheme. The raw XLab and Hacker News text give the URLs as http://. A model-written summary of the Hacker News page showed https://; the saved snapshots are the authority and say http.
  • Legitimate product files are context, never indicators. cwpsrv, /usr/local/cwpsrv/bin/cwpsrv and the CWP service are the genuine product. Only the rebuilt-build hashes identify the implant. Nothing here is a prevent row.
  • No vulnerability. XLab does not know how attackers get root or which flaw spreads cwpdoor. No CVE is attached. A search summary mentioned an unrelated CWP flaw; no source links it to cwpdoor and it is not used.
  • Ebury excluded. A file in the same archive was identified as Ebury; its name and any indicators are left out because the relationship is unknown.
  • Not fetched. BleepingComputer and other outlets in search results were not used (the BleepingComputer fetch returned a bot challenge); nothing is cited from them.
  • Unpublished: initial access, number of victims, hashes for versions other than the two named, SHA-256 values, how commands are launched by the helper process, and how the installer restores timestamps.
  • Injected instructions. No fetched page contained text directing an AI agent to act. Nothing was dropped on that ground.
  • Naming. The pack uses only names that appear in the sources: cwpdoor (XLab also writes CWPdoor), Control Web Panel and cwpsrv. No actor or campaign name is assigned by any source.

07

Native Audit-Log Hunts

These are read-only checks to run on each CWP server (a live-response session, a configuration tool or SSH). The first three are XLab's own checks. A clean result does not clear a host if an attacker with root has altered the tooling, so use them together with the hash comparison.

7.1 Unix socket (XLab's primary check)

ss -axp | grep integrity

A result naming ngx_http_integrity_helper indicates infection. XLab's example found the backdoor on a server whose list of open ports looked normal, because this is a Unix socket and not a network port.

7.2 Processes and binary strings (XLab)

ps -eo pid,ppid,user,lstart,args --forest | grep '[c]wpsrv'
strings /usr/local/cwpsrv/bin/cwpsrv | grep X-Ngx-Integrity

Look for helper child processes of cwpsrv that you cannot account for, and for the header-name strings in the binary. Compare process start times with what you expect for a panel restart.

7.3 Binary hash, backup and metadata

md5sum /usr/local/cwpsrv/bin/cwpsrv
sha256sum /usr/local/cwpsrv/bin/cwpsrv
ls -la /usr/local/cwpsrv/bin/
stat -c '%n mtime=%y ctime=%z' /usr/local/cwpsrv/bin/cwpsrv /usr/local/cwpsrv/bin

Compare the MD5 with the two backdoored-build hashes in Section 4. A match is conclusive; a non-match does not clear the host because only two builds are published. Look for a cwpsrv.prev- file with a date and time in its name: XLab says the installer creates it, and The Hacker News notes the installer's own description says it deletes the backup after success, so the file may be missing. The ls and stat times will not show the swap because the installer restores atime and mtime. Author inference, not from the sources: a change-time (ctime) that is later than the modification time, or that does not match the last legitimate upgrade, is a candidate tell because setting file times normally updates ctime. Validate this on a lab host before relying on it.

7.4 Network side: trigger requests

cwpsrv writes nothing to its own access log for a trigger request, so the evidence is upstream. On any TLS-terminating reverse proxy, WAF, load balancer or decrypting network sensor in front of the panel, search request headers for names beginning X-Ngx-Integrity and for HTTP 200 responses with content type application/octet-stream from the panel. Also search proxy and firewall logs for any connection to the download server (Section 4). Panel traffic that bypasses these devices cannot be checked this way.

7.5 Root access review (initial access is unknown)

last -F root | head -50
grep -E 'Accepted (password|publickey)' /var/log/secure /var/log/auth.log 2>/dev/null | tail -200
cat /root/.ssh/authorized_keys

Installation needs root, so look for root logons and SSH keys you cannot explain, especially before the date the cwpsrv binary last changed. History for the installing session may have been deleted by history -d.

Hardening: Tiered & Deployable

The attacker already holds root, so hardening has two aims: make a binary swap loud and verifiable, and keep the panel and its credentials out of reach so the next implant is harder. None of this removes an existing implant; for that use Section 14.

Immediate: see it and shut the door
  • Restrict the CWP panel ports to an admin network or VPN at the host or perimeter firewall. Prerequisite for the trigger requests to be reachable is a panel exposed to the internet; XLab counts 340,000 exposed instances. M1030, M1035. ⚠ best-practice, no formal benchmark for CWP. Verify: external port scan of the panel ports returns closed; ss -ltnp | grep cwpsrv and your firewall ruleset list only admin sources (Playbook 4).
  • Alert on, then block egress to the download server 136.0.141[.]71. Alert first and block after confirming no business traffic. M1037. Verify: Q3 returns nothing and the firewall counter shows hits (Playbook 4).
  • auditd watch on the cwpsrv binary directory for writes and attribute changes. The installer restores file times but a write still raises an audit event. M1047, NIST SP 800-53 SI-7, CIS Linux Benchmark logging and auditing section. Verify: auditctl -l | grep cwpsrv and a test touch of a copy raises an event (Playbook 3).
  • Run the Section 7 checks and Q1, Q2, Q6 on every CWP server today. M1047.
  • Block header names beginning X-Ngx-Integrity at the reverse proxy or WAF in front of the panel and log every occurrence. A legitimate client has no reason to send them. M1031, M1037. ⚠ best-practice, no formal benchmark for CWP. Verify: send a test request with a header of that name from a lab host and confirm it is dropped and logged.
Near term: verify the binary and tighten root (pilot first)
  • Baseline cwpsrv hashes per release and compare on a schedule (Q6, or a file-integrity monitor). Store the baseline off the host, because an attacker with root can edit local copies. M1022, M1047, NIST SP 800-53 SI-7, CIS Controls v8 safeguard 3.14 on logging sensitive data access. Verify: Q6 shows only known hashes.
  • Key-only SSH for root, no direct root logon, MFA on bastion access. Installation needs root and how attackers get it is unknown. M1032, M1026, CIS Linux Benchmark SSH server section. Verify: sshd -T | grep -E 'permitrootlogin|passwordauthentication'.
  • Immutable bit on the cwpsrv binary between upgrades (chattr +i), removed only inside a change window. This blocks the installer's overwrite unless the attacker clears it first, which is itself logged. M1022. ⚠ best-practice, no formal benchmark for CWP. Pilot first: it will break a normal CWP upgrade if forgotten (Playbook 3 rollback). Verify: lsattr /usr/local/cwpsrv/bin/cwpsrv.
  • Forward auditd, SSH and proxy logs off host so an attacker with root cannot erase them. M1029 Remote Data Storage, M1047. Verify: a test event appears in the central log store within minutes.
Strategic: change the exposure
  • Put the panel behind an authenticated reverse proxy or zero-trust access that terminates TLS and logs full request headers, so a trigger request leaves a record even though cwpsrv logs nothing. M1030, M1035, M1037. ⚠ best-practice, no formal benchmark for CWP.
  • Rebuild CWP servers from a known-good image and deploy by configuration management, with the panel and web server binaries verified against a signed or hashed release list. M1045 Code Signing, M1051 Update Software.
  • Keep CWP current. XLab recommends upgrading to the latest version after cleanup; it has not identified the spread vulnerability, so patching is necessary but is not proof an attacker cannot return (eSecurity Planet). M1051.
  • Network detection for the encrypted channel (decrypting sensor with header logging) to cover the gap that endpoint telemetry cannot see. M1031, M1047.
