Executive Summary

DarkMe is a Visual Basic 6 (VB6) spy-RAT attributed to the financially-motivated APT tracked as Water Hydra (a.k.a. the EvilNum-led Operation DarkCasino, first documented by NSFOCUS in September 2022). Huntress observed the malware in two separate incidents on 2026-08-31, and the notable shift is delivery: Water Hydra previously burned two zero-days to deliver DarkMe — the WinRAR extension-spoofing flaw (CVE-2023-38831, weaponized April 2023) and the Windows Defender SmartScreen bypass (CVE-2024-21412, weaponized late 2023/early 2024) — but this campaign uses neither. The infection now starts with a plain phishing email linking to what looks like a PNG; the click downloads image.pif, a Windows PE that modern Windows will execute on sight regardless of icon or claimed extension.

The attacker's objective is the same as it has always been: get the VB6 loader chain (Coconout.dll → Use.dll → Finalized.dll) onto the host, pass an inverted 329-application sandbox check ("does a real person use this machine"), establish triple persistence (COM CLSID hijack, custom protocol handler, Run key), and process-hollow the DarkMe payload into a legitimate signed Microsoft binary (clspack.exe) before beaconing to an RC4-obscured C2 for crypto-wallet theft, screenshots, and arbitrary command execution.

The highest-value defensive angle is not the phishing lure — it is the deterministic, low-noise execution chain behind it. rundll32.exe /sta {GUID} with no DLL path, reg.exe import of a .txt file, and a signed Microsoft utility running from %AppData% are all patterns Huntress independently rates as "rare in legitimate use" and that this pack turns into standing detections (§8).

Defender priority: every atomic indicator in this pack (hashes, domains, C2 IP) is corroborated by exactly one public source (Huntress) as of 2026-09-28. Per this pack's evidentiary bar, nothing here is promoted to a blocking/prevent posture — treat §10's Falcon IOC CSV as detect-only and lean on the behavioral queries in §8, which do not depend on this campaign's specific infrastructure staying static.

Native Audit-Log Hunts

Checks that do not depend on Falcon CQL — use where Sysmon, Windows auditing, or mail-gateway logs are the only telemetry available, or to cross-validate a Falcon hit.

Sysmon

  • Event ID 1 (Process Create): Image ends in .pif; or Image ends in msiexec.exe and CommandLine contains /i http; or Image ends in wscript.exe/cscript.exe and CommandLine contains .wsf and AppData; or Image ends in reg.exe and CommandLine contains import and .txt; or Image ends in rundll32.exe and CommandLine matches /sta {GUID} with no DLL argument.
  • Event ID 11 (File Create): TargetFilename under \AppData\Roaming\ComponentsFolder\, or any .pif creation outside a legacy line-of-business share.
  • Event ID 12/13/14 (Registry): TargetObject containing CLSID\{CFDC57BA-1705-45AF-BA10-EFC3D592982B}, Classes\Locked\shell\open\command, or a new value under ...\CurrentVersion\Run whose data starts with explorer.exe " followed by a non-http URI scheme.
  • Event ID 22 (DNS Query): QueryName = thatawful.boutique.
  • Event ID 3 (Network Connect): DestinationIp = 67.43.50.11 and/or DestinationPort = 7712.

Windows Security auditing

  • Event ID 4688 (process creation, with command-line auditing enabled via Include command line in process creation events GPO) as a fallback for the Sysmon process rules above on hosts without Sysmon.
  • Event ID 4657 (registry value modified, requires SACL on the relevant hive) for the CLSID/protocol-handler/Run-key writes, if Advanced Audit Policy > Object Access > Registry is enabled with the appropriate SACLs (see §13 Step 5).
  • Zone.Identifier alternate data stream on image.pif (Mark-of-the-Web) confirms the file arrived from the internet/email rather than being locally built — useful corroboration during triage even though Falcon does not surface ADS contents directly.

Mail gateway / SEG

  • Alert on inbound mail containing links whose display text or anchor implies an image (.png/.jpg extension, "photo", "scan") but whose true-file-type detonation returns a PE or .pif.
  • Alert on, or retroactively hunt for, delivery to readonline365.com, storageonline.me, viewdocument.live, advancedfuturetechnology.com, or sharedfuturetech.com in URL-click/proxy logs (single-sourced — treat as monitor-and-triage, not an automatic block; see §10).

Deployable Playbooks

Prerequisites (all steps): local admin / GPO management rights on target endpoints; Microsoft Defender Antivirus present and not in passive mode for the ASR steps; a pilot ring defined before any fleet-wide rollout. Estimated deploy time: 1–2 hours for Steps 1–3 across a pilot ring; Steps 4–5 depend on your mail-gateway/SIEM vendor's change process.

Step 1 — Disable Windows Script Host

What it does: Prevents wscript.exe/cscript.exe from executing .vbs/.wsf/.js files, breaking the prnfig.wsf staging step. Why it works: the loader chain cannot reach the registry-import/rundll32 handoff if the WSH engine itself refuses to run.

Prerequisites: confirm no business-critical .vbs/.wsf logon scripts or line-of-business tooling depend on WSH before disabling fleet-wide. Reboot required: No.

PowerShell:
$path = 'HKLM:\SOFTWARE\Microsoft\Windows Script Host\Settings'
New-Item -Path $path -Force | Out-Null
New-ItemProperty -Path $path -Name 'Enabled' -Value 0 -PropertyType DWORD -Force | Out-Null
Write-Output "Windows Script Host disabled"

GPO path:
Computer Configuration > Administrative Templates > (custom ADMX or direct registry policy — WSH has no native ADMX; deploy via Group Policy Preferences registry item or a signed script)

Verify:
(Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows Script Host\Settings' -Name Enabled -EA SilentlyContinue).Enabled
# Expect: 0

Rollback:
Set-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows Script Host\Settings' -Name Enabled -Value 1
# No reboot required

Step 2 — Enable Attack Surface Reduction rules (script & executable-content abuse)

What it does: Blocks obfuscated-script execution, JS/VBScript launching downloaded executables, executable content from email/webmail, and low-prevalence executables. Why it works: covers the image.pif delivery step and the prnfig.wsf execution step independently of the WSH-disable control.

Prerequisites: Microsoft Defender Antivirus active (passive mode acceptable if a third-party AV is primary, per Microsoft's ASR compatibility notes); pilot in Audit mode for 1–2 weeks if these rules are not already deployed. Reboot required: No.

PowerShell:
$ids = @(
  'be9ba2d9-53ea-4cdc-84e5-9b1eeee46550',  # Block executable content from email client and webmail
  '5beb7efe-fd9a-4556-801d-275e5ffc04cc',  # Block execution of potentially obfuscated scripts
  'd3e037e1-3eb8-44c8-a917-57927947596d',  # Block JavaScript or VBScript from launching downloaded executable content
  '01443614-cd74-433a-b99e-2ecdc07bfc25'   # Block executable files from running unless they meet a prevalence, age, or trusted list criterion
)
Set-MpPreference -AttackSurfaceReductionRules_Ids $ids -AttackSurfaceReductionRules_Actions Enabled,Enabled,Enabled,Enabled
Write-Output "ASR rules set to Block"

GPO path:
Computer Configuration > Administrative Templates > Windows Components > Microsoft Defender Antivirus >
Microsoft Defender Exploit Guard > Attack Surface Reduction > Configure Attack Surface Reduction rules
(add each GUID above with value 1 = Block; use 2 = Audit for the pilot ring)

Verify:
$i = (Get-MpPreference).AttackSurfaceReductionRules_Ids
$a = (Get-MpPreference).AttackSurfaceReductionRules_Actions
for ($n=0; $n -lt $i.Count; $n++) { "$($i[$n]) => $($a[$n])" }
# Expect: 1 (Block) for each of the four GUIDs above

Event ID 1121 (Block) / 1122 (Audit) in Microsoft-Windows-Windows Defender/Operational.

Add-MpPreference -AttackSurfaceReductionOnlyExclusions 'C:\Path\To\LegitimateTool.exe'

Rollback:
Set-MpPreference -AttackSurfaceReductionRules_Ids $ids -AttackSurfaceReductionRules_Actions Disabled,Disabled,Disabled,Disabled

Step 3 — AppLocker deny rule for execution from %AppData%

What it does: Denies EXE/DLL execution from user-writable AppData subfolders unless explicitly allowlisted. Why it works: breaks the chain at the point where Coconout.dll/Use.dll/Finalized.dll would otherwise load from %AppData%\ComponentsFolder\.

Prerequisites: AppLocker (or WDAC) available (Windows 10/11 Enterprise or Education for full policy flexibility); build and pilot an allowlist for any legitimate AppData-resident app (Electron apps, browser updaters, RMM agents) before enforcing. Reboot required: No (AppLocker policy refresh via gpupdate is sufficient); the Application Identity service must be running.

PowerShell (create + test in Audit mode first):
New-AppLockerPolicy -RuleType Publisher,Path -User Everyone -RuleNamePrefix "DenyAppDataExec" `
  -XmlPolicy | Set-AppLockerPolicy -Merge

# Minimal deny-path rule (adapt via the AppLocker MMC snap-in for a maintained allowlist):
# Deny EXE/DLL execution under %APPDATA%\* and %LOCALAPPDATA%\*, then add explicit Allow
# Publisher rules for any signed vendor tooling you need to exempt.

Verify (Audit mode first):
Get-AppLockerPolicy -Effective | Select-Object -ExpandProperty RuleCollections
Get-WinEvent -LogName "Microsoft-Windows-AppLocker/EXE and DLL" -MaxEvents 20

Set-AppLockerPolicy -XmlPolicy "C:\Path\To\PreviousPolicy.xml"
# or remove the rule collection: Remove-AppLockerPolicy (if fully rolling back AppLocker)

Step 4 — Block .pif at the mail gateway / secure email gateway

What it does: Stops image.pif (and any .pif) from reaching the inbox as an attachment, and flags/rewrites links whose true-file-type detonation resolves to a PE despite an image-looking URL or filename. Why it works: removes the initial-access step entirely.

Prerequisites: mail-flow rule or transport rule authoring rights (Exchange Online / on-prem Exchange / third-party SEG); Safe Attachments or equivalent detonation sandbox licensed and enabled. Reboot required: No.

Exchange Online PowerShell (illustrative — adapt file-type list to your standard):
New-TransportRule -Name "Block PIF Attachments" `
  -AttachmentExtensionMatchesWords "pif" `
  -RejectMessageReasonText "Blocked: .pif attachments are not permitted" `
  -Mode Enforce

Defender for Office 365:
Threat policies > Anti-malware > Common Attachment Types Filter > add "pif" to the blocked file-type list
Threat policies > Safe Attachments > enable dynamic delivery / true-file-type detonation on all recipient policies

Verify:
Send a benign test .pif from an external test mailbox and confirm rejection/quarantine in the message trace.

Rollback:
Disable-TransportRule -Identity "Block PIF Attachments"
# or remove "pif" from the Common Attachment Types Filter list

Step 5 — COM hijack registry auditing

What it does: Generates a Security-log event (4657) whenever a value under HKCU\Software\Classes\CLSID is created or modified, independent of Falcon coverage. Why it works: gives SIEM/SOAR a second, native-Windows detection path for the exact persistence mechanism this campaign relies on.

Prerequisites: Advanced Audit Policy Configuration available (Windows 8/Server 2012+); a SACL must be applied to the target registry key in addition to enabling the audit subcategory. Reboot required: No.

PowerShell / auditpol:
auditpol /set /subcategory:"Registry" /success:enable /failure:enable

# Apply a SACL to the CLSID hive (run as SYSTEM/admin; adjust for your SACL tooling of choice):
$acl = Get-Acl -Path 'Registry::HKEY_CURRENT_USER\Software\Classes\CLSID'
$rule = New-Object System.Security.AccessControl.RegistryAuditRule(
  "Everyone", "SetValue,CreateSubKey", "ContainerInherit", "None", "Success")
$acl.AddAuditRule($rule)
Set-Acl -Path 'Registry::HKEY_CURRENT_USER\Software\Classes\CLSID' -AclObject $acl

Verify:
auditpol /get /subcategory:"Registry"
Get-WinEvent -LogName Security -FilterXPath "*[System[EventID=4657]]" -MaxEvents 5

Rollback:
auditpol /set /subcategory:"Registry" /success:disable /failure:disable
# and remove the added RegistryAuditRule from the CLSID key's ACL via the same Get-Acl/Set-Acl pattern
