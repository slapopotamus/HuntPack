Executive Summary

GreyNoise reports an unattributed actor it tracks as GT13 that compromised Check Point Security Management Servers at no fewer than 22 organizations across financial services, energy, government, transportation, mining, engineering and manufacturing. GreyNoise confirms attack activity between 2026-10-17 and 2026-11-02, saw its own observation of the actor run from 2026-10-02 to 2026-11-02, and expects the campaign to be ongoing because the actor keeps access to victim Check Point devices. How the actor first reached the Check Point servers is not known.

What GreyNoise did see end to end was the actor's relay. It exploited a Rejetto HFS server (CVE-2026-61500, a session-forgery flaw) on 2026-10-02, installed HFS middleware hooks, appended an SSH key to /root/.ssh/authorized_keys, set up an unauthenticated HTTP staging server under /root/exfil, uploaded Nmap and Chisel, and ran a Chisel server as a reverse proxy. A download of a Linux implant GreyNoise calls ZULT from data-zt.newpayapp.com failed. Through a Chisel tunnel the actor used a CVE-2026-16232 script (SmartConsole authentication bypass to Run Script) to launch more than 100 management tasks: copying the firewall database and the internal CA, minting a certificate named pivot.p12, and unloading security policies. A bulk certificate task on 2026-10-26 reached 24 management servers and wrote output that was sent by scp back to the hop.

What Falcon can and cannot see. Check Point Gaia management appliances run no Falcon sensor, so this pack does not detect anything on the appliance itself. Its endpoint coverage is two surfaces: (a) the Linux hop class of host (ld.so.preload and key edits, an exfil staging directory, a Python staging script, Chisel, scp collection, and the uname, df and whoami check-in), and (b) downstream Windows and Linux victim hosts that the actor swept and exploited (Netlogon, Exchange, NetScaler, Ivanti and vCenter attempts, plus SSH and credential sprays). Everything that happens on the appliance is a gap here and is covered in Section 7 by native checks.

Evidence quality: GreyNoise is the only primary source, and every indicator is single-sourced to its table. GreyNoise publishes no file hashes and none are invented here. All 69 listed IP addresses are ExpressVPN space (AS206092), so they ship as a time-boxed retro-hunt list at detect only, never at prevent. The ld.so.preload and .libproc.so finding is GreyNoise's "may indicate an implant" and is reported here as unconfirmed. The claim that the actor used LLMs and agentic systems is GreyNoise's assessment about the actor, and the Cloud Security Alliance note calls it plausible but not demonstrated.

Defender priority: patch every Check Point Security Management and Multi-Domain Management server with the July 2026 Jumbo Hotfix, restrict Trusted Clients and management access to known addresses, and treat any server that was internet-reachable before patching as potentially compromised: patching does not remove access already established or invalidate stolen CA material. Then sweep sensored Linux hosts with Q4 to Q8 and Q10 and downstream Windows hosts with Q12 to Q14.

Decisions and discrepancies

  • The GreyNoise page disagrees with itself on two CVE numbers. Its summary lists CVE-2026-41089 (Windows NetLogon) and CVE-2025-5777 (Citrix NetScaler), while its timeline lists CVE-2020-1472 (Netlogon) and CVE-2023-4966 (NetScaler). This pack names both pairs, resolves neither, and hardens against all four.
  • Date windows differ by what is measured. GreyNoise's confirmed attack activity runs 2026-10-17 to 2026-11-02. Its own sensor observation of the actor runs from the HFS exploitation on 2026-10-02 to 2026-11-02 03:19:46 UTC. The pack uses 2026-10-02 as the earliest date for the infrastructure and relay behaviors.
  • 99 addresses are reported, 69 are listed. GreyNoise counts 99 IP addresses (ExpressVPN egresses or compromised Check Point devices) but publishes 69 in its table. The 30 not published cannot be hunted. Thirteen of the 69 are GreyNoise's own inference from a /24.
  • The SSH key GreyNoise describes was planted on the HFS hop, not on the Check Point devices. GreyNoise says the devices hold the matching private key and scp their output to the hop. Secondary coverage and the CSA note advise checking authorized_keys on the management servers too. That is reasonable hygiene but is not a GreyNoise finding, and this pack labels it so.
  • ld.so.preload and /usr/lib/.libproc.so: the only evidence is one error message in one output file. GreyNoise says it "may indicate an implant". No sample, hash or behavior is published, so this pack ships a behavioral hunt (Q10) and an on-appliance integrity check, not a confirmed-implant claim.
  • Check Point's July IPs are deliberately excluded. The vendor blog lists six attacker addresses for the July exploitation of CVE-2026-16232. No source ties them to GT13, and the CSA note reports no overlap with GreyNoise's table, so carrying them would break the rule that a pack ships only its own campaign's indicators.
  • Vendor position: Check Point told The Hacker News (as quoted by CSA and Security Affairs) that the activity involves a previously disclosed vulnerability with patches available and is not a new technique. The pack follows that framing: this is a patching and exposure problem plus a post-compromise recovery problem.
  • Not retrieved: Check Point's advisory page CPAI-2026-9895 returned HTTP 403, and the Hacker News article quoting Check Point could not be located, so neither is cited. The Hacker News statement appears here only as relayed by the CSA note and Security Affairs. Search results also returned other blog write-ups; none were fetched or cited.
  • Hostile or instruction-like text: none found in any retrieved source. Web content was treated as data throughout.

Known limitations and deployment notes
  • PowerQuery: The CQL's user-logon half is not translated: the logon source-address field is not attested, so successful and failed logons from these addresses are visible only on the CQL tab.
  • PowerQuery: Addresses are matched exactly; a customer who later received one of these egress addresses will match, as in the CQL.
  • PowerQuery assumes: IP Connect events carry the remote end in dst.ip.address for outgoing connections and in src.ip.address for incoming ones.
  • KQL – Defender XDR: The CQL's user-logon half is not translated: logons sit in DeviceLogonEvents, a second table, so they are visible only on the CQL tab.
  • KQL – Defender XDR: Advanced Hunting keeps 30 days, so the 2026-10-02 to 2026-11-02 campaign window is no longer fully reachable here; the CQL tab covers the longer window.
  • KQL – Defender XDR assumes: RemoteIP holds the remote end for both outgoing connections and accepted inbound ones.

Playbook 1: Linux file-integrity audit rules (hop-class and general Linux servers)

# 3. Load and verify
augenrules --load

# Rollback
