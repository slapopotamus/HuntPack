Gheist: Stolen-Token GitHub Actions Secret Dump

Wiz tracks Gheist since 2026-09-15. A tool uses stolen GitHub tokens to plant a one-file workflow on a ci-sync branch that prints base32-encoded secrets into the Actions log, then downloads the log and deletes the run. Built on the Wiz Research report and five derivative write-ups.

01

Executive Summary

Attacker objective. Harvest CI/CD secrets at scale. Operators feed stolen GitHub tokens (from infostealer logs and earlier supply-chain breaches, with the March 2026 Trivy compromise named as one source) into a tool that, for every repository a token can reach, creates a ci-sync- branch and commits one workflow file. [#1] [#2]

How it works. The push triggers the workflow, which prints the job environment and every secret the job can read, base32-encoded so GitHub log masking does not match. The tool then downloads the run log through the GitHub API and deletes the run seconds later. The secrets leave through GitHub itself, so there is no attacker server to block. One variant runs a job per deployment environment to reach environment-scoped, often production, secrets. [#1] [#2]

Scale and status. Wiz recovered more than 13,500 planted branches from more than 850 compromised accounts and has tracked the campaign since 2026-09-15. As of 2026-10-24 it was still active and about two thirds of the accounts were gone from GitHub. GitHub's hold on suspicious workflow runs (since 2026-07-28) stopped every public-repository run Wiz checked, but it covers public github.com repositories only, not private repositories or GitHub Enterprise Server, where runs completed and secrets were taken. In one enterprise case cloud credentials from the same organisation were used hours later to enumerate AWS Secrets Manager. [#1] [#2] [#3]

Self-hosted runner variant. From about 2026-10-19 one tool version pushes a second job that searches the runner machine for credentials (31 token formats, process environments, instance-role credentials, the Docker socket, runner credential files, the Kubernetes service-account token). Wiz calls it buggy and reports no successful run. [#1] [#2]

What CrowdStrike can and cannot see. Almost all of the attack happens inside GitHub (branch creation, workflow run, log download, run deletion) and in cloud audit logs. Falcon sees only the self-hosted runner hosts and developer endpoints. This pack gives you Falcon queries for those hosts and, in Section 7, native checks for the part Falcon cannot see. The Coverage Map in Section 15 marks the GitHub-side steps as gaps.

Intel quality. Wiz is the only originating source. The other outlets repeat or summarise it, so every indicator is single-sourced and ships as detect or hunt, never prevent.

Defender priority: deleting a ci-sync branch or run does not undo the exposure. For any repository a stolen token could reach, rotate every repository, organisation and environment secret, revoke the token that pushed, check its owner's device for an infostealer, and treat any self-hosted runner that ran a ci-sync branch as compromised.

Hunt Brief & Attack Chain

Seven hypotheses, ordered by fidelity. Telemetry is named in plain terms first, then by platform.

  1. H1 (high): a self-hosted runner executed the sync-host job. Evidence: command lines naming the .gdmp_ helper files or the gdmp-pivot header (Q1) or helper file writes (Q2). T1552.001. FP: none expected. Process creation with command line (CrowdStrike: ProcessRollup2. SentinelOne: Process Creation. Defender: DeviceProcessEvents).
  2. H2 (high): a shell on a runner or developer host encoded the environment with base32 at 120 columns (Q3). T1027. FP: rare scripts.
  3. H3 (medium): a runner host performed a multi-class credential sweep (Q5) or started a container with the host root mounted (Q6). T1003.007, T1552.005, T1552.007, T1611. FP: automation and diagnostics.
  4. H4 (medium): a host fetched or pushed a ci-sync branch (Q4). T1078.004, T1213.003. FP: responders.
  5. H5 (low): a developer endpoint had its GitHub token stores read or its token pasted into a command (Q7, Q8). T1528. FP: backup and credential helpers.
  6. H6 (native, high): planted branches exist, with the one-file commit and a matching blob id, in any repository the token reached (N1, N5). Outside endpoint telemetry.
  7. H7 (native, high): runs on ci-sync branches were deleted within a minute of finishing, the gheist user agent appears in audit logs, or a cloud role was assumed with a ci-sync subject (N2, N3). Outside endpoint telemetry.

07

Native Audit-Log Hunts

These checks need no Falcon query. They cover the GitHub and cloud side that endpoint telemetry cannot see. All commands are read-only.

N1 · Find planted branches

Where: a workstation with the GitHub CLI authenticated as someone who can read the repositories

# One repository
gh api "repos/OWNER/REPO/branches" --paginate -q '.[].name' | grep -E '^ci-sync-[0-9a-z]{6}$'
# Every repository in an organisation (set ORG first)
gh repo list "$ORG" --limit 2000 --json nameWithOwner -q '.[].nameWithOwner' | while read -r r; do
  gh api "repos/$r/branches" --paginate -q '.[].name' 2>/dev/null | grep -E '^ci-sync-[0-9a-z]{6}$' | sed "s|^|$r |"
done

An empty result is not proof. Wiz reports that a rename wave on 2026-10-06 wiped 610 ci-sync branches as a side effect, and operators can delete branches. Use N2 as well.

N2 · GitHub audit log

Where: organisation or enterprise audit log, or the SIEM you stream it to

# Look for (names vary by plan; confirm in your own audit-log schema):
#   - any event whose user agent is: gheist
#   - workflow runs on branches matching ci-sync-* that were deleted within a minute of finishing
#   - events: workflows.completed_workflow_run and workflows.delete_workflow_run for those branches
# Read-only API example for Enterprise Cloud organisations:
gh api --paginate "orgs/$ORG/audit-log?phrase=action:workflows.delete_workflow_run&per_page=100" \
  | jq -c '.[] | select(tostring | test("ci-sync-|gheist"; "i"))'

This is the primary place to find Gheist. Which events carry the user agent depends on your plan and on whether you stream the log.

N3 · Cloud audit logs for OIDC role assumptions

Where: AWS CloudTrail (or the Azure and Google Cloud equivalents)

# Wiz: role assumptions or token exchanges whose subject includes a ci-sync- branch show that
# Actions ran on an attacker branch, even if you collect no GitHub logs.
# AWS example: AssumeRoleWithWebIdentity events where the web identity subject contains ci-sync-
aws cloudtrail lookup-events --lookup-attributes AttributeKey=EventName,AttributeValue=AssumeRoleWithWebIdentity \
  --start-time 2026-09-01T00:00:00Z --query 'Events[].CloudTrailEvent' --output json \
  | jq -r '.[] | fromjson | select(tostring | test("ci-sync-")) | [.eventTime, .requestParameters.roleArn] | @tsv'
# Then review what the assumed session did next, especially Secrets Manager ListSecrets and GetSecretValue.

Repositories created after 2026-07-15 use an immutable default subject format with owner and repository ids, so search for the ci-sync- substring, not an exact subject. When a job uses a deployment environment the subject carries the environment instead of the branch.

N4 · Self-hosted runner host check

Where: each runner host registered to an affected repository or organisation

sudo find / -xdev \( -name '.gdmp_pat' -o -name '.gdmp_patg' -o -name '.gdmp_sweep' \) 2>/dev/null
sudo grep -rl 'gdmp-pivot' /path/to/actions-runner/_diag 2>/dev/null

Also search the runner job history in GitHub for any job on a ci-sync-* branch and the job logs for gdmp-pivot. A single hit means the host and its cloud instance role are compromised.

N5 · Confirm a planted commit

Where: a clone of an affected repository

git fetch origin 'refs/heads/ci-sync-*:refs/remotes/origin/ci-sync-*'
for b in $(git branch -r --list 'origin/ci-sync-*'); do
  echo "== $b"
  git rev-parse "$b:.github/workflows/sync-check.yml"      # git blob SHA-1, compare with Section 10
  git log -1 --format='%H | %an | sig=%G? | %s' "$b"        # unsigned, token owner as author, "ci: sync config"
  git diff --stat "origin/HEAD...$b"                       # expect exactly one new file
done

A match on blob id, message, unsigned status and a single changed file is a confirmed plant. A different blob id with everything else matching is probably an environment-matrix variant. The author named on the commit is the account whose token was stolen.

N6 · Held workflow runs

Where: public repositories on github.com

gh run list --repo OWNER/REPO --status action_required --json databaseId,headBranch,workflowName,createdAt

Wiz reports every public Gheist run it checked sat at action_required. Do not approve a held sync-check run and do not run code from a ci-sync branch.

Immediate (this week)
