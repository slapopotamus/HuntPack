Executive Summary

GhostAction is a credential-theft campaign against GitHub repositories. In the October 2026 wave, compromised maintainer accounts commit a workflow named "Security Audit" (security-audit.yml) or "Github Actions Security" (github_actions_security.yml) directly to default branches under the victim's own identity. The workflow runs on any push to any branch or tag and on manual dispatch, checks out full history (fetch-depth: 0), and collects two classes of secret: the repository's named Actions secrets, and credentials found in the working tree and the entire git history by regex sweeps for 13 patterns, with two lines of context around every AWS key ID. Everything leaves in one curl POST over plain HTTP to 193.32.204.199.

Socket reports more than 500 compromised accounts and workflows in tens of thousands of repositories since 2026-10-07. The 2026-10-08 burst alone placed the file in 346 repositories, including uber/athenadriver and kitao/pyxel. StepSecurity confirmed one completed exfiltration from a run log, and the attacker re-ran the workflow by hand in pyxel.

Honest coverage statement. The malicious workflow primarily executes on GitHub-hosted runners, which carry no Falcon sensor. Falcon cannot see that execution. This pack hunts only the surfaces Falcon really has: self-hosted runners, developer and CI workstations, any sensored host contacting the collector, and the downstream use of stolen cloud and AI keys.

Defender priority: in GitHub, search for the two workflow paths and the AKIA_CTX_START marker, delete the file from every branch, revoke the compromised account's tokens and sessions, and rotate every credential that ever appeared in any commit. Then run Q1 and Q2 across self-hosted runner hosts.

Q4 · Multi-vendor credential regex sweep (grep with AKIA and AI or SCM key prefixes)
CONF HIGH FP LOW COST LOW

Hardening: Tiered

GitHub platform controls below cite GitHub's own security hardening guidance and MITRE mitigations. No formal CIS benchmark is applied, so each is flagged best-practice, no formal benchmark. Several controls assume a paid GitHub plan; confirm availability before rollout.

Immediate (this week)
  • Remove the workflow and revoke the entry path. Delete security-audit.yml and github_actions_security.yml from every branch, revoke the compromised account's PATs, OAuth grants, SSH keys and sessions, re-enroll phishing-resistant MFA. MITRE M1032, M1026. Verify: git commands in section 10.
  • Rotate by exposure, not by list. Rotate every Actions secret and every credential ever committed to any branch. Revoke rather than rotate leaked PATs. M1027. Verify: CloudTrail and provider logs show no use of old keys after rotation.
  • Block the collector. Falcon IOC prevent, firewall and proxy deny for 193.32.204.199 ports 80 and 3000, including runner subnets. M1037. Verify: Q1 returns only blocked-attempt rows.
  • Default token read-only. Set org default GITHUB_TOKEN permissions to read. The athenadriver run used contents: read, which limited blast radius to stolen secrets. Best-practice, no formal benchmark.
Near term (1 to 4 weeks, pilot first)
  • Protect workflow files. Require pull-request review with code-owner approval for .github/workflows/** (CODEOWNERS plus branch protection or rulesets), and restrict who can bypass. Direct-to-default pushes with no review were the injection path. M1018. Best-practice, no formal benchmark.
  • Enable secret scanning with push protection on all repositories, and scan full history. Best-practice, no formal benchmark.
  • Run-approval and runner policy. StepSecurity reported one repository whose approval requirement stalled re-triggered runs. Treat this as a useful extra layer, not a guarantee against a compromised writer. Restrict runner groups to named repositories.
  • Ephemeral self-hosted runners with no persistent credentials on disk, on isolated networks. M1030. Verify with Q5 that runner hosts rebuild.
  • Egress allowlist for runners. Default-deny outbound, allow only package registries and GitHub. A bare-IP HTTP POST fails closed. M1037. Verify: Q7 returns nothing new.
Strategic (1 to 3 months)
  • Replace long-lived cloud keys with short-lived federation (OIDC trust from GitHub to cloud roles), so a history sweep finds nothing reusable. Credential-lifetime reduction, best-practice, no formal benchmark.
  • Trusted publishing for PyPI, crates.io and npm instead of stored publish tokens.
  • Enforce signed commits and alert on unsigned workflow-file changes by maintainers.
  • History hygiene. Purge committed secrets, then rotate; deleting from HEAD is irrelevant to git log -p --all.

Deployable Playbooks

Playbook 1: Find and remove the workflow (per repository)

Prerequisites: git, write access to the repository, repo admin to bypass branch protection if needed.
Reboot required: no.
1. git fetch --all --prune
2. git log --all --name-only --format="%h %an %s" -- .github/workflows/security-audit.yml .github/workflows/github_actions_security.yml
3. For each branch that contains the file: git checkout BRANCH && git rm .github/workflows/security-audit.yml .github/workflows/github_actions_security.yml && git commit -m "Remove malicious workflow" && git push origin BRANCH
Rollback: git revert the removal commit. Not advisable; only if the file was a confirmed legitimate workflow of the same name (check content first).

Playbook 2: Org default workflow token to read-only

Prerequisites: org owner, GitHub CLI authenticated (gh auth login), list of workflows that need write.
Reboot required: no.
1. gh api -X PUT /orgs/YOUR-ORG/actions/permissions/workflow -f default_workflow_permissions=read -F can_approve_pull_request_reviews=false
2. Verify: gh api /orgs/YOUR-ORG/actions/permissions/workflow
3. Grant per-job write explicitly with a permissions: block where a workflow truly needs it.
Rollback: gh api -X PUT /orgs/YOUR-ORG/actions/permissions/workflow -f default_workflow_permissions=write
(Pilot in one repository first; releases and labeling workflows commonly rely on the old default.)

Playbook 3: Require review for workflow changes

Prerequisites: repo admin; CODEOWNERS file; branch protection or rulesets available on your plan.
Reboot required: no.
1. Add to .github/CODEOWNERS: /.github/workflows/ @YOUR-ORG/security-reviewers
2. In repository Settings, Branches (or Rules), protect the default branch: require a pull request, require review from Code Owners, restrict bypass to a small admin team.
3. Verify: attempt a direct push of a test change under .github/workflows from a non-bypass account; it must be rejected.
Rollback: remove the rule from Settings, Branches (or Rules) and revert the CODEOWNERS line. Release automation that pushes directly will need an explicit bypass actor first.

Playbook 4: Block the collector on a Linux self-hosted runner

Prerequisites: root on the runner host; runner is idle or drained.
Reboot required: no (rules are not persistent across reboot unless saved).
1. iptables -I OUTPUT -d 193.32.204.199 -j REJECT
2. Verify: iptables -C OUTPUT -d 193.32.204.199 -j REJECT && echo present
3. Persist with your distribution's mechanism (for example netfilter-persistent save).
Rollback: iptables -D OUTPUT -d 193.32.204.199 -j REJECT and re-save. No other traffic is affected; this is a single-destination rule.

Playbook 5: Check AWS use of a leaked key

Prerequisites: AWS CLI with CloudTrail read access; the exposed access key ID (REPLACE_WITH_ACCESS_KEY_ID).
Reboot required: no.
1. aws cloudtrail lookup-events --lookup-attributes AttributeKey=AccessKeyId,AttributeValue=REPLACE_WITH_ACCESS_KEY_ID --max-results 50
2. Review source addresses, regions and calls such as CreateUser and CreateAccessKey.
3. Deactivate: aws iam update-access-key --access-key-id REPLACE_WITH_ACCESS_KEY_ID --user-name REPLACE_WITH_USER --status Inactive
Rollback: aws iam update-access-key ... --status Active, only if the key is confirmed unexposed and a dependent service broke. Prefer issuing a new key.
