Executive Summary

Read this first: coverage is narrow by design. A VMware ESXi hypervisor runs no Falcon sensor. GhostFrame's implant, its persistence in /etc/rc.local.d/local.sh, the vmhostd masquerade, the execInstalledOnly change and the VMkatz snapshot scraping are all off-sensor. No CQL in this pack can see them. The queries below cover only the surface Falcon can genuinely reach: sensored hosts talking to the published C2 addresses or the six-port fan-out, the Windows and Linux jump hosts that administer ESXi and vCenter, hosts that stage or copy VM memory and disk files or run VMkatz, and the in-guest aftermath when stolen credentials are used. Everything on the hypervisor is covered by non-Falcon checks, labelled as such in section 7 and the section 15 gap list.

Recorded Future's Insikt Group (2026-11-10) describes GhostFrame, a previously undocumented command-and-control and post-exploitation framework for compromised VMware ESXi hosts. It has a web operator panel with Sessions and Builder sections; the builder produces an ELF implant named vmhostd-core. Insikt tracks the operators as TAG-218, a cluster whose operations overlap with Settra ransomware intrusions.

GhostFrame carries no exploit of its own. The operator must already hold root on the ESXi host. Insikt saw TAG-218 infrastructure target SonicWall, Palo Alto Networks and Fortinet VPN appliances in the US and Europe from late August to October 2026, and four targeted organisations later appeared on the Settra leak site. On 2026-10-12 a victim Fortinet VPN appliance beaconed to both GhostFrame and MeshCentral infrastructure. Insikt presents the Settra link as operational overlap, and states the evidence does not establish that GhostFrame is exclusive to Settra. This pack represents it that way and does not treat GhostFrame and Settra as one codebase or one campaign.

The attacker's objective is control of the virtualization layer: one hypervisor gives access to every guest on it, and VMkatz (an open-source tool, not GhostFrame's own code) reads VM memory snapshots and virtual disk images to recover NTLM hashes, WDigest credentials, Kerberos tickets, SAM and LSA secrets and NTDS.dit data without running anything inside the guest. An endpoint agent on a domain controller VM sees nothing of that theft.

The highest-value defensive angles are therefore (1) stop and watch root access to ESXi, (2) close the VPN appliance entry path, (3) put ESXi syslog, ESXi egress and vCenter audit in front of a human, and (4) treat the first use of stolen credentials as the detection point Falcon can actually own.

Defender priority: if execInstalledOnly or the ESXi firewall keeps reverting after you fix it, that is an active implant loop (about every five seconds), not a misconfiguration. Do not just re-enable the setting. Find and remove the persistence, assume every credential reachable from guests on that host is exposed, and plan domain-wide rotation if a domain controller lived there.

Q2 · Six-port fan-out to one destination (53, 2222, 3389, 4444, 8443, 9443)

Looks for: One sensored host opening TCP connections to at least four of the six ports the implant races, against the same public destination, inside one minute. This is the infrastructure-agnostic pattern Insikt says survives C2 rotation. The real implant sits on ESXi and will not appear here; this finds a sensored host (pivot, jump host, a Linux guest) behaving the same way, and is the template for the firewall or NetFlow version in the non-Falcon checks. A. ESXi triage (read-only)

PLAYBOOK A: ESXi host triage (read-only evidence capture)
Prerequisites: root on the ESXi shell via an approved change; run from a jump host over SSH.

Rollback: none required (read-only). Do not reboot before capture: the boot script re-runs the implant.

1. Capture the settings that GhostFrame resets:

B. SSH and Shell removal, syslog, lockdown

PLAYBOOK B: Remove SSH and Shell exposure, add remote syslog, enter lockdown
Prerequisites: out-of-band console (DCUI or iLO/iDRAC) available; vCenter access works; syslog server reachable.
Reboot required: no.
Rollback: re-enable only for a change window: vim-cmd hostsvc/enable_ssh ; vim-cmd hostsvc/start_ssh ;
          vim-cmd -U dcui vimsvc/auth/lockdown_mode_exit ; remove the syslog setting with
          esxcli system syslog config set --loghost=''

1. Remote syslog (replace the host name with your collector):
   esxcli system syslog config set --loghost='tcp://syslog.example.com:514'
   esxcli system syslog reload
   esxcli network firewall ruleset set -r syslog -e true
2. Turn off SSH and the ESXi Shell:
   vim-cmd hostsvc/stop_ssh ; vim-cmd hostsvc/disable_ssh
   vim-cmd hostsvc/stop_esx_shell ; vim-cmd hostsvc/disable_esx_shell
3. Enter lockdown mode:
   vim-cmd -U dcui vimsvc/auth/lockdown_mode_enter
4. Verify: esxcli system syslog config get ; confirm events reach the SIEM (N6).

C. NTLM audit on domain controllers

PLAYBOOK C: Audit NTLM on domain controllers before restricting
Prerequisites: domain admin; apply through a GPO linked to the Domain Controllers OU on a pilot DC first.
Reboot required: no (applied by policy refresh; confirm on the pilot DC).
Rollback: set the value back to 0 or remove it, then gpupdate /force.

1. Audit incoming NTLM (registry equivalent of the GPO setting):
   reg add HKLM\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0 /v AuditReceivingNTLMTraffic /t REG_DWORD /d 2 /f
2. Review Microsoft-Windows-NTLM/Operational events for 2 to 4 weeks and list the legitimate users.
3. Verify:
   Get-ItemProperty 'HKLM:\SYSTEM\CurrentControlSet\Control\Lsa\MSV1_0' -Name AuditReceivingNTLMTraffic
4. Only then plan restriction (RestrictReceivingNTLMTraffic) per account class.

D. Protected Users for privileged accounts

PLAYBOOK D: Protect privileged accounts
Prerequisites: confirm none of the accounts needs NTLM, unconstrained delegation or Kerberos DES/RC4; pilot with one test admin.
Reboot required: no (takes effect at next sign-in).
Rollback: Remove-ADGroupMember -Identity 'Protected Users' -Members <account> -Confirm:$false

1. Add the account:
   Add-ADGroupMember -Identity 'Protected Users' -Members jdoe-admin
2. Verify:
   Get-ADGroupMember -Identity 'Protected Users' | Select-Object SamAccountName

E. ESXi egress control

PLAYBOOK E: ESXi management network egress (vendor-neutral rule specification)
Prerequisites: inventory of ESXi management addresses and the approved destinations (vCenter, syslog, NTP, update source).
Reboot required: no.
Rollback: remove the deny rule; keep the logging rule to retain visibility.

1. Allow ESXi management range -> vCenter, syslog, NTP, approved update source (by address and port).
2. LOG and DENY ESXi management range -> any other destination.
3. Alert on any hit to rule 2. A hit is an incident lead, not noise (see N4).
4. Add a monitoring rule for one source to one destination across TCP 53, 2222, 3389, 4444, 8443, 9443.
