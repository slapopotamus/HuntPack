GitSpawn: AI Coding Agent Git-Config RCE

Executive Summary

On 2026-09-01, Manifold Security disclosed GitSpawn: a vulnerability class affecting seven AI coding agents (Claude Code, OpenAI Codex, Cursor, Goose, Hermes Agent, Qwen Code, Grok Build) across eight distinct findings. Every one of these agents gathers project context by quietly running git status / git diff in the background: often before the user has typed a prompt, accepted a workspace-trust dialog, or authenticated. Git supports core.fsmonitor, a legitimate performance setting naming a helper program that git launches automatically whenever it refreshes its index. That value is read straight out of the repository's own .git/config. A malicious repository can set it (or the related core.hooksPath, attr.tree, or a clean/process filter command) to an attacker-chosen program, and the moment the agent's background git command touches that repo, the program runs: as the logged-in user, outside the agent's sandbox, and invisible to the agent's own permission/approval system.

Four of the eight findings were still unpatched at publication (Claude Code's second "ultrareview" path, Hermes Agent, Qwen Code, Grok Build). Two formal CVEs anchor the disclosure: CVE-2026-19592 (OpenAI Codex CLI/Desktop, CVSS 7.3, fixed 0.131.0) and CVE-2026-72718 (Goose, fixed 1.44.0). A related, separately-tracked Claude Code vulnerability, CVE-2026-55607 (git-worktree path confusion abusing the same fsmonitor execution sink, CVSS 8.8, fixed 2.1.163), shares the mechanism but a different delivery chain (requires a clone plus prompt-injection content, not merely opening a received folder): see §2 for the reconciliation.

Delivery reality: this cannot arrive via an ordinary git clone, fetch, or pull, since none of those transmit a hostile .git/config. The repository has to arrive as files with its .git directory already inside, exactly how developers routinely receive projects: a zipped project handoff from a contractor, a synced cloud-drive share, a "bug report" archive from a stranger, or a USB stick.

Defender priority: there are no published C2 domains, IPs, or file hashes for this research: the atomic surface is configuration strings and affected agent version numbers, not infrastructure, and the sensor cannot see the contents of a git config file it did not observe being written. The hunt is therefore behavioral: unexpected process ancestry (agent → git → shell/interpreter/network tool), archive extraction immediately preceding a git/agent launch, and the follow-on credential-access and persistence an attacker would chase once code execution lands. Patch/version-pin every affected agent (§12) and inspect .git/config in any repository received as files before opening it in an agent.

07

Native Audit-Log Hunts (non-CQL)

These checks give you ground truth on exactly what Falcon cannot see: the actual contents of a repository's .git/config, and which AI coding agent build is installed. Run before, or alongside, the CQL in §8.

Inspect a received repository before opening it in an agent (any platform)

git config --get core.fsmonitor
git config --get core.hooksPath
git config --get attr.tree
grep -nE "fsmonitor|hooksPath|\[filter" .git/config .gitattributes 2>/dev/null
# Any output naming an external program is a hold-and-review, not an open-in-agent.

Vendor-recommended safe context-gathering (per Manifold / The Hacker News)

# Strip the sink on any ad hoc background git command:
git -c core.fsmonitor=false status
git -c core.fsmonitor=false diff
# Set a permanent default until every agent in use is confirmed patched:
git config --global core.fsmonitor false

Inventory installed AI coding agent versions (run fleet-wide via RMM/MDM)

claude --version
codex --version
cursor --version
goose --version
grok-build --version 2>/dev/null
qwen-code --version 2>/dev/null
# Compare output against the affected/fixed table in Section 4 and the audit block in Section 10.

macOS-specific: confirm sandbox/seatbelt profile is current (CVE-2026-55607 surface)

  • Confirm Claude Code is at 2.1.163+ (CVE-2026-55607) and 2.1.196+ (GitSpawn core.fsmonitor path): both are required; they are different fixes.
  • Review ~/.zshenv, ~/.zprofile, and ~/.bash_profile for unexpected recent modification timestamps.
08

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first — every "Open in Falcon" button below uses this selection.
This is a behavioral hunt: there are no atomic IOCs to filter on. Every query below matches process ancestry and command-line shape, not a known-bad hash or address. Developer endpoints are inherently noisy for git activity, so every card with FP medium+ carries a // TUNING: exclusion: read it before you deploy.
Q1 · AI coding agent → git → shell/interpreter (core execution chain)
CONF HIGHFP MEDCOST LOW

Looks for: the exact GitSpawn execution chain: an AI coding agent binary as the grandparent, git as the parent, and a shell or scripting interpreter as the child. This is the moment core.fsmonitor/core.hooksPath/attr.tree actually fires. FP: git hooks, aliases, and editor integrations legitimately spawn shells; tune the agent-binary and shell lists to your fleet's actual toolset.

// HUNT: AI coding agent -> git -> shell/interpreter (GitSpawn core execution chain)
// MITRE: T1059, T1195
// CONF: high  FP: medium  COST: low | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
// FALSE POSITIVES: legitimate git hooks, shell aliases, editor/IDE git integrations spawning a shell
// TUNING: narrow GrandparentBaseFileName to the agent binaries actually deployed in your fleet; exclude known internal hook scripts by ParentCommandLine
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| GrandparentBaseFileName=/^(claude|claude-code|node|codex|codex-cli|cursor|cursor-agent|goose|goosed|hermes|hermes-agent|qwen-code|qwen|grok-build|grok)(\.exe)?$/i
| ParentBaseFileName=/^git(\.exe)?$/i
| FileName=/^(cmd|powershell|pwsh|wscript|cscript|mshta|rundll32|regsvr32)\.exe$|^(sh|bash|zsh|dash|osascript|python3?|perl|ruby|node)$/i
| table([ComputerName, UserName, GrandparentBaseFileName, ParentBaseFileName, FileName, CommandLine, ParentCommandLine], limit=200)
Q2 · git spawning an unexpected non-helper child
CONF HIGHFP MEDCOST LOW

Looks for: git launching a child that is neither an interactive shell (covered by Q1) nor one of git's own known helper binaries: a download tool, LOLBin, or scripting host, which is what a core.fsmonitor/hooksPath program typically resolves to when it isn't a plain shell. FP: credential-manager helpers and SSH askpass programs; the explicit helper exclusion keeps this narrow, but confirm your environment's git-credential-manager binary name is covered.

// HUNT: git spawns a child that is not a known git helper (fsmonitor/hooksPath payload)
// MITRE: T1059, T1105
// CONF: high  FP: medium  COST: low | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
// FALSE POSITIVES: git-credential-manager/askpass helpers not covered by the exclusion list below
// TUNING: add your credential-manager/askpass binary name to the FileName!= exclusion before deploying as a Detect IOA
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| ParentBaseFileName=/^git(\.exe)?$/i
| FileName=/^(curl|wget|certutil|bitsadmin|mshta|rundll32|regsvr32|powershell|pwsh|cmd)\.exe$|^(curl|wget|sh|bash|zsh|python3?|osascript|nc|ncat|socat)$/i
| FileName!=/^git-(remote-https|remote-http|credential-.*|upload-pack|receive-pack|shell|sh)(\.exe)?$/i
| table([ComputerName, UserName, ParentBaseFileName, FileName, CommandLine, ParentCommandLine], limit=200)
Q3 · git invoked with an explicit dangerous config override
CONF MEDFP MEDCOST LOW

Looks for: a git command line that sets core.fsmonitor, core.hooksPath, or attr.tree via -c: could be attacker automation staging the sink, or an analyst/engineer legitimately running the vendor-recommended git -c core.fsmonitor=false status mitigation. FP: the vendor mitigation itself will match; triage by whether the value is being set to a program (bad) or disabled (expected/good).

// HUNT: git invoked with -c core.fsmonitor=/-c core.hooksPath=/-c attr.tree= on the command line
// MITRE: T1059
// CONF: medium  FP: medium  COST: low | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
// FALSE POSITIVES: the vendor-recommended mitigation "git -c core.fsmonitor=false status" matches this pattern and is expected/benign
// TUNING: exclude CommandLine containing "fsmonitor=false" to isolate the risky (non-"false") sets from the benign mitigation runs
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^git(\.exe)?$/i
| CommandLine=/-c\s+(core\.fsmonitor|core\.hooksPath|attr\.tree)\s*=/i
| table([ComputerName, UserName, ParentBaseFileName, FileName, CommandLine], limit=200)
Q4 · Archive extraction immediately followed by a git/agent launch (delivery vector)
CONF MEDFP HIGHCOST MED

Looks for: the only viable delivery path for GitSpawn: a repository arriving as an archive (zip, tar, 7z) that already contains a .git directory, unpacked immediately before a git or agent process launches on the same host. This cannot happen via git clone. FP: high: routine project setup, dependency installs, and CI runners unpacking build artifacts all match; the join correlates by host only, not by directory, so run it over a narrow window.

// HUNT: Archive extraction immediately followed by git or AI-agent process launch (delivery vector)
// MITRE: T1204.002, T1027
// CONF: medium  FP: high  COST: medium | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
// FALSE POSITIVES: routine project setup (dependency installs unpacking archives), CI runners unzipping build artifacts, legitimate contractor handoffs
// TUNING: run over a narrow window (console time picker, 30-60 min) so the join only correlates temporally close events; exclude CI/build-agent hosts by ComputerName and known software-distribution paths by CommandLine
// LOOKBACK: run over 30-60m, not the default -- see TUNING
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^git(\.exe)?$/i OR GrandparentBaseFileName=/^(claude|claude-code|node|codex|cursor|goose|hermes|qwen-code|grok-build)(\.exe)?$/i
| join(query={
    #event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
    | FileName=/^(tar|unzip|7z|7za|ditto|winrar)(\.exe)?$/i OR FileName=/^Expand-Archive$/i
    | rename(field=FileName, as=ExtractTool)
    | rename(field=CommandLine, as=ExtractCommandLine)
    | table([aid, ExtractTool, ExtractCommandLine])
  }, field=aid, include=[ExtractTool, ExtractCommandLine], mode=inner)
| table([ComputerName, UserName, FileName, CommandLine, ParentBaseFileName, GrandparentBaseFileName, ExtractTool, ExtractCommandLine], limit=200)
Q5 · Credential/secret file access by a process descended from git
CONF HIGHFP LOWCOST LOW

Looks for: the natural next step after landing code execution through GitSpawn: reading SSH private keys, cloud CLI credential files, npm/git credential stores, or netrc. FP: low; legitimate tooling rarely references these exact paths on the command line.

// HUNT: Credential/secret file access by a process descended from git (post-compromise credential harvesting)
// MITRE: T1552.001, T1552.004, T1555
// CONF: high  FP: low  COST: low | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| ParentBaseFileName=/^git(\.exe)?$/i OR GrandparentBaseFileName=/^git(\.exe)?$/i
| (CommandLine="*.ssh/id_rsa*" OR CommandLine="*.ssh\\id_rsa*" OR CommandLine="*.ssh/id_ed25519*" OR CommandLine="*.aws/credentials*" OR CommandLine="*.aws\\credentials*" OR CommandLine="*.config/gcloud*" OR CommandLine="*.npmrc*" OR CommandLine="*.netrc*" OR CommandLine="*.git-credentials*")
| table([ComputerName, UserName, ParentBaseFileName, GrandparentBaseFileName, FileName, CommandLine], limit=200)
Q6 · Git worktree path confusion (CVE-2026-55607-class)
CONF HIGHFP LOWCOST LOW

Looks for: a git worktree created with a name/path of .git, which git tooling then interprets as a real git directory rather than a working tree: the CVE-2026-55607 technique that abuses fsmonitor execution via symlink/path confusion. FP: low; legitimate workflows do not name a worktree .git.

// HUNT: Git worktree created with a name/path of ".git" (worktree/symlink path confusion)
// MITRE: T1036.005, T1211
// CONF: high  FP: low  COST: low | REQUIRES: ProcessRollup2, SyntheticProcessRollup2
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^git(\.exe)?$/i
| CommandLine=/worktree\s+add/i
| (CommandLine="*worktree add .git*" OR CommandLine="*worktree add \".git\"*" OR CommandLine="*worktree add './.git'*")
| table([ComputerName, UserName, ParentBaseFileName, GrandparentBaseFileName, CommandLine], limit=200)
Q7 · Outbound network connection from a shell descended from git
CONF MEDFP HIGHCOST MED

Looks for: a shell or scripting interpreter descended from git that also makes an outbound connection off the internal network: staging a second-stage payload after the RCE moment. FP: high: this correlates by host, not by exact process, so any unrelated outbound traffic from the host in the same window will match; narrow the window and exclude known-good destinations before trusting hit volume.

// HUNT: Outbound network connection from a shell/interpreter descended from git (post-RCE staging/C2)
// MITRE: T1105, T1071
// CONF: medium  FP: high  COST: medium | REQUIRES: ProcessRollup2, NetworkConnectIP4
// FALSE POSITIVES: host-level correlation, not process-level -- any unrelated outbound traffic in the same window will match
// TUNING: run over a narrow window (console time picker, 15-30 min); exclude allow-listed corporate-egress destinations by RemoteAddressIP4
// LOOKBACK: run over 15-30m, not the default -- see TUNING
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^(cmd|powershell|pwsh)\.exe$|^(sh|bash|zsh|dash|osascript|python3?|perl|ruby|node|curl|wget)$/i
| ParentBaseFileName=/^git(\.exe)?$/i OR GrandparentBaseFileName=/^git(\.exe)?$/i
| join(query={
    #event_simpleName=NetworkConnectIP4
    | !cidr(RemoteAddressIP4, subnet="10.0.0.0/8")
    | !cidr(RemoteAddressIP4, subnet="172.16.0.0/12")
    | !cidr(RemoteAddressIP4, subnet="192.168.0.0/16")
    | !cidr(RemoteAddressIP4, subnet="127.0.0.0/8")
    | table([aid, RemoteAddressIP4, RemotePort])
  }, field=aid, include=[RemoteAddressIP4, RemotePort], mode=inner)
| table([ComputerName, UserName, FileName, ParentBaseFileName, GrandparentBaseFileName, CommandLine, RemoteAddressIP4, RemotePort], limit=200)

// MITRE: T1547.001, T1053.005

L1 triage checklist (for a Q1/Q2/Q6 hit)

  1. Confirm the AI coding agent's installed version against the affected/fixed table in §4: is this endpoint actually running a vulnerable build?
  2. Pull the full command line and working directory of the flagged git process; identify the repository path.
  3. If the repository is reachable, inspect its .git/config and .gitattributes for core.fsmonitor, core.hooksPath, attr.tree, or filter commands (§7).
  4. Identify how the repository arrived: git log/reflog will show no clone history for a files-delivered repo; check Downloads, sync-folder, or USB provenance.
  5. Check the flagged host for Q5 (credential access), Q7 (outbound connections), Q8/Q9 (persistence) hits in the same window.
  6. If the helper program executed, treat the endpoint as compromised: rotate any credentials the logged-in user could reach (SSH keys, cloud tokens, git-credential store, saved API tokens).
  7. Isolate the host via Falcon RTR pending investigation; preserve the offending repository folder for analysis rather than deleting it.
  8. Patch/upgrade the agent to a fixed version (§12) before returning the host to service.

Pivot queries

  • Host-scoped: re-run Q1, Q5, Q7, Q8, Q9 filtered to the single flagged aid over the preceding 24h to reconstruct the full session.
  • Environment-wide: re-run Q4 (archive-extraction → git/agent) across all developer endpoints for the prior 7 days to check for other deliveries of the same repository.

Hardening: Tiered

Immediate (this week)
  • Disable the fsmonitor sink globally on every developer endpoint: git config --global core.fsmonitor false: until every AI coding agent in use is confirmed on a fixed build. (MITRE M1042 Disable or Remove Feature or Program · Manifold/The Hacker News vendor mitigation guidance)
  • Version-pin and upgrade every affected agent to the fixed builds in §4/§10 (Claude Code 2.1.196+ and 2.1.163+, Codex CLI 0.131.0+, Goose 1.44.0+); treat Hermes Agent, Qwen Code, and Grok Build as unpatched regardless of version until vendor fixes ship. (MITRE M1051 Update Software · CVE-2026-19592 / CVE-2026-72718 / CVE-2026-55607 fix records)
  • Instruct developers to inspect .git/config before opening any repository received as files (zip, cloud-drive share, USB, "bug report" archive): never a normal clone/fetch/pull: using the audit commands in §7/§10. (MITRE M1017 User Training · ⚠ best-practice, no formal benchmark)
Near term (1–4 weeks)
  • Deploy Q1/Q2/Q6 as scheduled searches (promoting to Detect IOAs after the benign-baseline pass in §11) so the execution chain is caught even if an agent is missed during the version-pin rollout. (MITRE M1040 Behavior Prevention on Endpoint)
  • Route archive/zip handoffs (contractor deliverables, "bug report" attachments) through a scan-and-quarantine step that flags any archive containing a .git directory for manual config review before it reaches a developer's agent. (MITRE M1038 Execution Prevention · ⚠ best-practice, no formal benchmark)
  • Set safe.directory scoping so git does not implicitly trust arbitrary extracted/synced folders, reducing the surface that silently triggers background context-gathering commands. (MITRE M1042 · git-scm.com safe.directory documentation)
Strategic (1–3 months)
  • Standardize on agent versions via a managed software catalog with automatic update enforcement for AI coding agents, closing the "which build is actually installed" gap that made this class of bug persist across releases. (MITRE M1051 · CIS Control 2: Inventory and Control of Software Assets)
  • Application allowlisting / execution control on developer endpoints for the helper-program shape this bug abuses: an unsigned or unexpected binary/script launched as a child of git should require explicit approval. (MITRE M1038 · NIST SP 800-167 Application Whitelisting)
  • Sandbox or VM-isolate first-time-seen repositories (contractor handoffs, external contributions received as files) before opening them in any AI coding agent, so a live fsmonitor/hooksPath payload cannot reach the primary developer identity/credential set even if it fires. (MITRE M1048 Application Isolation and Sandboxing · NIST SP 800-207 Zero Trust Architecture)

Deployable Playbooks

Playbook A: Disable the fsmonitor sink fleet-wide (Windows / macOS / Linux, shell)

Prerequisites: git 2.x installed; ability to push a global gitconfig change via RMM/MDM/Ansible to developer endpoints. Reboot required: none. Rollback: re-enable with git config --global core.fsmonitor true (or remove the line from the global gitconfig) once every agent in the fleet is confirmed patched.

# 1. Push to every developer endpoint's per-user git global config
git config --global core.fsmonitor false

# 2. Verify it took effect
git config --get core.fsmonitor
# expect: false

# 3. (Optional, stronger) also neutralize the other reported sinks globally where supported by your git version:
git config --global core.hooksPath ""
# Rollback: git config --global --unset core.fsmonitor
#           git config --global --unset core.hooksPath

Playbook B: Version-pin and upgrade affected agents

Prerequisites: package-manager or installer access for each agent (npm/pip/brew/winget/direct installer); a maintenance window is not required since these are user-space CLI tools, but active agent sessions should be closed first. Reboot required: none for CLI agents; Codex Desktop / Cursor (Electron apps) require the application to restart, not the OS. Rollback: pin back to the prior version only if the upgrade breaks a workflow: re-exposes the vulnerability, so pair any rollback with Playbook A staying active.

npm install -g @anthropic-ai/claude-code@latest   # need >=2.1.196 AND >=2.1.163
claude --version

npm install -g @openai/codex@latest
codex --version

# Goose -- need >=1.44.0
# (use your platform's Goose install/update mechanism; verify via)
goose --version

# Rollback: revert to the previously pinned package version via your package
# manager's install-specific-version syntax if the new build breaks a workflow.

Playbook C: Repository intake review (any platform received as files, not cloned)

Prerequisites: none beyond a shell and git itself; suitable for a pre-commit-style local script or a SOAR/EDR RTR script triggered on archive extraction. Reboot required: none. Rollback: none required: this is a read-only inspection step with no persistent system change.

#!/usr/bin/env bash
# Run against any repository that arrived as a zip/tar/synced-folder/USB copy
# (never needed for a plain "git clone" -- that path cannot carry these settings).
REPO_DIR="$1"
cd "$REPO_DIR" || exit 1
echo "== Checking $REPO_DIR/.git/config and .gitattributes for named-program sinks =="
grep -nE "fsmonitor|hooksPath|\[filter" .git/config .gitattributes 2>/dev/null
if [ $? -eq 0 ]; then
  echo "HOLD: this repo's config names an external program -- review before opening in any AI coding agent."
  exit 1
fi
echo "No known GitSpawn sink strings found. Still confirm agent version against Section 4/10 before proceeding."

Playbook D: Safe-directory scoping (git >=2.35.2, all platforms)

Prerequisites: git version supporting safe.directory (2.35.2+, effectively all currently-supported git releases). Reboot required: none. Rollback: git config --global --unset-all safe.directory restores git's prior implicit-trust behavior.

# Scope trust to explicitly-approved project roots instead of trusting every
# directory git is pointed at (reduces the set of folders where an agent's
# background git command will silently operate on an unreviewed .git/config):
git config --global --add safe.directory /Users/*/projects/*
git config --global --add safe.directory C:/Users/*/source/*
# Verify:
git config --get-all safe.directory
# Rollback: git config --global --unset-all safe.directory

Known gap: there is no way to detect a malicious .git/config value purely from its presence on disk with EDR telemetry: the sensor sees the process that reads it (the git launch) and the process it spawns, not the file's contents. This pack closes that gap behaviorally (§8 Q1–Q3) rather than via file-content inspection, and closes it operationally via the intake-review playbook (§13C) that DOES read the file.
