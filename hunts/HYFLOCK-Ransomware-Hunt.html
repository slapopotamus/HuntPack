Executive Summary

HYFLOCK is a ransomware operation that Check Point Exposure Management traced across four Windows encryptor generations from April to October 2026. The core is Rust (Check Point calls it Rust/Nishi). July added a separate loader that carries the payload, configuration and key material; an earlier October build used a Go carrier; the October 17 build is a standalone Rust encryptor that copies itself into a directory made to look like a software-update component and registers a scheduled task. Encryption uses 16-byte symmetric keys, AES counter-mode and RSA-protected recovery material.

What the research establishes. Confirmed in analysis: file encryption, scheduled-task registration, network-share activity (TCP/445 probing and administrative-share processing) and recovery-sabotage attempts. Not established: how any victim was first compromised, domain-wide propagation (Group Policy spreading was disabled in the recovered configuration), RDP-session resilience, BYOVD driver killing, and data exfiltration. The eight victim claims posted on October 13 are unverified attacker claims, not confirmed incidents.

Recovery reality. There is no decryptor. The October 17 build encrypted only the first 4,096 bytes of larger files in testing, and Check Point recovered 73 CRC-valid components from seven Office files without a key. That is partial content recovery, not decryption. An earlier October build has a defect that can permanently discard file data even with the correct key. Do not tell stakeholders that files are recoverable.

Indicator posture. Check Point's blog publishes no hashes or network indicators, but its full report (a PDF linked from the blog) does: eight SHA-256 values and a table of runtime artifact names. No C2 domain or IP is published by any source. The pack therefore leads with behaviour (EdgeUpdate-style staging, scheduled task, eu.exe / eu.cfg / system_config.dat, share artifacts, ransom note, recovery destruction) and ships six executable hashes as DETECT-only.

Defender priority: alert on any process or scheduled task whose path is ProgramData\EdgeUpdate_<suffix>\ (Q1, Q3, Q4) and on shadow-copy or backup-catalog destruction (Q11); verify offline, tested backups today, because a keyless recovery path does not exist.

Static trailer check on preserved encrypted-file copies

The HFLKEY01 marker is the only artifact that proves a file came from the October 17 build. It is visible to file inspection, not process telemetry. Use this on copies pulled for evidence preservation.

# Read-only: test a suspect file for the October 17 trailer marker. Run on a COPY, never the original.
param([Parameter(Mandatory)][string]$Path)
$fs = [System.IO.File]::OpenRead($Path)
try {
  if ($fs.Length -lt 556) { 'too small for a 556-byte trailer'; return }
  $fs.Seek(-556, 'End') | Out-Null
  $buf = New-Object byte[] 556
  $fs.Read($buf, 0, 556) | Out-Null
  # layout (Check Point): 8 B prefix length | 16 B IV | 8 B marker | 12 B run id | 512 B wrapped key
  $marker = [System.Text.Encoding]::ASCII.GetString($buf, 24, 8)
  $runId  = [System.Text.Encoding]::ASCII.GetString($buf, 32, 12)
  if ($marker -eq 'HFLKEY01') { "HFLKEY01 trailer present; run id: $runId" } else { 'no HFLKEY01 marker at the expected offset' }
} finally { $fs.Close() }

Q1 · Process running from a ProgramData\EdgeUpdate_* staging directory
CONF HIGHFP LOWCOST LOW

Looks for: Any process image under \ProgramData\EdgeUpdate_<suffix>\. This is the October 17 build's self-staged copy (eu.exe, started with --daemon by the scheduled task). The match is on the stable prefix only; the suffix is variable and is never fabricated. FP: The genuine Microsoft Edge updater lives under Program Files (x86)\Microsoft\EdgeUpdate and ProgramData\Microsoft\EdgeUpdate. Neither contains the underscore-suffixed directory directly under ProgramData, so the pattern does not collide with it. Confirm that on your fleet before alerting.

Hardening: Tiered & Deployable

No hardening here depends on a decryptor existing, because none does. Controls map to MITRE mitigations (the why) and to a platform baseline or vendor guide (the what).

Immediate (this week)
  • Offline, immutable backups and a tested restore (M1053 Data Backup; T1486, T1490). There is no keyless recovery path, so the backup is the recovery. Keep at least one copy that credentials from the domain cannot delete, and restore a real server end to end.
  • Audit scheduled-task creation (M1047 Audit; T1053.005): enable Security 4698 auditing and the TaskScheduler Operational log. Verify with auditpol /get /subcategory:"Other Object Access Events". Benchmark: CIS Microsoft Windows audit policy section.
  • Attack Surface Reduction rules in audit mode (M1040 Behavior Prevention on Endpoint, M1038 Execution Prevention): ransomware protection, prevalence/age/trusted-list executable block, and PSExec/WMI process creation. Microsoft Defender ASR documentation.
  • Hunt now: run Q1, Q3, Q4 and Q11 across the estate for the last 30 days.
Near term (1 to 4 weeks)
  • Restrict inbound SMB on workstations (M1030 Network Segmentation, M1037 Filter Network Traffic; T1021.002, T1135): allow TCP/445 only from file servers, management hosts and jump hosts. Host firewall via GPO.
  • Share least privilege: remove Everyone and Authenticated Users from share and NTFS ACLs, split write access by role (M1022 Restrict File and Directory Permissions, M1026 Privileged Account Management). Check Point lists network-share access reviews and segmentation as relevant controls.
  • Unique local administrator passwords (Windows LAPS; M1026, M1018): the October 17 build processed administrative shares, and a shared local admin password makes those shares reachable everywhere.
  • Controlled Folder Access on file-owning endpoints, audit then enforce (M1040).
  • SMB signing required on servers (M1037); test legacy device impact first.
Strategic (1 to 3 months)
  • Application control (WDAC, or AppLocker for admin-exempt gaps) so that unsigned binaries cannot start from ProgramData (M1038). Default AppLocker rules exempt administrators, so a path rule alone does not stop an admin-context encryptor. A path rule for ProgramData\EdgeUpdate_* belongs in audit mode first; never write a rule against the genuine Microsoft updater paths.
  • Tiered administration and segmentation of file and backup servers (M1030, M1026): backup consoles and repositories reachable only from dedicated hosts.
  • Retention and offsite copies sized for no-decryptor recovery, including the data owners' restore time objectives.

Recovery and decryptor position

There is no decryptor. Check Point states that no evidence-backed keyless decryptor is available, that no complete victim file was decrypted and that no plaintext AES key or RSA private key was recovered. Partial recovery from the October 17 build exists only because larger files were encrypted for their first 4,096 bytes; Check Point recovered 73 Office components from seven files. An earlier October build can permanently discard file data, so even the correct key may not restore everything. Recovery outcomes depend on which build hit you.
  • Preserve first. Keep several encrypted files, the ransom note, the run identifier and any console or memory evidence from the original execution; do not rename encrypted files in bulk, and do not run the encryptor again (a new run generates new key material). Check Point notes plaintext-key diagnostics are a conditional opportunity only if output from the original run survives.

  • Restore from tested backups into a clean environment; treat prefix-only recovery as salvage, not as a plan.
