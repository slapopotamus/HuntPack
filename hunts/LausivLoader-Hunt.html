Executive Summary

LausivLoader is a multi-stage Windows malware loader documented by the SANS Internet Storm Center (Jan Kopriva, diary 33348, published 2026-09-17, last updated 2026-09-22). It arrives as a purchase-quotation spearphishing lure carrying an obfuscated JavaScript file inside a .r01 archive. The attacker's objective is to establish durable logon persistence disguised as a Microsoft Edge Update task, then stage a four-layer loader chain — JavaScript → PowerShell → first .NET loader → second .NET downloader — that ultimately hides its final payload inside a PNG image's iTXt metadata chunk, decoding it into a .NET assembly or native EXE that is executed via reflection or process hollowing.

The single most distinctive TTP is how the JavaScript hands decode instructions to PowerShell: instead of hardcoding file paths on the command line, the JS stage sets variables in its own process environment, which the intermediate conhost.exe --headless process and the child powershell.exe process inherit. This defeats naive analysis that extracts only the decoded PowerShell command line, and it means the file paths and decode context never appear together in any single visible artifact.

Highest-value defensive angle: because the payload content and the env-var handoff itself are not independently visible in standard Falcon process telemetry, this pack leans on process lineage (script host → conhost.exe --headless → PowerShell) and the scheduled task masquerade (MicrosoftEdgeUpdateTaskCore) as the highest-fidelity, lowest-FP detection surface — both are structurally unusual regardless of how the payload content is obfuscated.

Defender priority: the env-var handoff, in-memory AMSI patch, RC4/AES/GZip/DEFLATE transforms, and the final reflective-load/process-hollowing step are not independently visible via standard Falcon process/file events — do not rely on payload-content inspection. Hunt the process-lineage and persistence signatures in §8 first; treat any hit as high-priority triage given how few legitimate reasons exist to produce this lineage.

Native Audit-Log Hunts

Non-CQL checks for organizations without full Falcon coverage on a given surface, or as corroborating pivots.

  1. Email gateway: search inbound mail for multi-volume archive attachments (.r00–.r99, .zip, .7z) containing script files, where SPF and/or DMARC evaluated to fail/none but the message was still delivered — that policy gap is exactly what let this sample through the sending gateway's own defenses. Cross-reference purchase-order / quotation lure language in the subject or body.
  2. Task Scheduler Operational log (Microsoft-Windows-TaskScheduler/Operational, Event ID 106 — task registered): filter for task names containing MicrosoftEdgeUpdateTaskCore, or for any task whose registering process is not taskeng.exe/svchost.exe (a task registered via COM from wscript.exe is anomalous). Note that genuine Edge Update tasks are named MicrosoftEdgeUpdateTaskMachineCore / MicrosoftEdgeUpdateTaskMachineUA — the missing "Machine" segment is itself a naming mismatch worth flagging.
  3. PowerShell Script Block Logging (Event ID 4104, Microsoft-Windows-PowerShell/Operational): hunt decoded script-block content for AES/GZipStream/Assembly.Load/entry-point patterns, and correlate 4104 events whose parent chain includes conhost.exe with a --headless flag.
  4. Sysmon Event ID 1 (Process Create) — the same lineage hunt as Q3 for non-Falcon estates: ParentImage=conhost.exe AND CommandLine contains --headless AND Image=powershell.exe.
  5. Windows Defender Operational log (Event ID 1116/1117): any detection naming this family, or generic loader/heuristic detections on files under %TEMP%\<random>\ or %LOCALAPPDATA%\Microsoft\PhotoEngine\.
  6. AMSI ETW telemetry (if instrumented): hunt for gaps in AMSI scan coverage for a PowerShell process immediately following the conhost.exe lineage — a missing AMSI scan record where one would normally be expected can indicate a successful patch of AmsiScanBuffer/AmsiScanString.

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first — every "Open in Falcon" button below uses this selection.
Q1 · Script Host Executing a Double-Extension Script
CONF HIGHFP MEDIUMCOST LOW

Looks for: wscript.exe/cscript.exe executing a script whose name has a spoofed double extension immediately before .js/.vbs/.jse/.vbe — the LausivLoader lure pattern. FP: rare legitimate double-extension automation filenames.

// HUNT: Script Host Executing a Double-Extension Script
// MITRE: T1566.001, T1204.002, T1059.007
// CONF: high
// FP: medium
// COST: low
// REQUIRES: Falcon process telemetry (ProcessRollup2 / SyntheticProcessRollup2)
// FALSE POSITIVES: legitimate installers or IT scripts that name files with double extensions (rare); vendor update wrapper scripts
// TUNING: exclude known-good software-deployment paths (RMM script staging directories) and signed installer wrapper scripts once baselined
// LOOKBACK: 7d
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^(wscript|cscript)\.exe$/i
| CommandLine=/\.\.(js|jse|vbs|vbe)\b/i
| table([ComputerName, UserName, FileName, ParentBaseFileName, CommandLine, TargetProcessId, aid, @timestamp])
Q2 · conhost.exe Launching PowerShell with --headless
CONF HIGHFP LOWCOST LOW

Looks for: conhost.exe invoked directly with a --headless flag and a PowerShell target embedded in its own command line — the distinctive JS-to-PowerShell handoff mechanism. FP: essentially none observed; this is not how conhost.exe is normally invoked.

// HUNT: conhost.exe Launching PowerShell with --headless
// MITRE: T1564.003, T1059.001
// CONF: high
// FP: low
// COST: low
// REQUIRES: ProcessRollup2
// FALSE POSITIVES: none commonly observed; conhost.exe is not normally invoked directly against a target executable with --headless by legitimate software
// TUNING: if a legitimate internal tool is found using this pattern, exclude it by SHA256HashData rather than by path (paths are trivially spoofable)
// LOOKBACK: 7d
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^conhost\.exe$/i
| CommandLine=/--headless/i
| CommandLine=/powershell\.exe/i
| table([ComputerName, UserName, ParentBaseFileName, FileName, CommandLine, TargetProcessId, ParentProcessId_decimal, aid, @timestamp])
Q3 · Full Chain Correlation: Script Host → conhost --headless → Encoded PowerShell
CONF HIGHFP LOWCOST MEDIUM

Looks for: the complete three-generation process lineage (grandparent script host, parent conhost.exe --headless, child hidden/encoded PowerShell) in one query — the single highest-fidelity signature in this pack. FP: very low; requires all three unusual conditions to co-occur.

// HUNT: Full Chain Correlation - Script Host to conhost --headless to Encoded PowerShell
// MITRE: T1059.007, T1059.001, T1564.003
// CONF: high
// FP: low
// COST: medium
// REQUIRES: ProcessRollup2 with parent/grandparent lineage populated
// FALSE POSITIVES: rare; some legitimate hidden automation also uses -W Hidden -EncodedCommand, but the wscript-to-conhost---headless grandparent lineage is highly unusual outside this loader family
// TUNING: exclude known internal automation/RMM tooling that legitimately chains through conhost.exe in your environment, once confirmed benign ⚠ validate in tenant
// LOOKBACK: 7d
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/^powershell\.exe$/i
| ParentBaseFileName=/^conhost\.exe$/i
| GrandparentBaseFileName=/^(wscript|cscript)\.exe$/i
| CommandLine=/-nop\b|-noprofile/i
| CommandLine=/-w\s+hidden|-windowstyle\s+hidden/i
| CommandLine=/-enc\b|-encodedcommand/i
| table([ComputerName, UserName, GrandparentBaseFileName, ParentBaseFileName, FileName, CommandLine, TargetProcessId, aid, @timestamp])

Q7 · Rare Outbound HTTPS Destinations from a PowerShell Process (Stage-4 Egress Pivot)
CONF MEDIUMFP HIGHCOST MEDIUM

// CONF: medium
// FP: high
// COST: medium

Hardening — Tiered

Immediate (this week)
  1. ASR rule — Block JavaScript/VBScript from launching downloaded executable content (D3E037E1-3EB8-44C8-A917-57927947596D) in Block mode. MITRE M1038. CIS Microsoft Windows Benchmark 18-9-47-5-1-6. Directly blocks the stage-1→stage-2 handoff pattern.
  2. ASR rule — Block execution of potentially obfuscated scripts (5BEB7EFE-FD9A-4556-801D-275E5FFC04CC) in Block mode. MITRE M1038, M1040. CIS 18-9-47-5-1-7. Targets the 450-junk-comment-line obfuscation technique directly. ⚠ Windows Defender AV must be active (or passive-mode alongside Falcon) for ASR to evaluate — confirm compatibility with your EDR vendor if Falcon is primary AV.
  3. Enable PowerShell ScriptBlock Logging and Module Logging (Event ID 4104). MITRE M1047. CIS 18-9-100-2/18-9-100-3. Restores visibility into the decoded -EncodedCommand content, even though the env-var payload paths themselves will not appear.
  4. Block executable/script content from the email gateway for archive attachments containing script files (.js/.vbs/.jse/.wsf) inside .zip/.r0x/.7z containers, and hard-fail delivery on SPF/DMARC failure. MITRE M1017, M1031, M1054. Client-side complement: ASR rule BE9BA2D9-53EA-4CDC-84E5-9B1EEEE46550 (Block executable content from email client and webmail).
Near term (1–4 weeks)
  1. AppLocker/WDAC path rule blocking wscript.exe/cscript.exe execution from %TEMP%, %LOCALAPPDATA%, and archive-extraction staging paths for standard users; allow only signed/approved automation. MITRE M1038, M1033. ⚠ pilot ring first — some legitimate installers stage scripts in %TEMP%.
  2. Audit and lock down Task Scheduler task creation via COM (Schedule.Service) for non-admin users; review AD/GPO delegation on the \Microsoft\Windows\ scheduled-task folders. MITRE M1018, M1022, M1047.
  3. Restrict registry and Task Scheduler root write access; require elevation for new top-level task registration outside \Microsoft\Windows\... paths. MITRE M1024, M1022.
Strategic (1–3 months)
  1. PowerShell Constrained Language Mode / WDAC-enforced PowerShell policy fleet-wide, removing free-form -EncodedCommand from the standard user's effective capability set outside signed, allow-listed automation. MITRE M1042, M1038. ⚠ significant piloting required — breaks ad hoc admin scripting; needs a signed-script exception workflow.
  2. DNS-layer filtering (block newly-registered/uncategorized domains for standard endpoints) to catch stage-4 payload hosts like yapw[.]life before the fact, independent of any single atomic IOC's inevitable rotation. MITRE M1021, M1037. Vendor best-practice (Cisco Umbrella / Cloudflare Gateway category policy). ⚠ best-practice, no formal CIS benchmark entry for third-party DNS filtering products.

Deployable Playbooks

Playbook: LausivLoader Delivery & Execution-Chain Hardening (T1566.001, T1059.007, T1027)

MITRE: T1566.001, T1059.007, T1027 → M1038, M1040, M1047
Estimated deploy time: 2–3 hours (Immediate tier), plus a 1-week Audit-mode pilot for the ASR rules
Prerequisites: Windows 10 1809+ / Server 2019+, Microsoft Defender Antivirus present (active or passive alongside Falcon), local admin / GPO management rights
Reboot required: No for ASR rules and logging (take effect on next policy refresh / new process); Yes only if PowerShell v2 is also being removed in the same maintenance window

Step 1 — Enable ASR rule: Block JS/VBScript from launching downloaded executable content

What it does: Defender blocks JavaScript/VBScript from launching downloaded executable content.
Why it works: directly interrupts the stage-1-to-stage-2 handoff this loader depends on.

$asrRule = 'D3E037E1-3EB8-44C8-A917-57927947596D'
Set-MpPreference -AttackSurfaceReductionRules_Ids $asrRule -AttackSurfaceReductionRules_Actions AuditMode
Write-Output "ASR rule $asrRule set to Audit -- review Event ID 1122 for 1 week before Block"

GPO path: Computer Configuration > Administrative Templates > Windows Components > Microsoft Defender Antivirus > Microsoft Defender Exploit Guard > Attack Surface Reduction > Configure Attack Surface Reduction rules

Verify:

$ids = (Get-MpPreference).AttackSurfaceReductionRules_Ids
$actions = (Get-MpPreference).AttackSurfaceReductionRules_Actions
for ($i = 0; $i -lt $ids.Count; $i++) { if ($ids[$i] -eq 'D3E037E1-3EB8-44C8-A917-57927947596D') { "Action: $($actions[$i]) (1=Block, 2=Audit, 6=WarnUser)" } }

After a clean 1-week audit period, flip to Block:

Set-MpPreference -AttackSurfaceReductionRules_Ids 'D3E037E1-3EB8-44C8-A917-57927947596D' -AttackSurfaceReductionRules_Actions Enabled

Rollback:

Set-MpPreference -AttackSurfaceReductionRules_Ids 'D3E037E1-3EB8-44C8-A917-57927947596D' -AttackSurfaceReductionRules_Actions Disabled

Prerequisites: Defender AV present. Reboot required: No. Rollback: shown above — immediate, no reboot needed.

Step 2 — Enable ASR rule: Block execution of potentially obfuscated scripts

What it does: Defender blocks scripts that use heavy obfuscation (matches the 450-junk-comment-line technique).
Why it works: targets the obfuscation layer directly, independent of the specific lure filename.

$asrRule = '5BEB7EFE-FD9A-4556-801D-275E5FFC04CC'
Set-MpPreference -AttackSurfaceReductionRules_Ids $asrRule -AttackSurfaceReductionRules_Actions AuditMode
Write-Output "ASR rule $asrRule set to Audit -- review Event ID 1122 for 1 week before Block"

Verify: same pattern as Step 1, substituting the rule GUID.

Monitor for false positives: Event ID 1121 (Block) / 1122 (Audit) in Microsoft-Windows-Windows Defender/Operational. If a legitimate obfuscated script (rare) trips it, add a targeted exclusion:

Add-MpPreference -AttackSurfaceReductionOnlyExclusions 'C:\Program Files\YourTool\script.js'

Rollback:

Set-MpPreference -AttackSurfaceReductionRules_Ids '5BEB7EFE-FD9A-4556-801D-275E5FFC04CC' -AttackSurfaceReductionRules_Actions Disabled

Prerequisites: Defender AV present. Reboot required: No. Rollback: shown above.

Step 3 — Enable PowerShell ScriptBlock and Module Logging

What it does: logs decoded PowerShell script-block content to Event ID 4104.
Why it works: the env-var handoff hides file paths from the command line, but the decoded script block executed inside PowerShell still lands in this log once decrypted in memory.

$sbl = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging'
New-Item -Path $sbl -Force | Out-Null
New-ItemProperty -Path $sbl -Name 'EnableScriptBlockLogging' -Value 1 -PropertyType DWORD -Force | Out-Null

$ml = 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging'
New-Item -Path $ml -Force | Out-Null
New-ItemProperty -Path $ml -Name 'EnableModuleLogging' -Value 1 -PropertyType DWORD -Force | Out-Null
Write-Output "ScriptBlock + Module logging enabled"

GPO path: Computer Configuration > Administrative Templates > Windows Components > Windows PowerShell > Turn on PowerShell Script Block Logging → Enabled; and ... > Turn on Module Logging → Enabled, modules = *

Verify:

(Get-ItemProperty 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging' -ErrorAction SilentlyContinue).EnableScriptBlockLogging
# expect 1
Get-WinEvent -LogName 'Microsoft-Windows-PowerShell/Operational' -MaxEvents 1 -ErrorAction SilentlyContinue

Rollback:

Remove-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ScriptBlockLogging' -Name 'EnableScriptBlockLogging' -ErrorAction SilentlyContinue
Remove-ItemProperty -Path 'HKLM:\SOFTWARE\Policies\Microsoft\Windows\PowerShell\ModuleLogging' -Name 'EnableModuleLogging' -ErrorAction SilentlyContinue

Prerequisites: PowerShell 5.0+. Reboot required: No — applies to new PowerShell sessions immediately. Rollback: shown above, no reboot needed.

Step 4 — AppLocker path rule: block script hosts from staging/temp paths

What it does: denies wscript.exe/cscript.exe execution of scripts from %TEMP%, %LOCALAPPDATA%, and common archive-extraction staging directories for standard users.
Why it works: the delivery mechanism depends on the extracted JS running from exactly these paths; this closes the execution surface even if the ASR rules in Steps 1–2 are bypassed by a future variant.

# Run in an elevated PowerShell session; requires AppLocker policy already provisioned via GPO
$rule = New-AppLockerPolicy -RuleType Path -User Everyone -Action Deny `
  -PathCondition "%OSDRIVE%\Users\*\AppData\Local\Temp\*","%LOCALAPPDATA%\*" -Verbose
Write-Output "Review the generated rule, then merge into your AppLocker GPO in AUDIT mode first"

GPO path: Computer Configuration > Windows Settings > Security Settings > Application Control Policies > AppLocker > Script Rules — add a Deny path rule scoped to Everyone, then explicitly allow your known-good automation by publisher or hash.

Verify:

Get-AppLockerPolicy -Effective -Xml | Select-String "AppData\\Local\\Temp"

Rollback:

# Remove the specific Deny rule GUID from the AppLocker GPO and run:
gpupdate /force

Prerequisites: AppLocker policy infrastructure already provisioned (Application Identity service running); pilot ring with 2–4 weeks of Audit-mode logging before enforcing. Reboot required: No, but the Application Identity service must be running (a service restart, not a reboot). Rollback: shown above — remove the rule and force a GPO refresh; no reboot needed.
