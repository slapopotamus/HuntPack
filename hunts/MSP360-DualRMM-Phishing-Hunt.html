Executive Summary

Starting in July 2026, Microsoft Defender Experts observed phishing campaigns across multiple industries that distribute a legitimate, digitally signed MSP360 Remote Monitoring and Management (RMM) installer (v2.5.0.67) under deceptive filenames themed as meeting invitations, PDF-reader updates, e-cards, job offers, document-signature requests, and government benefit statements. The attacker's objective is not to exploit software, but to get a victim to run a trusted, vendor-signed management tool voluntarily, converting a single click into full remote administration of the endpoint.

Once installed, the MSP360 RMM Agent service is abused to launch PowerShell and silently install a second, independent remote-access tool, ConnectWise ScreenConnect, via msiexec.exe /qn. This "dual-RMM" design gives the operator redundant access: removing one tool does not evict the other. ScreenConnect's built-in RunFile feature is then used to transfer and execute a battery of credential-theft and defense-evasion utilities named to mimic Windows, Defender, and Phone Link components. The activity is unattributed; Microsoft has not linked it to a named threat actor, and a parallel July 2026 cluster achieved the same outcome using Faronics Deploy Agent instead of MSP360 as the first-stage tool.

The highest-value defensive angle is not alerting on MSP360 or ScreenConnect presence alone: both are legitimate tools many MSPs run deliberately. The reliable discriminators are: (1) the distinctive _rmm_v2.5.0.67_oid filename suffix baked into every observed lure, (2) the co-occurrence of MSP360 and ScreenConnect installing on the same endpoint within a short window, and (3) the revoked code-signing certificate used on the observed installer sample.

Defender priority: Hunt the filename pattern and the dual-RMM correlation first (Q1 and Q5 in Section 8): they fire on the attacker's unique behavior rather than on tool presence, and both are corroborated by multiple independent sources.

Consolidated IOC Table

Every atomic indicator in this pack ships detect, not prevent. That is deliberate and it is the most important thing to understand about this campaign. The binaries here are not malware. Microsoft's own IOC table labels the four service hashes "Legitimate MSP360 RMM Agent Service observed during the campaign", and the installer is the genuine MSP360 RMM v2.5.0.67 package carrying a deceptive filename. A bulk prevent import of these hashes would break MSP360 for any organization that legitimately licenses it. Microsoft does not recommend blocking them either: its guidance is to hunt for unapproved deployments and to block unapproved RMM software by publisher certificate through application control. See Section 12 for that control, and the conditional-escalation note below before changing any action value.

38 atomic indicators are carried in this pack, all traced to the saved source snapshots in MSP360-DualRMM-Phishing-Hunt-sources/. Source counts below record corroboration strength, which is a separate question from whether an indicator is safe to block.

Conditional escalation to prevent: escalate the installer SHA256/SHA1 only if MSP360 is not approved software anywhere in your estate, and only after confirming no business unit licenses it. The four service hashes should remain detect in all environments: they are stock product files, so a hit means "MSP360 is installed here", not "this host is compromised". Native Audit-Log Hunts (non-CQL)

Email gateway / M365 Defender

  • Search mail flow for attachments or links to filenames matching *_rmm_v2.5.0.67_oid* or subjects themed as meeting invites, e-cards, RSVP, DHL/package delivery, job offers, or government-benefit statements, especially where the link resolves to Amazon S3, Cloudflare R2, Dropbox, GitLab, or Supabase.
  • If Defender for Office 365 is in use, pull Threat Explorer for delivered messages whose payload hash matches the published installer SHA256/SHA1.

Windows Event Log (Sysmon / native)

  • Sysmon Event ID 1 (process create): filter OriginalFileName or Image for the deceptive filename pattern and for RMM.Agent.exe spawning powershell.exe.
  • Windows Application log, source "MSP360 RMM Agent installer": Microsoft notes the installer emits eventcreate.exe entries "Begin installation" / "End installation. MSP360 de Success.": hunt for these strings where no corresponding IT change ticket exists.
  • Sysmon Event ID 13 (registry value set): hunt for autorun/Run-key writes referencing MSP360 UI components outside a known deployment window.
  • Windows Firewall operational log / netsh advfirewall firewall show rule: enumerate inbound allow rules naming RMM.Agent.exe on UDP/48678 fleet-wide; this is the authoritative source of truth the CQL Q6 proxy cannot fully replace.
  • Authenticode / Get-AuthenticodeSignature: spot-check any MSP360 installer found in the environment against the known-revoked certificate serial; Falcon does not expose a certificate-serial field natively (see Section 8 callout).

Software inventory / asset management

  • Cross-reference your RMM/CMDB asset inventory against any host where this pack's CQL fires: a host running MSP360 or ScreenConnect without an inventory record is a strong indicator of unauthorized installation.

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first — every "Open in Falcon" button below uses this selection.

Falcon has no native "firewall rule added" event (FirewallMatchEvent does not exist in the sensor's data model); Q6 below is a process-command-line proxy for that behavior, not a direct read of firewall state: corroborate with the native hunt in Section 7.

Q1 · Masqueraded MSP360 installer execution (deceptive filename pattern)
CONF HIGHFP LOWCOST LOW

Looks for: Execution of any binary whose filename carries the campaign's distinctive _rmm_v2.5.0.67_oid suffix, regardless of the lure prefix (ecard, Zoom, PDF, SSA.GOV, etc.).

// HUNT: Masqueraded MSP360 installer execution (deceptive filename pattern)
// MITRE: T1204, T1036, T1036.005
// CONF: high  FP: low  COST: low
// REQUIRES: ProcessRollup2 / SyntheticProcessRollup2
// FALSE POSITIVES: none expected; this exact string is attacker-specific and not used by legitimate MSP360 distribution packaging.
// LOOKBACK: set with the Falcon time picker (recommended 7d)
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| FileName=/_rmm_v2\.5\.0\.67_oid/i
| table([@timestamp, aid, ComputerName, UserName, FileName, ParentBaseFileName, SHA256HashData, CommandLine])
| sort(@timestamp, order=desc)

Q3 · RMM.Agent.exe spawns PowerShell to stage and silently install ScreenConnect
CONF HIGHFP MEDIUMCOST LOW

Looks for: The two-stage pivot Microsoft documented: the newly installed MSP360 service (RMM.Agent.exe) launching PowerShell, and that PowerShell session (or the RMM-launched process tree) subsequently running msiexec.exe /qn against a ClientSetup.msi package staged under a Temp path.

FP: legitimate MSPs do sometimes drive ad-hoc PowerShell through an RMM console for routine administration.

// HUNT: RMM.Agent.exe spawns PowerShell to stage and silently install ScreenConnect
// MITRE: T1059.001, T1218.007, T1105
// CONF: high  FP: medium  COST: low
// REQUIRES: ProcessRollup2 / SyntheticProcessRollup2
// FALSE POSITIVES: legitimate MSPs do sometimes drive ad-hoc PowerShell through an RMM console for routine administration.
// TUNING: exclude hosts with an approved change-management ticket authorizing remote PowerShell via your RMM; treat a hit here as high-confidence only when it also appears in Q1 (deceptive installer) or Q5 (dual-RMM correlation).
// LOOKBACK: set with the Falcon time picker (recommended 7d)
#event_simpleName=/ProcessRollup2|SyntheticProcessRollup2/
| (ParentBaseFileName=/^RMM\.Agent\.exe$/i FileName=/^powershell\.exe$/i)
  or (ParentBaseFileName=/^powershell\.exe$/i FileName=/^msiexec\.exe$/i CommandLine=*ClientSetup.msi*)
| table([@timestamp, aid, ComputerName, UserName, ParentBaseFileName, FileName, CommandLine, SHA256HashData])
| sort(@timestamp, order=desc)

Q5 · Dual-RMM correlation: MSP360 and ScreenConnect installed on the same host within a short window
CONF HIGHFP MEDIUMCOST MEDIUM

Looks for: The single highest-fidelity signal in this hunt, per Microsoft, TheHackerNews and GBHackers: both MSP360/RMM Agent and ConnectWise ScreenConnect appearing in the software inventory of the same endpoint. selfJoinFilter correlates the two installs by agent ID; review the collected timestamps in the output to confirm proximity (campaign activity observed both installs within hours, not weeks).

FP: organizations mid-migration between RMM vendors, or MSPs that legitimately run both tools fleet-wide, will also trigger this.

// HUNT: Dual-RMM correlation: MSP360 and ScreenConnect installed on the same host within a short window
// MITRE: T1219, T1543.003
// CONF: high  FP: medium  COST: medium
// REQUIRES: InstalledApplication
// FALSE POSITIVES: organizations mid-migration between RMM vendors, or MSPs that legitimately run both tools fleet-wide, will also trigger this.
// TUNING: exclude hosts on a documented RMM-migration change ticket; narrow to pairs whose collected timestamps fall within 24-48 hours of each other; prioritize hits that also match Q1 or Q6.
// LOOKBACK: set with the Falcon time picker (recommended 7d)
#event_simpleName=InstalledApplication
| selfJoinFilter(field=[aid], where=[
    {ApplicationName=/MSP360|RMM Agent/i},
    {ApplicationName=/ScreenConnect/i}
])
| groupBy([aid, ComputerName], function=[collect(ApplicationName), collect(@timestamp)], limit=5000)
| table([aid, ComputerName, ApplicationName, @timestamp])

Hardening: Tiered & Deployable

Immediate (deploy this week)
  • Enable Microsoft Defender cloud-delivered protection (M1049: Antivirus/AV). Microsoft's own recommendation for this campaign; no compatibility risk, no user-visible change. CIS Microsoft Windows Benchmark § "Configure Microsoft Defender Antivirus" aligns with this control.
  • Enable the ASR rule "Block process creations originating from PsExec and WMI commands" (M1038: Execution Prevention), GUID d1e49aac-8f56-4280-b9ba-993a6d77406c. Microsoft flags possible server compatibility issues; pilot on servers, deploy broadly elsewhere immediately.
  • Block the published installer hash and revoked signing certificate via Microsoft Defender for Endpoint's "block certificate" / indicator action (M1038). This blocks only the specific malicious build, not legitimate MSP360 deployments signed with a valid, non-revoked certificate.
  • Enforce MFA on every approved RMM platform's admin console (M1032: Multi-factor Authentication). Microsoft's own recommendation; closes the credential-reset gap if an RMM install is later found to be unauthorized.
Near term (1-4 weeks)
  • Deploy AppLocker or Windows Defender Application Control (WDAC) publisher-deny rules for unapproved RMM software (M1038). AppLocker's publisher-rule condition can block non-approved RMM installers by certificate without naming every possible filename. Pilot on a ring before fleet-wide enforcement; CIS Windows Benchmark § "Application Control" is the governing baseline.
  • PowerShell Constrained Language Mode + enhanced script-block logging (M1042 : Disable or Remove Feature or Program) on endpoints where an RMM agent should never need unrestricted PowerShell. CIS Benchmark § 18.9.95 (PowerShell logging) and § 2.3.* (User Rights) are the reference controls.
  • DNS/network egress filtering for the 7 published C2 domains (M1031: Network Intrusion Prevention). Single-sourced indicators, so stand them up as a monitored/alerting rule before converting to a hard network block.
Strategic (1-3 months)
  • Formal RMM governance program: a documented allowlist of approved RMM tools and vendors, procurement/change-management review before any new remote-access tool is deployed, and periodic reconciliation of the software inventory against that allowlist (M1018: User Account Management; M1047: Audit).
  • Fleet-wide WDAC enforcement (not just publisher-deny) moving from audit to enforced mode, informed by the near-term pilot (M1038).
  • Network segmentation limiting RMM agent outbound traffic to only the vendor's documented management endpoints, reducing the blast radius if an RMM agent is ever compromised or unauthorized (M1030: Network Segmentation).
