Executive Summary

Microsoft Threat Intelligence disclosed NeedyMantis on 2026-09-28: a modular, post-compromise Windows malware family used to maintain long-term access after a network is already breached. Microsoft found it while pivoting from indicators tied to Kaspersky's DAEMON Tools supply-chain investigation, though Microsoft has not observed NeedyMantis itself being distributed through a supply-chain compromise; it is deployed only after an actor already has a foothold. Activity traces back to at least October 2025 and has hit a small, selectively chosen set of victims: telecommunications firms, universities, medical nonprofits, intergovernmental organizations, and government contractors. Microsoft attributes observed use to threat actors operating from China and has designated the primary operator Storm-3069, without attributing it to a specific nation-state; it has not ruled out that more than one operator has access to the malware. Other public reporting has linked related activity to Google Threat Intelligence's UNC6863 cluster.

NeedyMantis ships as a three-part bundle: a legitimate signed program (Poedit, curl, Vim, and TightVNC are documented; Microsoft has also observed masquerades of Microsoft Office, Broadcom, Intel, and NVIDIA components), a malicious DLL with a legitimate-sounding name that the program sideloads on launch, and a custom encrypted file archive. The sideloaded DLL extracts a second-stage loader (in the analyzed sample, a file literally named encryptbase64.ps1 that, despite its extension, contains x64 shellcode rather than a PowerShell script) which decodes and loads the main component. That component creates a mutex named <username>-<processname>, then beacons over HTTPS before upgrading the connection to a WebSocket carrying an RC4-encrypted binary protocol to corp.tripswithengine.com on port 443 (URI /library/zip/), using a hard-coded firefox/21.0 user agent. From there it can load and unload additional operator-supplied modules; the capabilities of those modules remain unconfirmed by Microsoft.

In one observed incident, an operator used the Impacket toolkit for hands-on-keyboard activity: copying the legitimate program, malicious DLL, and archive from a network share and executing them on a target host. This illustrates one path by which NeedyMantis reaches a device once an actor already has access, not the initial-access method itself. An older variant Microsoft analyzed (October 2025, built around a libcurl-named archive) carried a persistence module named is that installs a Windows service instead of relying purely on the loader chain. Microsoft Defender flags the malware as TrojanDropper:Win64/NeedyMantis and Behavior:Win64/NeedyMantis, and flags the observed Impacket activity separately as HackTool:Win32/Impacket.

Defender priority: every atomic indicator in this pack traces to a single primary source, the Microsoft Security blog post (2026-09-28). The Hacker News and CyberKendra coverage saved alongside it are syndicated summaries of that same Microsoft report, not independent research, so this pack does not count them as a second independent source. Per this pack's evidentiary bar, §10's Falcon IOC CSV ships at action=detect only; nothing here is promoted to a blocking or prevent posture. Lean on the behavioral queries in §8, which target the documented DLL sideload mechanics rather than infrastructure alone.

Native Audit-Log Hunts

Checks that do not depend on Falcon CQL. Use where Sysmon, Windows auditing, a proxy/SWG, or Microsoft Defender is the only telemetry available, or to cross-validate a Falcon hit.

Sysmon

  • Event ID 7 (Image Loaded): ImageLoaded ends in one of WinSparkle.dll, libcurl.dll, vim64.dll, dbghelp.dll, jli.dll, nvml.dll, AND the loading path matches one of the nine documented combos, or more broadly any ProgramData/ProgramFiles subfolder outside System32/SysWOW64. This is the only telemetry, native or Falcon, that observes the actual DLL load event itself rather than the file write that preceded it.
  • Event ID 1 (Process Create): CommandLine contains encryptbase64; or Image path matches one of the nine documented folders; or ParentImage ends in services.exe and CommandLine matches the cmd.exe /Q /c pattern.
  • Event ID 3 (Network Connect): DestinationHostname = corp.tripswithengine.com, or the IP that name currently resolves to.
  • Event ID 22 (DNS Query): QueryName = corp.tripswithengine.com.
  • Event ID 13 (Registry) or Event ID 6 (Driver Loaded): not expected to fire for this threat; NeedyMantis's persistence is service-based (older variant) or loader-chain-based, not registry ASEP.

Windows Security auditing

  • Event ID 4688 (process creation, with command-line auditing enabled via Include command line in process creation events GPO) as a fallback for the Sysmon process rules above on hosts without Sysmon.
  • Event ID 7045 (a new service was installed) and Event ID 4697 (a service was installed in the system) for the older-variant persistence module, cross-referenced against the nine documented folder names in the service's ImagePath.
  • Zone.Identifier alternate data stream on the legitimate installer package, if it arrived by download or email ahead of the operator staging NeedyMantis into it. This corroborates a delivery vector for the carrier software even though NeedyMantis itself is a post-compromise tool, not the initial-access payload.

Proxy / SWG

  • Alert on outbound HTTPS/WebSocket sessions carrying User-Agent firefox/21.0 together with a URI path of /library/zip/, especially from a server or infrastructure host that has no legitimate reason to present a browser-identifying user agent.
  • Alert on, or retroactively hunt for, connections to corp.tripswithengine.com in proxy and DNS logs.

Microsoft Defender / MDE portal (if licensed)

  • Search directly for the three Defender detection names: TrojanDropper:Win64/NeedyMantis, Behavior:Win64/NeedyMantis, HackTool:Win32/Impacket.
  • Run Microsoft's own published hunting queries from the primary source: a DeviceFileEvents/DeviceProcessEvents query for the nine documented DLL paths, and a search in (DeviceNetworkEvents, EmailUrlInfo, UrlClickEvents, DeviceEvents, DeviceFileEvents, DeviceProcessEvents) query for corp.tripswithengine.com.

Deployable Playbooks

Prerequisites (all steps): local admin/GPO management rights on target endpoints; Microsoft Defender Antivirus present and not in passive mode for the Defender-specific steps; a pilot ring defined before any fleet-wide rollout. Estimated deploy time: 1 to 2 hours for Steps 1 to 3 across a pilot ring; Steps 4 and 5 depend on your network/SIEM vendor's change process.

Step 1 – Enable Microsoft's published Attack Surface Reduction rules

What it does: Blocks low-prevalence/untrusted executable launches and obfuscated-script execution, both cited by Microsoft as mitigations for this threat. Why it works: the sideloaded first-stage DLL and its host binary are both low-prevalence in most fleets, and the second-stage loader's shellcode-in-a-script pattern trips the obfuscated-script rule.

Prerequisites: Microsoft Defender Antivirus active (passive mode acceptable if a third-party AV is primary, per Microsoft's ASR compatibility notes); pilot in Audit mode for 1 to 2 weeks if these rules are not already deployed. Reboot required: No.

PowerShell:
$ids = @(
  '01443614-cd74-433a-b99e-2ecdc07bfc25',  # Block executable files from running unless they meet a prevalence, age, or trusted list criterion
  '5beb7efe-fd9a-4556-801d-275e5ffc04cc'   # Block execution of potentially obfuscated scripts
)
Set-MpPreference -AttackSurfaceReductionRules_Ids $ids -AttackSurfaceReductionRules_Actions Enabled,Enabled
Write-Output "ASR rules set to Block"

GPO path:
Computer Configuration > Administrative Templates > Windows Components > Microsoft Defender Antivirus >
Microsoft Defender Exploit Guard > Attack Surface Reduction > Configure Attack Surface Reduction rules
(add each GUID above with value 1 = Block; use 2 = Audit for the pilot ring)

Verify:
$i = (Get-MpPreference).AttackSurfaceReductionRules_Ids
$a = (Get-MpPreference).AttackSurfaceReductionRules_Actions
for ($n=0; $n -lt $i.Count; $n++) { "$($i[$n]) => $($a[$n])" }
# Expect: 1 (Block) for each of the two GUIDs above

Monitor for false positives:
Event ID 1121 (Block) / 1122 (Audit) in Microsoft-Windows-Windows Defender/Operational.
If a legitimate internal tool trips it, add a targeted exclusion:
Add-MpPreference -AttackSurfaceReductionOnlyExclusions 'C:\Path\To\LegitimateTool.exe'

Rollback:
Set-MpPreference -AttackSurfaceReductionRules_Ids $ids -AttackSurfaceReductionRules_Actions Disabled,Disabled

Step 2 – Enable cloud-delivered protection, EDR block mode, and network protection

What it does: Turns on the three remaining Microsoft-recommended baseline controls: rapid cloud lookup of new/unknown variants, EDR-driven remediation of malicious artifacts even when a non-Microsoft AV is primary, and network-layer blocking of known-malicious connections. Why it works: covers the case where a NeedyMantis variant's specific hash or path is not yet in a static signature.

Prerequisites: Microsoft Defender Antivirus/Defender for Endpoint licensed and installed. Reboot required: No.

PowerShell:
Set-MpPreference -MAPSReporting Advanced
Set-MpPreference -SubmitSamplesConsent SendAllSamples
Set-MpPreference -DisableBlockAtFirstSeen $false
Set-MpPreference -EnableNetworkProtection Enabled

# EDR in block mode is a Microsoft Defender for Endpoint tenant setting:
# Settings > Endpoints > Advanced features > "Enable EDR in block mode" = On
Write-Output "Cloud protection, block-at-first-sight, and network protection enabled"

Verify:
Get-MpPreference | Select-Object MAPSReporting, DisableBlockAtFirstSeen, EnableNetworkProtection
# Expect: MAPSReporting=2 (Advanced), DisableBlockAtFirstSeen=False, EnableNetworkProtection=1 (Enabled)

Rollback:
Set-MpPreference -MAPSReporting Basic
Set-MpPreference -DisableBlockAtFirstSeen $true
Set-MpPreference -EnableNetworkProtection Disabled

Step 3 – Block C2 egress at DNS/firewall

What it does: Stops resolution of, or connectivity to, corp.tripswithengine.com, Microsoft's own first-listed mitigation. Why it works: removes the C2 channel even if the loader chain runs successfully on a host.

Prerequisites: DNS Response Policy Zone (RPZ) support on your internal resolver, or equivalent firewall/SWG policy-authoring rights. Reboot required: No.

Windows DNS Server (RPZ) PowerShell:
Add-DnsServerQueryResolutionPolicy -Name "Block-NeedyMantis-C2" `
  -Action IGNORE `
  -FQDN "EQ,corp.tripswithengine.com"

Generic firewall/SWG rule (illustrative; adapt to your platform):
Deny outbound TCP/443 where destination FQDN/SNI = corp.tripswithengine.com

Verify:
Resolve-DnsName corp.tripswithengine.com -ErrorAction SilentlyContinue
# Expect: resolution failure or a sinkhole address from an internal, non-production test host

Rollback:
Remove-DnsServerQueryResolutionPolicy -Name "Block-NeedyMantis-C2"
# or remove the equivalent firewall/SWG rule

Step 4 – AppLocker/WDAC deny rule for the nine documented sideload paths

What it does: Denies DLL loads from the nine Microsoft-published folder/basename combinations. Why it works: breaks the chain at the exact point where the malicious DLL would otherwise be sideloaded by its legitimate host binary.

Prerequisites: AppLocker (or WDAC) available (Windows 10/11 Enterprise or Education for full policy flexibility); confirm no legitimate Intel/Broadcom/Office-adjacent tooling in your fleet installs into these exact folder names before enforcing. Reboot required: No (AppLocker policy refresh via gpupdate is sufficient); the Application Identity service must be running.

PowerShell (create + test in Audit mode first):
New-AppLockerPolicy -RuleType Publisher,Path -User Everyone -RuleNamePrefix "DenyNeedyMantisSideload" `
  -XmlPolicy | Set-AppLockerPolicy -Merge

# Minimal deny-path rules (adapt via the AppLocker MMC snap-in for a maintained policy):
# Deny DLL execution matching each of:
#   %ProgramFiles%\Poedit\WinSparkle.dll        %ProgramData%\USOShared\libcurl.dll
#   %ProgramData%\VIM\vim64.dll                  %ProgramData%\TightVNC\VIM\vim64.dll
#   %ProgramData%\office\dbghelp.dll             %ProgramData%\broadcom\dbghelp.dll
#   %ProgramData%\Intel\jli.dll                  %ProgramFiles%\modifiable\nvml.dll

Verify (Audit mode first):
Get-AppLockerPolicy -Effective | Select-Object -ExpandProperty RuleCollections
Get-WinEvent -LogName "Microsoft-Windows-AppLocker/EXE and DLL" -MaxEvents 20

Rollback:
Set-AppLockerPolicy -XmlPolicy "C:\Path\To\PreviousPolicy.xml"
# or remove the rule collection: Remove-AppLockerPolicy (if fully rolling back AppLocker)

Step 5 – Enable Sysmon Event ID 7 (Image Loaded) on servers and critical hosts

What it does: Logs every DLL/image load, closing the one visibility gap this pack cannot cover natively: Falcon's own event model does not expose a generic DLL-load event, so the actual sideload moment is only visible through Sysmon. Why it works: gives SIEM/SOAR a second, independent detection path for the exact technique this campaign relies on.

Prerequisites: Sysmon installed (via Microsoft Sysinternals); a maintained config that enables Event ID 7 with appropriate DLL-path/hash filtering to control log volume (unfiltered Event ID 7 is extremely high-volume). Reboot required: No.

Sysmon config snippet (merge into your existing sysmonconfig.xml):
<ImageLoad onmatch="include">
  <ImageLoaded condition="end with">WinSparkle.dll</ImageLoaded>
  <ImageLoaded condition="end with">libcurl.dll</ImageLoaded>
  <ImageLoaded condition="end with">vim64.dll</ImageLoaded>
  <ImageLoaded condition="end with">dbghelp.dll</ImageLoaded>
  <ImageLoaded condition="end with">jli.dll</ImageLoaded>
  <ImageLoaded condition="end with">nvml.dll</ImageLoaded>
</ImageLoad>

Deploy:
sysmon64.exe -c updated-sysmonconfig.xml

Verify:
Get-WinEvent -LogName "Microsoft-Windows-Sysmon/Operational" -FilterXPath "*[System[EventID=7]]" -MaxEvents 5
sysmon64.exe -c
# Confirm the ImageLoad rule block above is present in the active config dump

Rollback:
sysmon64.exe -c previous-sysmonconfig.xml
# or remove the ImageLoad block and redeploy the prior config
