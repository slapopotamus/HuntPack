01

Executive Summary

Attacker objective. Steal developer and operator secrets. On 2026-10-19 someone using a legitimate OVHcloud contributor's GitHub account swapped the prebuilt archives on five existing releases of the OVHcloud CLI (v0.11.0 to v0.15.0) with a build that reads credentials and files from disk. [#1] [#2] [#4]

How it worked. The uploads came through the ordinary GitHub Releases API. No tag was pushed, no workflow ran, and the source and build pipeline were untouched. OVHcloud's own root cause is that release immutability was not enabled, so a user with write permission could overwrite assets on published releases. [#1] [#3] [#5] The bad files covered macOS (Intel and ARM), Linux (x86_64 and arm64) and Windows x86_64, and were live for about 94 minutes (14:47 to 16:21 Paris time, 12:47 to 14:21 UTC) before OVHcloud deleted them after a customer's pinned-hash CI check failed. [#1] [#2] [#3]

What the binary does. It is the real CLI recompiled with extra Go code. Per OVHcloud it collects IDE and AI-assistant databases, cloud, container and Terraform credentials, SSH keys, .netrc and git config into a folder named envchecker-NNNNNNNNN in the temp directory, archives it, and uploads it to a hard-coded address, using Solana RPC calls through one of five public endpoints. [#1] The advisory reports about 250 downloads. [#1]

Attribution is open. One analysis ties the hijacked account to the GlassWorm campaign through an earlier loader in the account's personal repositories and calls the link an inference. Another report says nothing from the October binary has been tied to GlassWorm because no copy was preserved, and the binary's Solana wallet in the advisory differs from the wallet in that earlier loader. [#3] [#4] [#1] This pack does not assert the attribution and ships none of that campaign's indicators.

Defender priority: find every host or CI runner that downloaded or ran an ovhcloud binary on 2026-10-19 between 12:47 and 14:21 UTC (Q7, Q8, Q1). For any hit, treat every secret readable on that machine as stolen and rotate it from a different machine. Then require immutable releases and pinned hashes for every tool you pull from GitHub Releases.

Decisions

  • Hash roles corrected. The brief that started this pack described 5c2beb56…aeb80e0 as a partial malicious hash. Source 2 gives it in full and labels it the original (legitimate) v0.15.0 Linux arm64 archive. The swapped (malicious) archive is the 3833daff value. The legitimate hash is kept out of the IOC import.
  • Related-cluster indicators excluded. The advisory root-cause section and the OpenSourceMalware report list a wallet, a loader file hash, a key and IV, an address and an extension from the account's earlier compromise. They belong to a different incident and are not shipped. The wallet in the advisory's own IOC list (the binary's wallet) is shipped as a hunt string.
  • Time zones. OVHcloud's 14:47 to 16:21 is Paris time (UTC+2), equal to 12:47 to 14:21 UTC. OpenSourceMalware says 94 minutes, the advisory says 1h33.
  • Version detail. The reporter's build info is from the Linux arm64 binary and the advisory's from a Linux x86_64 build. Both show the same pseudo-version and commit, so those two strings are the signal. The +dirty flag is not, because the clean v0.16.0 build also reports it [#4].

Hunt Brief & Attack Chain

Seven hypotheses, ordered by fidelity.

  1. H1 (high): a host executed one of the five replaced binaries. Event: process start with MD5/SHA-256 (Q1, Q7). T1195.002. FP: none.
  2. H2 (high): a host connected to the advisory's upload address (Q2). T1041. FP: none, but the address may be changed by the operator.
  3. H3 (high): an ovhcloud process resolved a Solana RPC hostname (Q3, Q4). T1102. FP: blockchain tooling for Q4.
  4. H4 (medium): ovhcloud spawned shells, archivers or credential-store CLIs (Q5). T1119, T1552.001. FP: helper launches.
  5. H5 (medium): the CLI was fetched during 12:47 to 14:21 UTC on 2026-10-19 (Q8). T1195.002. FP: normal installs outside the window.
  6. H6 (low): a command line names an envchecker temp folder (Q6). T1119. Rarely visible, use N1.
  7. H7 (low): ovhcloud reached an unexpected public address (Q9). T1041. FP: OVHcloud API addresses.

Native Audit-Log Hunts

These checks need no Falcon query.

N1 · Endpoint triage: stealer working folder

Where: Developer workstation or runner

# macOS / Linux (read-only)
ls -ld "${TMPDIR:-/tmp}"/envchecker-* 2>/dev/null
# Windows PowerShell (read-only)
Get-ChildItem -Path $env:TEMP -Directory -Filter "envchecker-*" -ErrorAction SilentlyContinue

The advisory says the folder is created on every run and never deleted. A match means the swapped binary ran on this machine. Absence is not proof: the tool may have run before the folder was cleaned.

N2 · CI and build logs: release downloads in the window

Where: CI system, container build logs, package mirror logs

# Search for the window 2026-10-19 12:47 to 14:21 UTC (14:47 to 16:21 Paris)
# Strings: ovhcloud-cli, releases/download, install.sh, ovhcloud-cli_Linux_x86_64.tar.gz
# Any job that fetched an archive without a pinned hash in that window is exposed

Pinned-hash jobs failed and are safe. Unpinned jobs, Dockerfiles and the CLI's own upgrade command pulled the swapped file.

N3 · Proxy, firewall and resolver logs

Where: Egress logging

# Destination 45.32.148.174 port 443 (path /upload)
# DNS or SNI: solana.drpc.org, solana-rpc.publicnode.com, solana.api.pocket.network,
#             api.mainnet-beta.solana.com, solana.api.onfinality.io
# Hits from build hosts with no blockchain role are suspicious

Covers hosts and runners with no sensor.

N4 · GitHub organisation audit log

Where: GitHub org settings, audit log

# Review release asset delete and upload events on every repo, by user
# Flag assets changed on releases older than 24 hours
# List members with Write on release-publishing repos; check for personal accounts
# Confirm immutable releases is enabled org-wide

This is how the swap could be spotted at the source. Event names vary by plan; check your own audit log schema.

N5 · Check a binary without running it

Where: Any host that kept a copy

go version -m ./ovhcloud
# Malicious: mod ... v0.15.1-0.20261013083505-5ead8ef9b43d+dirty and vcs.revision=5ead8ef9b43d354dfb5caadff803b11afc8c5c58
# Do NOT treat vcs.modified=true alone as malicious: the clean v0.16.0 build also reports it
md5sum ./ovhcloud        # compare with the five MD5 values in Section 10
shasum -a 256 ovhcloud-cli_*.tar.gz

Never run the binary to check it.

Hardening: Tiered & Deployable

Immediate (this week)
  • T1. Turn on immutable releases for every repository that publishes binaries, at the organisation level. A release created after the setting is on cannot have assets changed or removed. OVHcloud's own fix. Existing releases are not protected retroactively, so re-publish critical old releases. Framework: ATT&CK T1195.002 and M1051; GitHub immutable-releases documentation (GA since Oct 2025 per [#4]). Verify: Playbook P1.
  • T2. Remove personal accounts and excess Write access from release-publishing repositories. The uploader here was a contributor who was not a public org member. Publish only through a service account or workflow identity with short-lived credentials. Framework: M1018, M1026; T1078. Verify: N4.
  • T3. Pin and verify the hash of every release asset you download in CI, Dockerfiles and install scripts. The single pinned-hash job here failed and exposed the swap. Pin against a source other than the same release page (checksums.txt was swapped too). Framework: ATT&CK T1195.002 and M1051; ⚠ best-practice, no formal benchmark. Verify: Playbook P2.
  • T4. Rotate every secret readable on any host that ran a swapped build, from a different machine. Framework: M1027 Password Policies, M1026; T1552.001. Verify: Playbook P5.
Near term (1 to 4 weeks)
  • T5. Block or alert on Solana RPC lookups from build runners and servers with no blockchain role. Public services, so block by role, never globally. Framework: M1037 Filter Network Traffic; T1102. Verify: Q4 and Playbook P4.
  • T6. Require signature or attestation verification before installing release binaries. OVHcloud v0.16.0 ships a release attestation; check it with the GitHub CLI. Framework: ⚠ best-practice, no formal benchmark; vendor guidance [#3] [#4]. Verify: Playbook P2.
  • T7. Stop piping install scripts to a shell on developer machines. Download, hash-check, then run. Framework: M1017 User Training; ⚠ best-practice.
Strategic (1 to 3 months)
  • T8. Keep developer credentials short-lived and out of well-known files. Use SSO-backed cloud sessions, hardware-backed SSH keys and a secret manager, so a file-scraping stealer finds nothing durable. Framework: M1041 Encrypt Sensitive Information, M1022 Restrict File and Directory Permissions; T1552.
  • T9. Sign commits and tags, use CODEOWNERS on release workflows, and link release rights to central identity management. OVHcloud lists these as its own next steps [#1]. Framework: M1032 Multi-factor Authentication; T1078.
  • T10. Control IDE extensions on developer machines. The advisory attributes the original account takeover to a malicious editor extension [#1]. Allowlist extensions. ⚠ best-practice, no formal benchmark.

P2 · Hash-pin and verify a release asset in CI (POSIX shell)

#!/bin/sh
set -eu
VERSION="v0.16.0"
ASSET="ovhcloud-cli_Linux_x86_64.tar.gz"
# EXPECTED_SHA256 comes from your own reviewed config, not from the same release page
EXPECTED_SHA256="${OVH_CLI_SHA256:?set the pinned hash}"
curl -fsSL -o "$ASSET" "https://github.com/ovh/ovhcloud-cli/releases/download/${VERSION}/${ASSET}"
echo "${EXPECTED_SHA256}  ${ASSET}" | sha256sum -c -
gh attestation verify "$ASSET" --repo ovh/ovhcloud-cli
tar -xzf "$ASSET"
Prerequisites: curl, sha256sum (shasum -a 256 on macOS), GitHub CLI authenticated; the hash pinned after you verified it once.
Reboot required: no
Rollback: remove the step from the pipeline; nothing on the host changes.
