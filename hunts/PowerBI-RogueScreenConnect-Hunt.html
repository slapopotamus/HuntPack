Executive Summary

Attacker objective: persistent, interactive remote control of a victim's Windows machine, obtained by getting the user to install a legitimate remote-management product that is configured to call back to the attacker. Per Huntress, the campaign began on 2026-09-10 and abuses Microsoft Power BI. A phishing email links to a dashboard that the attacker built on the real app.powerbi.com domain. The dashboard shows a blurred form and a "Download Reference" button.

Because the first link is on a Microsoft domain, the reporting says it slips past Microsoft 365 mail filters and gateways that trust it. The button sends the victim to an attacker-controlled staging site that checks the browser before it allows a download. The reported checks cover browser version, operating system, device characteristics, automation indicators, screen size, iframe context and cloud-provider cookies. Failed checks redirect to a decoy page. The page also embeds a hardcoded Telegram Bot credential and reports victim IP address, geolocation and browser details to it. A visitor who passes the checks receives a ScreenConnect installer instead of a reference document.

The attacker then builds redundancy. The first client connects to a relay on the ScreenConnect vendor cloud. A command file runs PowerShell from a temporary directory, which fetches a second installer from separate attacker infrastructure and removes the first client. A tool named HideUL_x64.exe hides the activity from the user and from security software, and a scheduled task named SCAutoRepairEvery2Min keeps a script running every two minutes. Huntress's point is that removing only the first visible instance can leave another foothold intact.

Attribution: Huntress named no actor and neither does this pack. No source retrieved ties the campaign to a known group.

Highest-value defensive angle: hunt the endpoint, not the email. The Power BI link and the browser fingerprinting are invisible to endpoint telemetry. What the host does see is durable: a ScreenConnect client carrying an instance ID you did not provision (Q1), more than one instance on the same host (Q2), a scheduled task that repeats every two minutes (Q7), and a client talking to a relay outside screenconnect.com (Q9).

Defender priority: a ScreenConnect client is a full remote-control channel, so a hit is a hands-on-keyboard incident, not adware. Check every host for all ScreenConnect instances, not only the one you found, because the campaign deliberately leaves a second client behind. Do not block the vendor's binaries or the whole screenconnect.com domain on the strength of this pack: the hashes and installer names here belong to a legitimate product and ship detect-only.

  • The press articles relay Huntress. The pack still limits blocking to indicators that appear in the vendor primary and at least one corroborating snapshot.
  • The decoy host is press-only. The retrieved Huntress text does not list it. It appears in three press snapshots, so it ships as detect and not prevent.
  • What the scheduled task runs is stated two ways. The Huntress text says the task executes SCAutoFix.ps1. GBHackers calls it a concealment script. The pack matches the task and script names without asserting the script's content.
  • Launcher name. LyN03DvVjUKPrun.cmd looks like a randomised prefix plus a fixed suffix. The pack matches the reported value and tells analysts to pivot on SCAutoFix.ps1 if it does not match.
  • Not carried forward. The task brief mentioned filtering for business ISPs and a delayed script-triggered download. No retrieved snapshot contains either statement, so the pack makes neither claim. The snapshots say the download is automatic and that the fingerprint covers the attributes listed in the summary.

CONF HIGHFP LOWCOST LOW

Looks for: any process whose image path or command line carries one of the two ScreenConnect client instance IDs named in the reporting. A ScreenConnect client embeds its instance ID in the install folder and service name, so a hit means the attacker's client is or was running on the host. The first ID belongs to the client that was later removed, so a historical hit with no live process still proves exposure.

Q2 · Host Running More Than One ScreenConnect Instance Over the Window
CONF HIGHFP MEDCOST MED

Looks for: hosts where ScreenConnect client processes ran under two or more different instance IDs across the search window. The campaign installs a second client on separate infrastructure and then uninstalls the first, so the two instances may never overlap in time. Counting distinct IDs over the window catches the swap that a point-in-time inventory misses. Reporting states that investigating endpoints with multiple RMM clients is the recommended triage. FP: an MSP or helpdesk that migrates between its own ScreenConnect instances will also hit. Exclude hosts whose instance IDs are all in your approved list.

Validation: schema-aligned, static-reviewedAutomated: static-passedEquivalence: approximate-analytic, equivalent-with-schema-assumptionsProfiles: microsoft-defender-xdr, sentinelone-endpoint-ocsf
Known limitations and deployment notes
  • PowerQuery: The instance ID is not extracted, so the output lists distinct paths rather than IDs.
  • PowerQuery: Hosts that only ever ran the user-session client binary (windowsclient.exe) are not counted.
  • PowerQuery assumes: Each ScreenConnect instance installs into its own folder named ScreenConnect Client followed by the 16-character instance ID in parentheses.
  • PowerQuery assumes: The service binary runs from the same folder as the rest of the instance, so one distinct path is one instance.
  • PowerQuery assumes: estimate_distinct is exact at this cardinality.
  • KQL – Defender XDR: An instance that never started a process the sensor observed is not counted.

Hardening: Tiered

Controls are ordered by leverage against this chain. The campaign needs three things: a user who can install software, an RMM client that is allowed to run and reach any relay, and no one watching which RMM instances exist. Each control removes one of them.

Immediate: deploy this week

I1 · Stop standard users from installing remote-access software

The chain ends in a user running an installer. Without local admin rights, the installer cannot register the client service. Where users must install software, route it through an approval flow.
Authority: MITRE M1038 (Execution Prevention), M1026 (Privileged Account Management). CIS Controls v8 2.5 (Allowlist Authorized Software) and 5.4 (Restrict Administrator Privileges). Verify: a standard user cannot run a test MSI that installs a service. Risk: medium, may surface shadow IT.

I2 · Inventory every RMM and approve an instance allowlist

You cannot tell a rogue ScreenConnect client from yours without a list of your own instance IDs and relay hostnames. Run the read-only inventory (P1), build the list, then use it to tune Q1, Q2, Q3 and Q9.
Authority: MITRE M1047 (Audit), M1038. CIS Controls v8 2.1 (Establish Software Inventory). Verify: P1 output reconciled with the approved list. Risk: low.

I3 · Alert on external mail linking to Power BI view pages

Audit-mode transport rule (P3) plus the Defender for Office hunt N1 show who received the lure. Audit first, because legitimate external Power BI sharing exists.
Authority: MITRE M1017 (User Training), M1021 (Restrict Web-Based Content). Microsoft Exchange Online mail flow rule documentation. best-practice, no formal benchmark for this specific lure. Verify: test message from an external mailbox appears in the audit log. Risk: low in audit mode.

I4 · Turn on PowerShell script block and module logging

The second stage runs PowerShell from a temporary directory. Without logging, what it downloaded and removed is not recoverable.
Authority: MITRE M1047; CIS Microsoft Windows benchmark PowerShell logging guidance. Verify: Event 4104 appears after a test command. Risk: low, plan for log volume.

Near term: 1 to 4 weeks, pilot first

N1 · Restrict ScreenConnect to your own instance at the proxy and DNS layer

Permit only your approved instance hostnames, and alert on any other host under screenconnect.com. Do not block the whole vendor domain if you use it. Load the five prevent domains from section 10 into the same filter.
Authority: MITRE M1031 (Network Intrusion Prevention), M1021. best-practice, no formal benchmark for per-instance allowlisting. Verify: a lookup of a non-approved instance hostname is logged or refused. Risk: medium.

N2 · Attack surface reduction rules in audit, then block

Enable the rule that blocks executables that do not meet a prevalence, age or trusted-list test (it targets freshly downloaded installers) and the rule against obfuscated scripts, in audit mode for a week (P2). Confirm both GUIDs against Microsoft Learn before deployment.
Authority: MITRE M1040 (Behavior Prevention on Endpoint); Microsoft Defender ASR rules reference. audit first Risk: medium, the prevalence rule can flag internal tools.

N3 · Browser download controls for executables from uncategorised sites

Web content filtering for newly registered and uncategorised domains cuts off the staging step, since all four staging domains and the decoy are throwaway names.
Authority: MITRE M1021. Microsoft Defender for Endpoint web content filtering documentation. best-practice, no formal benchmark Risk: medium, expect help-desk tickets.

Strategic: 1 to 3 months

S1 · Application control that allows only your RMM

WDAC or AppLocker policy that permits remote-management tools signed for, or configured for, your instance only. Application control is the only control here that stops a freshly built rogue client with a new hash. Authority: MITRE M1038, M1045 (Code Signing). Deploy in audit mode first. Risk: high, needs ownership.

S2 · One approved remote-support platform with SSO and MFA

Reduce the number of tools users see as normal, so an unexpected ScreenConnect prompt is itself a signal. Authority: MITRE M1032 (Multi-factor Authentication), M1017. best-practice, no formal benchmark

S3 · User guidance aimed at this exact lure

No document needs a "Download Reference" button that installs software, and a shared dashboard from outside should not ask for a download. Put that in the next awareness cycle, and give users a one-click report button. Authority: MITRE M1017.

  • Instance ID extraction depends on folder naming. Q2 reads the ID from the image path. If your tenant stores the client elsewhere, Q2 returns nothing, so confirm in gate G1.
  • The hiding mechanism and the script content are not published. The pack matches names and never asserts what they do.
  • A decoy hit is not a compromise. A visitor who fails the fingerprint check is redirected and gets no installer, so a Q8 hit on the decoy host proves the lure reached a user, not that a host was compromised.

Validation: gates G1 to G6 in section 11 govern promotion. No query proceeds to alert before clearing G2, and none is recommended for Block.
