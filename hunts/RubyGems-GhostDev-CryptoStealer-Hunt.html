Executive Summary

On 2026-10-05 the RubyGems account reqthrottle_3474, whose profile calls itself "Ghost Dev", published 42 malicious gems in about one hour. Twenty-six carry crypto-themed or generic utility names and sixteen are typosquats of real gems such as bitcoin, keccak and solana-ruby. Every gem declares a native extension, and RubyGems runs that extension's extconf.rb during gem install or bundle install. The Ruby in lib/ is a decoy.

The loader checks that it is on a real developer workstation (no CI variables, no sandbox-like hostname, user or path, uptime over 30 minutes, and developer files such as .ssh or .gem/credentials present), decodes a Base64 payload, forks twice, detaches, sleeps 20 to 40 minutes and then runs it. Eleven gems (Template A) open a reverse /bin/sh to 45.138.12.177 on TCP 8089 or 8090. Thirty-one (Template B) download wgkit.tar.gz from the same host on TCP 8092 and run wg_install.sh. OpenSourceMalware analysed that kit: a local TLS-intercepting proxy, a clipboard hijacker and a wallet grabber that swap withdrawal addresses and send seed phrases, private keys and wallet files to a hard-coded collector.

Highest-value defensive angle. Hunt the install, not the payload. The 20 to 40 minute sleep and a double fork cut the process link between gem install and the shell (Q8 rebuilds it by host), and the campaign's own gating means a sandbox or CI scan of the gems shows nothing. Name-based hunting of the 42 gems (Q1, native hunt N1) and the one hard-coded address (Q5) are the two checks that do not depend on catching the payload in the act.

Defender priority. Treat any developer workstation that installed one of the 42 gems as compromised, as SafeDep advises: the shell runs with the installing user's rights. Rotate every credential that user could read, check wallets and exchange accounts from a clean device, and block 45.138.12.177 at the network edge.

What this pack does not claim. No actor or group name is attributed: the only designators in the sources are the account name and the profile label "Ghost Dev". On the sources' own code excerpt the payload reads /proc/uptime and treats a read failure as 0.0, so on macOS (no /proc/uptime) the uptime check should fail and the payload should not run. That is an inference from the quoted code, not a statement in the reports, so macOS hits are treated as exposure of the install, not proof of compromise. The tools in the chain (ruby, gem, bundle, sh, tar, curl) are stock software and nothing here blocks them.

The two detection challenges

Challenge 1: the sleep breaks the lineage. The shell or downloader runs 20 to 40 minutes after gem install returned, in a process that was forked twice, given its own session and re-parented once its parent exited. A rule that waits for gem to be the ancestor of sh will never fire. This pack therefore hunts the install by name (Q1, N1), the payload by what it does regardless of ancestry (Q3, Q5, Q6, Q7), and joins the two by host (Q8). A ps check for an orphaned extconf.rb process during the sleep window is in N2. Whether a forked child that never calls exec produces its own process event on the sensor is not documented in the sources; validate it on a lab host.

Challenge 2: a detonation lab shows nothing. The campaign checks for CI variables, sandbox-style hostnames and users, scratch install paths such as /tmp/, short uptime and missing developer files, so an automated scanner, a CI job or a fresh container records a clean install with no network traffic. A "clean" verdict from a sandbox, a registry scanner that detonates, or a CI dependency check is not evidence a gem is safe. Hunt by name and by endpoint behavior on real developer machines, and do not try to reproduce the payload against the live C2 to prove the detection.
