Executive Summary

Sucuri documented a WordPress backdoor family it codenamed SC (from the SC_ markers in its injected content): a self-healing mesh that spreads one payload across at least eight interdependent persistence points (files, the WordPress database, and System V shared memory) such that deleting any single component triggers another to rebuild it. The attacker's objective is durable, stealthy, full control of the site: a hidden, fully-privileged administrator; front-end JavaScript injection (skimming on checkout pages); arbitrary additional PHP deployment; and the ability to detect and remove competing security plugins. Command and control runs over roughly twenty public, legitimate Ethereum JSON-RPC gateways rather than a single attacker-owned domain, so no single network block stops it.

The highest-value defensive angle is not matching a hash or a domain: Sucuri published neither. It is (1) file-integrity monitoring on a small, fixed set of WordPress bootstrap paths that legitimate sites almost never touch at runtime (wp-content/db.php, wp-content/advanced-cache.php, wp-content/mu-plugins/*), (2) behavioral detection of the web-server worker process doing things it normally never does (spawning a shell, writing a ZIP, talking to MySQL directly), and (3) a host/database audit for the off-disk persistence (wp_options blob, SysV shared memory segment, cron hooks, database triggers) that no EDR agent can see into.

Defender priority: assume file cleanup alone will fail. Sucuri is explicit that the order of remediation matters: off-disk copies (database option row, shared-memory segment, cron hooks, triggers) must be cleared before or alongside the files, or the very next page load silently restores everything that was just deleted.

07

Native Audit-Log Hunts (non-CQL)

The off-disk persistence Sucuri describes (the database row, the shared-memory segment, cron hooks, and, in related variants, database triggers) is the part no EDR agent can see. These checks run on the host or against the WordPress/MySQL application layer directly, and they are what actually closes the reinfection loop.

WordPress / filesystem

ls -la wp-content/.*.php wp-content/*.php 2>/dev/null          # hidden dot-prefixed PHP in wp-content root
cat .user.ini php.ini 2>/dev/null | grep -i auto_prepend_file   # confirm the prepend target before touching it
grep -rl "SC_" wp-content/db.php wp-content/advanced-cache.php wp-content/themes/*/functions.php 2>/dev/null
find wp-content/uploads wp-content/themes -maxdepth 3 -iname '*.zip' -regex '.*/[0-9a-f]\{8,\}\.zip' 2>/dev/null

WordPress database

wp cron event list --fields=hook,next_run_relative            # look for randomized hook names beside a known fetch hook
wp option list --search="*" --format=csv | awk -F, 'length($2)>20000 {print}'   # oversized option blobs
wp user list --fields=ID,user_login,roles,user_registered      # cross-check against user_list_table ajax output for a hidden admin
wp db query "SELECT user_id, meta_key, LENGTH(meta_value) FROM wp_usermeta WHERE meta_key LIKE '%capabilities' ORDER BY LENGTH(meta_value) DESC LIMIT 20;"
wp db query "SELECT TRIGGER_NAME, EVENT_OBJECT_TABLE, ACTION_STATEMENT FROM information_schema.TRIGGERS;"  # audit for an admin-recreating trigger

Host-level shared memory

ipcs -m                     # list System V shared-memory segments; cross-reference fixed numeric keys across scans
ipcs -m -p                  # creator PID per segment -- correlate to the PHP-FPM/web worker pool
# A segment that persists across a full file + database cleanup and still decodes to readable PHP
# starting "<?php" is live malware, not a stale leftover; purge with ipcrm -m <id> only after confirming
# the drop-ins that would read it back (advanced-cache.php) are already removed.

Web-server / WAF access logs

egrep -i '\?[a-z]{1,4}=[0-9a-f]{6,}' /var/log/{httpd,nginx,apache2}/*access*.log | less
# Hunt for the magic beacon parameter: a short prefix followed by a fixed value, answered with a
# normal-looking response and no corresponding WordPress page render in the timing/size profile.
# No exact parameter name is published -- baseline your own site's legitimate query-string vocabulary
# first, then flag anything short, fixed-value, and unexplained by app behavior.

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first: every "Open in Falcon" button below uses this selection.

All eleven queries below are detect / hunt only. None of them, and nothing in the IOC appendix (Section 10), should be wired to a blocking action: the egress and DNS queries in particular hit shared, legitimate third-party infrastructure (public Ethereum RPC gateways) that many unrelated benign systems also use.

Q1 · New or Modified .user.ini Setting auto_prepend_file
CONF HIGHFP LOWCOST LOW

Looks for: a web-server worker process writing .user.ini at runtime, the #1 persistence point (auto_prepend_file), cached by PHP for up to five minutes. FP: legitimate deploy pipelines touching .user.ini during a release window.

// HUNT: New or modified .user.ini setting auto_prepend_file
// MITRE: T1505.003
// CONF: high
// FP: low
// COST: low
// REQUIRES: CriticalFileModified (Falcon FIM / Critical File policy covering the web document root) -- ⚠ validate in tenant: .user.ini must be added to your Falcon File Integrity Monitoring path list, it is not covered by default
// FALSE POSITIVES: deploy pipelines (Composer/WP-CLI/CI runners) touching .user.ini during a scheduled release window
#event_simpleName=/CriticalFileModified/
| FileName=/^\.user\.ini$/i
| ContextBaseFileName=/^(php-fpm|php-fpm[0-9.]*|php|httpd|apache2|nginx)/i
| table([aid, ComputerName, FileName, FilePath, ContextBaseFileName, ContextProcessId, UserName, @timestamp])

Hardening: Tiered

Immediate (this week)

Deny PHP execution inside writable upload/theme directories. M1038 (Execution Prevention). The single highest-leverage control: it breaks the shim, the hidden loader, the mu-plugin drop, and the ZIP-restore fallback in one move, because none of them can run if the web server refuses to execute PHP from those paths. Cite: OWASP WordPress hardening guidance; CIS Apache/Nginx benchmarks (web-root execution restrictions).
Verify: curl -s -o /dev/null -w '%{http_code}' https://SITE/wp-content/uploads/test.php should return 403/404 after a harmless test file is placed and the rule is live.

Immediate (this week)

Lock down .user.ini handling at the PHP-FPM pool level. M1038 (Execution Prevention) / M1022 (Restrict File and Directory Permissions). Kills persistence point #1 (auto_prepend_file). ⚠ best-practice, no formal benchmark: php.net documents user_ini.filename but no CIS/vendor baseline covers this specific control; include it anyway, it is sound and directly threat-relevant.
Verify: php -i | grep user_ini.filename on the pool shows an empty value, or a changed .user.ini under the web root produces no behavior change after PHP-FPM reload.

Near term (1-4 weeks)

Deploy File Integrity Monitoring on the fixed drop-in set (db.php, advanced-cache.php, theme functions.php, mu-plugins/*, .user.ini) and rotate WordPress/DB/hosting credentials and salts. M1047 (Audit) / M1032-adjacent credential hygiene. Ties directly to CQL Q1-Q5.
Verify: a deliberate test write to any listed path produces a CriticalFileModified event within the expected latency window; wp config shuffle-salts run and confirmed via a forced re-login of all sessions.

Near term (1-4 weeks)

Add a WAF rule flagging (not necessarily blocking) the short-prefix/fixed-value beacon parameter, and an egress-monitoring rule surfacing web-server HTTPS connections to public blockchain RPC providers for SOC review. M1037 (Filter Network Traffic).
Verify: a synthetic request carrying a candidate beacon-shaped parameter appears in the WAF log/alert queue; a test outbound connection to a known public RPC endpoint from the web host appears in the egress-monitoring queue.

Strategic (1-3 months)

Run PHP-FPM under a dedicated, least-privilege user per site; enable open_basedir; disable exec/shell_exec/system/proc_open/popen in the web-facing pool's disable_functions; reduce the WordPress DB user's grants to remove CREATE TRIGGER/DROP rights. M1018 (User Account Management) / M1042 (Disable or Remove Feature or Program). Directly blocks the shell-spawn (Q7), the direct-mysql-client path (Q9), and the database-trigger reinfection vector Sucuri flags in related variants.
Verify: php -i | grep disable_functions lists the disabled set; SHOW GRANTS FOR 'wp_user'@'%'; no longer includes TRIGGER/DROP.

Strategic (1-3 months)

Formalize a WordPress core/plugin/theme patch-management SLA. M1051 (Update Software). Sucuri's own prevention guidance states most of the compromises they handle exploit already-fixed vulnerabilities; this is the actual root-cause control for the unconfirmed initial-access step in Section 3.
Verify: wp plugin list --update=available and wp core check-update return empty against the documented SLA window.

Deployable Playbooks

Playbook 1: Deny PHP execution in uploads (Nginx)

Prerequisites: shell access to the Nginx config for the vhost; ability to reload Nginx. Reboot required: no (config reload only). Rollback: remove the added location block and reload; no data is modified.

location ~* /wp-content/uploads/.*\.php$ {
    deny all;
    return 403;
}
# Reload (no restart, no downtime):
sudo nginx -t && sudo systemctl reload nginx

Playbook 2: Deny PHP execution in uploads (Apache / .htaccess)

Prerequisites: mod_rewrite/mod_authz_core enabled; write access to wp-content/uploads/.htaccess. Reboot required: no. Rollback: delete the added <FilesMatch> block from the .htaccess file.

<FilesMatch "\.php$">
    Require all denied
</FilesMatch>

Playbook 3: Lock down PHP-FPM pool (disable_functions + .user.ini)

Prerequisites: access to the PHP-FPM pool's php.ini / pool conf; a maintenance window (some legacy plugins may call shell_exec and will break; test on a staging ring first). Reboot required: PHP-FPM service restart (brief request-queue pause, not a host reboot). Rollback: restore the previous php.ini from backup and restart PHP-FPM; re-enabling individual functions is also possible without a full revert if one legitimate plugin is found to need one.

; php.ini (web-facing pool)
disable_functions = exec,shell_exec,system,passthru,proc_open,popen
user_ini.filename =
open_basedir = /var/www/site/:/tmp/

; Reload the pool:
sudo systemctl restart php8.3-fpm

Playbook 4: WordPress DB user least privilege

Prerequisites: MySQL/MariaDB admin access; confirm no legitimate plugin relies on the WP DB user holding TRIGGER/CREATE/DROP (most do not). Reboot required: no. Rollback: re-grant the removed privileges with the equivalent GRANT statement if a legitimate plugin breaks.

REVOKE TRIGGER, CREATE, DROP, SUPER, FILE ON *.* FROM 'wp_user'@'%';
GRANT SELECT, INSERT, UPDATE, DELETE, ALTER, INDEX ON wordpress_db.* TO 'wp_user'@'%';
FLUSH PRIVILEGES;
SHOW GRANTS FOR 'wp_user'@'%';   -- confirm TRIGGER/CREATE/DROP/SUPER/FILE are gone
