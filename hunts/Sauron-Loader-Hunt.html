Executive Summary

DCSO CyTec published research on 2026-09-24 describing a previously undocumented loader family it calls Sauron Loader, encountered in multiple real-world incidents against organizations in Germany. The malware is sold as Malware-as-a-Service in Russian-speaking underground forums by an actor operating under the alias "S4ur0n" (leetspeak for "Sauron"), and the seller's own advertisement states the loader is intended exclusively for Russian-speaking customers and is not to be used against public-sector organizations or post-Soviet states. Cyber Security News independently corroborated the finding on 2026-09-25 after DCSO shared the report with them directly, and the write-up was further mirrored by Cryptika, summarized by Mallory.ai, and cross-posted to the malware.news community board. This pack treats the DCSO CyTec research as the primary technical source and Cyber Security News as the second independent confirmation.

In the incidents DCSO supported, Sauron Loader was the final stage of attack chains that began with social engineering rather than exploitation: ClickFix-style fake verification prompts and voice phishing, where victims were first flooded with spam email (email bombing) and then contacted by attackers posing as IT support, in some cases directing the victim to start a Microsoft Quick Assist remote-assistance session. The observed MSI installer drops three files into the hardcoded directory C:\ProgramData\keyroll: the legitimate, genuinely Mozilla-signed utility rnpkeys.exe (part of the RNPGP suite), the malicious loader library rnp.dll that it side-loads, and a second malicious library tdwp.dll that decrypts rnp.dll's encrypted sections directly in memory and creates a scheduled task named keyroll for persistence. The malware deliberately delays execution during decryption, a technique intended to frustrate antivirus and automated sandbox analysis.

The highest-value defensive angle is the directory and the task name, not the DLL filenames. rnpkeys.exe and rnp.dll are real Mozilla RNP component names, so hunting on the filenames alone risks flagging genuine RNPGP installs. What is campaign-specific is the combination: those exact binaries running from C:\ProgramData\keyroll, dropped by an MSI, backed by a scheduled task literally named keyroll. That combination has no benign explanation in a normal estate.

The second-highest-value angle is the four named command-and-control domains recovered from the decrypted embedded configuration: api.namsb-show.com, api.quinlantours.com, api.virtual-magic.com, and api.lahaina-shores.com. All four, plus the four SHA-256 hashes (the malicious MSI, the malicious rnp.dll, the malicious tdwp.dll, and the legitimate rnpkeys.exe for context only), were independently published by both DCSO CyTec and Cyber Security News, which qualifies the malicious set for a block posture under this pack's two-source rule.

Defender priority: import the section 10 CSV into Falcon IOC Management and block the four C2 domains at DNS and proxy today, then run Q2 and Q4 across a 90-day window. A hit on either is a confirmed compromise until proven otherwise: nothing in a normal estate legitimately places rnpkeys.exe in C:\ProgramData\keyroll or registers a task named keyroll. Never block the rnpkeys.exe hash itself; it is a genuine signed Mozilla binary and blocking it does nothing to stop the campaign.

Research decisions

  • Prevent/critical requires two independent sources. The four C2 domains and the three malicious SHA-256 hashes (MSI, rnp.dll, tdwp.dll) are published identically by both DCSO CyTec and Cyber Security News, two editorially independent outlets, so they ship at action=prevent. The Cryptika mirror is not counted as a second source because it discloses itself as a republish of the Cyber Security News piece.
  • The legitimate rnpkeys.exe hash never ships as prevent. It is a genuine, correctly signed Mozilla RNPGP binary that the loader abuses for side-loading. It is listed as a hunt anchor with an explicit do-not-block marker in sections 4 and 10.
  • Filenames alone are not sufficient hunt anchors. rnpkeys.exe and rnp.dll are real RNPGP component names. Every CQL query keys on the unexpected parent path (C:\ProgramData\keyroll), the MSI-dropped context, the scheduled task name, or the DLL appearing outside its known location, never on the filename in isolation.
  • No aggregator-only indicators. Mallory.ai's page masks every atomic value, so nothing atomic in this pack traces to it. It was used only to confirm the narrative and the actor alias.
  • No related-cluster IOCs imported. Mallory.ai's "Related stories" panel lists unrelated malware (LegionLoader/Satacom, TA4922's SilentRunLoader/Atlas RAT, generic ClickFix/Donut loader campaigns). None of their indicators (for example a 167.88.167.9:8356 callback or an obs.dll sideload from a different campaign) belong to Sauron Loader and none are shipped in this pack.
  • Prompt-injection review. All five fetched sources (DCSO/malware.news mirror, Cyber Security News, Cryptika, Mallory.ai, DCSO's GitHub repository) were reviewed for text addressed to an automated reader: instructions to fetch further URLs, change scope, or skip a check. None were found. No source was disqualified.
  • Access note. The DCSO CyTec Medium post (the cited primary source) returns HTTP 403 to automated fetch tools. Its full text was retrieved and saved instead from its malware.news community mirror, which reproduces the post verbatim including the appendix TTP-mapping table and the indicator list.
  • Perishability. DCSO reports finding additional Sauron Loader samples with different embedded C2 infrastructure beyond the analyzed sample. The four named domains will not be the last set this loader uses; the behavioral queries in section 8 (path, task name, MSI-to-sideload chain) are built to outlive a C2 rotation.

07

Native Audit-Log Hunts (non-CQL)

Proxy / web gateway

  • Search proxy access logs for HTTPS POST requests whose path matches /<prefix>/v[1-9]/<action><resource> where prefix is one of api, webhook, metrics, public, internal, action is set or get, and resource is one of Config, Status, Profile, Settings, Preferences, Token, Metadata, Connection, Timeout, Features. A single client hitting several of these path shapes at a steady interval is the loader's registration/poll cycle.
  • Filter on the two documented loader user-agent strings: Mozilla/5.0 (Windows NT %d.%d; Win64; x64) AppleWebKit/537.36 (KHTML, like Gecko) Chrome/143.0.0.0 Safari/537.36 Edg/143.0.3650.96 for Windows 10 and above, and Mozilla/5.0 (Windows NT %d.%d; Trident/7.0; rv:11.0) like Gecko for Windows 8, where %d.%d is the actual Windows major/minor version.
  • Look for a steady beacon rhythm consistent with the documented sleep timers: roughly 160 seconds after a failed registration or poll (also triggers C2 rotation to one of the other three domains), and roughly 600 seconds after a successful poll/task cycle.
  • If your proxy or firewall can TLS-inspect the session, the plaintext-before-encryption structure is a Salsa20 key/nonce header (16-byte key, 8-byte nonce on client requests; 32-byte key, 8-byte nonce on server responses) followed by an RSA signature and ciphertext length fields, then 1111 to 9999 bytes of random padding. This shape is unusual enough to fingerprint even without breaking the encryption.

DNS resolver

  • Query resolver logs for the four named domains in section 4 over your longest retention window. DCSO notes it found additional samples with different embedded C2 infrastructure, so treat the four names as a floor, not a ceiling.
  • Flag repeated NXDOMAIN or fast domain-rotation patterns from a single client immediately following a resolution of one of the four known domains: this is the loader's documented C2-rotation-on-failure behavior.

Email gateway

  • Search for a sudden, sharp increase in inbound mail volume to a single mailbox in a short window (email bombing), especially newsletter or mailing-list signup confirmations, which is a common bombing technique.
  • Cross-reference any mailbox that received an email-bombing pattern against subsequent inbound or outbound calls, help-desk tickets, or remote-assistance session logs within the following hours.

Remote-assistance tooling

  • Audit Microsoft Quick Assist (and AnyDesk, if present in your estate) session logs for sessions initiated by a standard user shortly after an email-bombing event, without a corresponding IT ticket opened beforehand by the user.
  • Confirm your help desk has, and staff actually follow, an out-of-band identity-verification step before starting any unsolicited remote-assistance session.

Windows endpoint (Sysmon / native)

  • Sysmon Event ID 7 (Image Loaded): rnpkeys.exe loading rnp.dll from C:\ProgramData\keyroll. This is the cleanest sideloading signal and Falcon's Custom IOA rule types are the closest native equivalent (section 9).
  • Sysmon Event ID 11 (File Create): any of rnpkeys.exe, rnp.dll, or tdwp.dll created under C:\ProgramData\keyroll.
  • Sysmon Event ID 1 (Process Create) with a command line invoking schtasks.exe /create and a task name of keyroll, as a cross-check against the native ScheduledTaskRegistered event used in Q4.
  • Enumerate C:\ProgramData for any subdirectory containing exactly the triad rnpkeys.exe, rnp.dll, tdwp.dll, regardless of the parent folder name, in case a future build renames the drop directory. Playbook 1 in section 13 does this estate-wide.

Pick your tenant's cloud first: every "Open in Falcon" button below uses this selection.

None of these queries carry an in-query time filter. Set the window with the console time picker; the intended lookback is recorded in each card as a // LOOKBACK: comment. For this campaign use 90 days minimum, since DCSO reports finding additional samples with independently rotated C2 infrastructure.

Detection Validation Gates

Gate 1 — Telemetry ready

  • Confirm ScheduledTaskRegistered events are present estate-wide before trusting a clean result from Q4, Q8, or Q12: #event_simpleName=/^ScheduledTaskRegistered$/ | groupBy([ComputerName], function=count(as=n), limit=5000). A host group returning zero is invisible to the persistence queries.
  • Confirm DnsRequest is flowing before trusting Q1's silence.
  • Confirm PeFileWritten or NewExecutableWritten is enabled before trusting Q3, Q9, or Q10's silence.
  • Confirm your DNS resolver and proxy retention actually covers 90 days. If it covers 30, record that in the hunt ticket rather than reporting a clean hunt.

Gate 2 — Benign baseline

  • Before enabling Q7 or Q8 as a scheduled search, confirm whether your estate has a legitimate Thunderbird/RNP deployment or any scheduled tasks that legitimately install under ProgramData, and add the tuning exclusion in the card before promoting either to an alert.
  • Run Q11 for one full week first and inspect the Conns distribution; anything that looks like normal telemetry or update-check traffic belongs in the CIDR/vendor-range exclusion, not in the alert.

Gate 3 — Confirm the finding, not just the query

  • A hit on Q2, Q3, Q4, or Q5 is high-confidence on its own; still pull the full directory listing of C:\ProgramData\keyroll before isolating, since the loader may already have staged an additional payload there.
  • A hit on Q7, Q8, Q9, Q10, or Q11 alone is not sufficient to declare compromise; corroborate against Q1, Q2, Q4, or Q6 on the same host before escalating.

Hardening — Tiered

Each control names the MITRE mitigation it satisfies and the platform authority that defines it. Controls are ordered by leverage against this specific chain, not by comprehensiveness.

Immediate — deploy this week, no compatibility risk
  1. Block the four confirmed C2 domains at DNS and proxy. Import the section 10 CSV into Falcon IOC Management and add the same domains to your resolver's denylist. MITRE M1037 Filter Network Traffic. Verify: resolve each name from a user subnet and confirm NXDOMAIN or sinkhole.
  2. Deny execution from unexpected ProgramData subdirectories. An AppLocker or WDAC deny rule targeting non-vendor executables running from %ProgramData%\* removes the exact drop-and-run pattern this loader depends on. MITRE M1038 Execution Prevention; CIS Microsoft Windows Benchmark application-control section; Microsoft Security Baseline. Verify: stage a benign EXE under a non-approved ProgramData subfolder and confirm it is blocked.
  3. Require out-of-band identity verification for any unsolicited IT-support contact. The vishing chain depends entirely on the victim trusting a cold caller. Publish and drill a verification procedure (callback to a known internal extension, ticket-number cross-check) before any remote-assistance session is granted. MITRE M1017 User Training. best practice, no formal benchmark covers social-engineering process controls directly.
  4. Restrict who can initiate or accept Microsoft Quick Assist sessions. At least one DCSO-observed incident used Quick Assist as the remote-access vector after the fake support call. MITRE M1042 Disable or Remove Feature or Program. Verify: confirm Quick Assist is removed or policy-restricted on standard-user endpoints outside an active, ticketed support session.
  5. Enable the three Defender ASR rules listed in section 10 in Block mode. The JS/VBS and Office child-process rules cut off two of the ten documented payload-handler execution paths. MITRE M1038, M1040 Behavior Prevention on Endpoint; Microsoft Defender ASR documentation. Verify: Get-MpPreference | Select-Object -ExpandProperty AttackSurfaceReductionRules_Ids.
  6. Alert on email-volume anomalies per mailbox. Email bombing is the documented precursor to the vishing call in this campaign. MITRE M1031 Network Intrusion Prevention. best practice, most mail security platforms ship a volume-anomaly rule that is disabled by default.
Near term — 1 to 4 weeks, pilot on a ring first
  1. Remove non-admin MSI install rights. Set AlwaysInstallElevated=0 in both hives and DisableMSI=2 for standard users. The ClickFix and vishing chains both rely on a user (or an attacker with remote-assist access) being able to run an unmanaged MSI. MITRE M1026 Privileged Account Management, M1038; CIS Windows Benchmark installer section.
  2. Publisher-and-path allowlisting for signed vendor utilities. A WDAC or AppLocker publisher rule that permits rnpkeys.exe (and other genuine Mozilla/vendor binaries you rely on) only from their real install paths directly defeats this side-load pattern regardless of which signed binary a future build picks. MITRE M1038; CIS Windows Benchmark; Microsoft WDAC design guide. Verify: Get-AppLockerPolicy -Effective -Xml and a copy-to-ProgramData execution test.
  3. Baseline and alert on new scheduled task creation outside a known-good vendor set. Every DCSO-observed Sauron Loader infection persists via exactly one scheduled task. MITRE M1047 Audit. Feeds Q8 and Q12 directly.
  4. TLS-inspecting proxy on user egress, with a documented exception list. Without it, the C2 URI shape and Salsa20/RSA header structure in section 7 are unavailable to you, and the loader's beacon looks like any other HTTPS traffic. MITRE M1020 SSL/TLS Inspection.
  5. Simulated vishing / email-bombing tabletop exercise for the help desk. The technique's reported 72% success rate in industry reporting on this class of attack means a documented process alone is not enough; staff need to have practiced saying no. MITRE M1017 User Training.
Strategic — 1 to 3 months, architectural
  1. WDAC in enforcement mode across the managed estate. Application control is the only control in this list that defeats an unknown future Sauron Loader build on the day it ships, regardless of which signed binary or drop directory it uses. Audit mode first, then enforce ring by ring. MITRE M1038; Microsoft WDAC deployment guidance.
  2. Retention uplift for DNS, proxy, and remote-assistance session logs to 12 months. DCSO reports finding additional samples with rotated infrastructure; a 30-day retention window would report a live compromise as clean. MITRE M1047 Audit. best practice, retention targets are regulatory, not benchmark-defined.
  3. Formalize a help-desk impersonation runbook as part of the broader incident-response plan. Vishing followed by fake IT support has been used to deliver DarkGate and by Black Basta affiliates historically, and this campaign confirms it is still a live, effective initial-access technique. MITRE M1017.

Deployable Playbooks

Playbook 1 — Sweep for the Sauron Loader triad (PowerShell)

Finds the drop directory or any folder anywhere on disk containing all three loader filenames together, in case a future build renames the keyroll directory. Read-only; run it estate-wide before you change anything.

# Run as SYSTEM or an admin. Read-only enumeration.
$known = 'C:\ProgramData\keyroll'
if (Test-Path $known) {
    Get-ChildItem -Path $known -File -ErrorAction SilentlyContinue | ForEach-Object {
        [pscustomobject]@{
            Host   = $env:COMPUTERNAME
            Path   = $known
            File   = $_.Name
            Sha256 = (Get-FileHash $_.FullName -Algorithm SHA256).Hash
        }
    }
}

# Broader sweep: any ProgramData subfolder containing all three filenames,
# in case a future build renames the "keyroll" directory itself.
Get-ChildItem 'C:\ProgramData' -Directory -ErrorAction SilentlyContinue | ForEach-Object {
    $dir = $_.FullName
    $has = @('rnpkeys.exe','rnp.dll','tdwp.dll') | Where-Object {
        Test-Path (Join-Path $dir $_)
    }
    if ($has.Count -eq 3) {
        [pscustomobject]@{
            Host      = $env:COMPUTERNAME
            Directory = $dir
            Triad     = 'CONFIRMED'
        }
    }
}
# All three filenames together in one ProgramData subfolder is the Sauron
# Loader triad regardless of the directory name. Collect the folder and the
# scheduled task list before isolating.

Playbook 2 — Audit for the "keyroll" scheduled task (PowerShell)

Cross-checks the native ScheduledTaskRegistered telemetry in Q4 against the local task scheduler directly. Read-only.

Get-ScheduledTask | Where-Object { $_.TaskName -match 'keyroll' } | ForEach-Object {
    $info = Get-ScheduledTaskInfo -TaskName $_.TaskName -TaskPath $_.TaskPath
    [pscustomobject]@{
        Host      = $env:COMPUTERNAME
        TaskName  = $_.TaskName
        TaskPath  = $_.TaskPath
        Action    = ($_.Actions | ForEach-Object { $_.Execute }) -join ';'
        Arguments = ($_.Actions | ForEach-Object { $_.Arguments }) -join ';'
        State     = $_.State
        LastRun   = $info.LastRunTime
    }
}

Playbook 3 — Deny execution from ProgramData (AppLocker, GPO)

Deploy in Audit mode for 48 hours first; the report tells you which legitimate applications you are about to break before you enforce.

# 1. Create or edit a GPO linked to your workstation OU.
# 2. Computer Configuration
#      -> Policies
#      -> Windows Settings
#      -> Security Settings
#      -> Application Control Policies
#      -> AppLocker

Playbook 4 — Help-desk vishing verification checklist (process)

A one-page script for help-desk and IT staff to challenge an unsolicited "IT support" contact, especially one that follows an email flood.

1. Did the user open a ticket BEFORE this contact arrived? If no, treat as
   unsolicited.
2. Call the user back on a number from the internal directory, never a
   number the caller provided.
3. Never accept a Quick Assist / AnyDesk / remote-assist session initiated
   in response to an unsolicited call or a "fix it yourself" prompt.
4. Never read out, or ask the user to enter, a one-time code or session
   PIN to someone who called them first.
5. If a recent inbox flood is confirmed, treat any IT-support contact
   in the following 24 hours as suspicious by default and escalate to
   the security team before any remote access is granted.

Containment & Incident Response Runbook

  1. Isolate, don't kill, the affected host first. Network-contain via Falcon host isolation rather than terminating the process; killing tdwp.dll's scheduler mid-cycle can complicate forensic timing but the host should stop reaching the C2 immediately.
  2. Preserve C:\ProgramData\keyroll before remediation. Copy the full directory listing, all three files, and their hashes off the host. Confirm whether an additional payload has already been staged there via the message-type-4 payload-retrieval mechanism.
  3. Pull the scheduled task definition for "keyroll." schtasks /query /tn keyroll /xml before deleting it, to capture the exact executable path and arguments for the case file.
  4. Identify the entry vector. Check whether the user reports a recent email-bombing event, an unsolicited IT-support call, or a ClickFix-style prompt they were told to run. This determines whether the help-desk verification gap (hardening item 3) or the mail-flow anomaly detection (hardening item 6) needs the more urgent fix.
  5. Check for a granted remote-assistance session. Review Quick Assist, AnyDesk, or similar tool logs around the infection window for a session the user did not initiate themselves.
  6. Hunt laterally with Q1, Q2, Q4, and Q6 estate-wide before declaring scope. A single confirmed host rarely means a single victim; the loader's registration message reports domain-join status, so check whether the host is domain-joined and, if so, whether credentials used on it require rotation.
  7. Rotate credentials used on or near the compromised host if there is any indication of screenshot exfiltration (task-results messages with non-zero total_data_length) or a downloaded credential-theft payload via the DLL or shellcode handler.
  8. Remove the triad and the scheduled task, then re-image if the loader executed a downloaded second-stage payload. A confirmed hit on Q9 (temp-staged payload) or Q12 (rundll32/regsvr32 against a component DLL) raises this from "clean the loader" to "assume second-stage compromise."
  9. Block the four C2 domains estate-wide if not already enforced, and check DNS logs for any other host that has ever resolved them.
  10. File the hunt ticket in section 16 with the confirmed entry vector, host count, and whether a second-stage payload executed, before closing the incident.
