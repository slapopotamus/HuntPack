Executive Summary

ShellterLoader is a Windows downloader/dropper reported by CYFIRMA in its Weekly Intelligence Report dated 2026-10-01. It is not itself a data-theft tool: its job is to establish an initial foothold and retrieve a second-stage payload, making the visible sample only one link in a longer chain. On startup it creates two named mutexes (ChromeProcessSingletonStartup! and OMADM_NAMED_MUTEX) to enforce a single running instance, then runs basic environment checks and may alter its behavior or terminate if the host looks unsuitable for continued execution (analysis evasion). It masquerades as, or runs from paths and under names associated with, Chrome, Edge, and Windows system binaries (chrome.exe, msedge.exe, BackgroundTaskHost.exe, RuntimeBroker.exe) and mimics Chromium user-data artifacts. It uses reflective loading and in-memory execution, with memory and thread manipulation consistent with code injection into another process's context, to retrieve and stage its next-stage payload over a websocket channel at wss.scriptlab.cc. CYFIRMA's own narrative also describes the loader communicating with, or masquerading traffic as, the legitimate comScore analytics domain sb.scorecardresearch.com during payload retrieval.

Single-source caveat: as of this pack's build date, CYFIRMA is the only source located for ShellterLoader under this name. A targeted search (threat name, sample hashes, named mutexes) found no independent corroboration. Per this pipeline's two-source rule, every indicator in this pack ships at action=detect only — nothing is promoted to Prevent or Critical. Treat any hit as a precursor to a broader compromise: the second-stage payload is not described in the available reporting.

Defender priority: sb.scorecardresearch.com is a legitimate third-party comScore analytics domain. CYFIRMA's own text frames ShellterLoader as masquerading as, or abusing, traffic to it — not owning it. Do not block this domain. The actionable, low-noise signals are path/name anomalies on Chrome/Edge/system-binary masquerades and the dedicated scriptlab.cc C2 domain.

Native Audit-Log Hunts (non-CQL)

The behaviors below are described in the source reporting but are not exposed as queryable fields in Falcon's documented LogScale event model (crowdstrike-logscale-v3 reference set). They are listed here as honest gaps with the best available compensating approach, rather than being forced into a fabricated CQL field.

  • Mutex creation (ChromeProcessSingletonStartup!, OMADM_NAMED_MUTEX): Falcon's CQL/LogScale event model does not expose named kernel-object creation as a queryable event. This guardrail is visible to Falcon's on-sensor ML/behavioral detection engine but not as raw telemetry you can hunt with CQL. Validate presence of these objects via Falcon Real Time Response (RTR) on hosts already flagged by Q1–Q5, or a live-response handle enumeration during IR.
  • Reflective loading / in-memory execution / thread or memory manipulation consistent with injection: no Falcon CQL field directly exposes RWX memory allocations or remote-thread creation. Rely on Falcon's built-in IOA/ML detections (console-side, not LogScale-queryable) for this layer, and use RTR to inspect the loaded-module list of hosts already flagged by Q1–Q5 for threads whose start address does not map to a known module.
  • Chromium user-data artifact mimicry (settings.dat, lockfile, Variations, BrowserMetrics-6AB8F3B2-122C.pma under a masquerading User Data tree): these are non-executable data-file writes. Falcon's documented event catalog (PeFileWritten, NewExecutableWritten, ZipFileWritten) covers executables and archives, not arbitrary data files, so this artifact set is not reliably CQL-queryable today. If your environment layers Sysmon, hunt Event ID 11 (FileCreate) for these exact filenames under a path that fails the FilePath anchoring used in Q1.
  • Environment / host-suitability checks (generic discovery before ShellterLoader decides whether to run): the source reporting describes these only generically — no atomic registry key, command, or API was published. Treat as a documented gap rather than building a hunt on an assumption; pair any Q1–Q5 hit with the discovery-chain hunts already in your library (for example systeminfo.exe/tasklist.exe/wmic.exe spawned immediately after a masquerading process).
