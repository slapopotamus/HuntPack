Executive Summary

SignDrop is a public, unpatched Windows local privilege escalation: a standard user reaches NT AUTHORITY\SYSTEM by abusing the CLFS log-file authentication feature that Microsoft added after October 2025. Proof-of-concept code was published on 2026-11-10 on GitHub by the researcher Abdelhamid Naceri (handles Nightmare Eclipse, MSNightmare). There is no CVE, no patch and no Microsoft advisory as of 2026-11-12. The mechanism is a logic flaw, not memory corruption: when a privileged process opens a prepared CLFS log, clfs.sys creates the companion .cnpf file in that process's security context, and Object Manager symbolic links redirect the creation to an attacker-chosen path. In the published chain the privileged caller is the Microsoft Defender antimalware service, reached through its signature-update RPC interface.

What is and is not known. No attacks using the exploit have been reported and it is not in CISA KEV (THN, Cyderes). Cyderes reproduced a SYSTEM shell. An independent test by 78researchlab found it works but is not reliable enough for operational use (THN). The researcher's claim that about 80 percent of Windows installations are vulnerable has no supporting data (Cyderes: low confidence). Microsoft told SecurityWeek it is investigating, that Defender detects and blocks exploitation and alerts on the associated behavior, and that it has not observed exploitation in the wild. This pack does not imply active exploitation.

Why it still matters. The code is public, the attacker needs only a standard-user foothold, and the exploit deletes its planted DLL afterward, so evidence must come from file-creation, image-load and process-creation telemetry captured at the time. Prior releases from the same researcher have been weaponized: THN reports three earlier Defender flaws from this researcher were exploited in attacks. SignDrop itself is a different class of issue.

Defensive angle. The highest-signal detections per Cyderes are a Defender signature-update RPC call from outside the Defender service tree and any hid.dll creation in the ink directory. The RPC call has no standard endpoint event, so this pack leads with the file, process and image-load angles that do, and flags the RPC and symbolic-link stages as honest telemetry gaps. Do not disable CLFS authentication as a workaround: it re-exposes the older memory corruption bugs the feature was built to stop.

Defender priority: deploy Q1, Q2 and Q3 now (hid.dll in the ink directory, the chain correlation, and any child of consent.exe), turn on file-creation auditing for the ink directory, inventory the CLFS Authentication Mode on every host, and make sure file-creation and image-load telemetry is retained long enough to survive the exploit's self-delete. Watch the Microsoft Security Update Guide for a CVE.

Decisions and conflicts

  • Mode values. Microsoft documents 0, 1 and 2. THN says a value of 2 or 3 means the mitigation is disabled. This pack treats any value other than 0 or 1 as outside the claimed attack surface, and treats the host as having lost the protection against the older bug class.
  • Defender as a control. THN says Defender must be enabled for the published chain. Microsoft says Defender detects and blocks it. Cyderes builds its detections so none depend on Defender catching the exploit, because Defender is the component the exploit uses. This pack follows Cyderes: Defender alerts are a bonus, not the control.
  • Researcher publication points. The GitHub repository and two mirrors named by Cyderes are research provenance. They are not adversary infrastructure and none of them ships as a block, prevent or C2 row.
  • Related releases. Cyderes notes the symbolic-link monitoring also helps for ShieldBreak and ShieldCrash. That shared detection value is noted in Section 15. No indicator from those releases is imported here.
  • Not carried forward. The writeup claim that SignDrop turns off any AV or EDR is single-sourced to press paraphrase and was not tested by Cyderes or the independent lab, so it is not used to rate severity.

Q1 · hid.dll created in the Common Files ink directory
CONF HIGHFP LOWCOST LOW

Looks for: A file named hid.dll written into C:\Program Files\Common Files\microsoft shared\ink. Cyderes states the file does not ship there with Windows, so any write is the successful privileged write (Table 2, row D) regardless of variant. The path is the signal, not the name: the real hid.dll lives in System32.

Known limitations and deployment notes
  • PowerQuery: The CQL restricts to portable-executable writes; this query keys on the path and name, so a non-PE file with this name also matches.
  • PowerQuery assumes: tgt.file.path holds the full path of the written file.
  • PowerQuery assumes: A modification of an existing file at this path is treated like a creation.
  • KQL – Defender XDR: The CQL restricts to portable-executable writes; this query keys on the path and name.

Hardening: Tiered

There is no patch. These controls reduce exposure and raise detection; none removes the flaw. Do not disable CLFS authentication, and do not disable Defender, as a workaround. THN and Cyderes both warn that disabling the mitigation reopens the older CLFS memory corruption bugs.
Immediate (this week)
  • Inventory CLFS authentication Mode on every host (Playbook 1). Mode 0 or 1 defines the population to prioritize. MITRE M1047 (Audit), M1019 (Threat Intelligence Program). Authority: Microsoft Learn CLFS logfile authentication; Cyderes. Verify: the script output.
