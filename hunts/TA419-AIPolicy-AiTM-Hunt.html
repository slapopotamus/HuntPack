Executive Summary

TA419, a China-aligned, espionage-motivated threat actor tracked by Proofpoint since at least April 2025, has run credential-phishing campaigns against US AI-policy experts at think tanks, universities, and legal-sector organizations from at least December 2025 through July 2026 (reported 2026-10-01). The attacker's objective is session-cookie / credential theft that survives MFA, not malware deployment: there is no payload anywhere in this chain.

The lure is a benign "conversation starter" email impersonating real named policy figures (a former White House OSTP leadership member, an economist/foreign-policy expert, and in one wave a senior Anthropic employee) inviting the target to join an "AI Policy Advisory Committee" or contribute to a report. Only after the victim replies does TA419 send a shortened URL that redirects through a first-stage filtering domain (Cloudflare Turnstile gate), then lands on a second-stage OneDrive-themed page built on a customized "Frameless BitB" browser-in-the-browser kit. That kit relays the victim's real Microsoft sign-in — including the MFA challenge — to genuine Microsoft infrastructure while silently capturing the resulting session cookie, giving the attacker a signed-in session without ever needing to defeat MFA directly.

Because this is a browser/authentication-layer compromise, the highest-value defensive angle is not endpoint detection — there is no process or file artifact to find — it is (1) blocking the 19 published pieces of infrastructure, (2) correlating DNS/browser-process telemetry to catch a host mid-chain, and (3) hunting Entra/M365 sign-in logs for the session-cookie-replay signature (non-interactive sign-in from a new ASN/country right after a legitimate interactive one, with no fresh MFA challenge). Phishing-resistant FIDO2/WebAuthn MFA structurally defeats this technique because the credential is bound to the legitimate origin and cannot be relayed through a look-alike domain.

Defender priority: if any of the identity hunts in §8 fire, treat it as a likely-successful compromise already in progress — revoke sessions and force re-authentication immediately. Do not wait for an endpoint signal that this campaign does not produce.

Native Audit-Log Hunts (non-CQL)

These checks use native portal/report views rather than CQL and should be run alongside §8:

  • Entra ID → Security → Risky sign-ins / Risk detections: filter for "unfamiliar sign-in properties" and "anonymous IP address" risk types in the campaign window (Dec 2025–present).
  • Entra ID → Conditional Access → Insights and reporting: review sign-ins that satisfied CA with a token/session that was issued outside expected device/location patterns.
  • Exchange Admin Center → Mail flow → Rules: audit for newly created inbox rules or transport rules in the hours following any flagged sign-in.
  • Exchange/Defender → anti-phishing impersonation report: check for messages from the four sender-impersonation domains that bypassed existing policy.
  • Web/SWG proxy logs (if present): search for Cloudflare Turnstile challenge-page loads immediately preceding a visit to any second-stage domain — not visible in endpoint DNS/network telemetry alone.

Q5 · Identity — Non-Interactive Sign-In From New Country/ASN After Interactive Sign-In
CONF MEDIUMFP MEDIUMCOST LOW

Looks for: per-user sign-in history to spot a non-interactive/token-based sign-in from a new country shortly after a legitimate interactive sign-in — the classic session-cookie-replay signature. // HUNT: TA419 - T1539 - Session Cookie Replay: Non-Interactive Sign-In From New Country After Interactive Sign-In
// HYPOTHESIS: After a legitimate interactive sign-in, the AitM-captured session cookie is replayed, producing a non-interactive sign-in for the same user from a different country shortly after -- with no fresh MFA challenge.

// TUNING: cross-check any hit against known corporate VPN egress ranges and recent business travel before escalating; collapse results per user and review the two closest-in-time entries for a country/ASN change.

azure_signinlogs
| groupBy([userPrincipalName], function=[collect([@timestamp, ipAddress, "location.countryOrRegion", isInteractive, authenticationRequirement], limit=200)], limit=5000)
| sort(userPrincipalName, order=asc)
Q6 · Identity — Same Session/Token Identifier From Two Distinct Source IPs
CONF MEDIUMFP MEDIUMCOST LOW

Looks for: a single sign-in token identifier observed from more than one source IP — direct evidence of a stolen session being used from attacker infrastructure alongside the legitimate user. FP: corporate load-balanced egress or carrier-grade NAT can occasionally present as multiple IPs for one session.

// HUNT: TA419 - T1539 - Same Session Token From Two Distinct Source IPs
// HYPOTHESIS: A session/token identifier captured by the AitM proxy is replayed from attacker infrastructure while the legitimate user continues to use the same token -- both source IPs appear against one token in the same window.
// CONF: medium  FP: medium  COST: low | REQUIRES: Entra ID sign-in logs (azure_signinlogs) with a token/session identifier field -- NOT core Falcon EDR
// ⚠ TENANT-SPECIFIC: uniqueTokenIdentifier is Microsoft's documented sign-in log field name; confirm it is populated and not parser-renamed in your tenant.
// TUNING: exclude known NAT/load-balancer egress pools (CGNAT, corporate proxy ranges) before escalating; a DistinctIPs count of exactly 2 with one IP geolocating outside the user's normal country is the highest-confidence case.
// LOOKBACK: 7d (set in the Falcon time picker)
azure_signinlogs
| groupBy([uniqueTokenIdentifier], function=[count(ipAddress, distinct=true, as=DistinctIPs), collect([@timestamp, userPrincipalName, ipAddress, "location.countryOrRegion"], limit=50)], limit=5000)
| DistinctIPs > 1
| sort(DistinctIPs, order=desc)

Hardening & Prevention

TTP: TA419 AI-Policy AitM Credential Phishing (Frameless BitB / session-cookie theft)   MITRE Technique: T1557, T1539, T1566.002, T1621   Primary Mitigations: M1032, M1056, M1017, M1021, M1018, M1047

This compromise lands entirely on the identity/authentication layer — there is no endpoint payload to contain. Hardening centers on making a captured credential/session cookie worthless (phishing-resistant auth, token binding) and on narrowing the lure's delivery surface.

Immediate — deploy this week
  • Block the full published TA419 indicator set (19 domains at the web proxy and DNS/firewall; the 3 attacker sender addresses at the mail gateway; the TLS cert fingerprint wherever cert telemetry is inspected) — 23 indicators in total. Framework: M1021; Proofpoint primary source (2026-10-01).
  • Revoke refresh tokens / force session sign-out for any user who resolved a listed domain, invalidating any session cookie already captured. Framework: M1018; Microsoft Entra "Revoke user sessions."
  • Enable Continuous Access Evaluation (CAE) tenant-wide to shorten the usable window of a stolen token. Framework: M1032; Microsoft Entra Conditional Access / CAE documentation.
  • Enable impersonation-protection / external-sender banners for the four lookalike partner domains and the organizations they imitate (Heritage Foundation, Japan-Taiwan Exchange Association, Japanese Defense Ministry). Framework: M1021; Exchange Online Protection anti-phishing policy.
Short-term — 1 to 4 weeks
  • Roll out phishing-resistant FIDO2/WebAuthn passkeys to the highest-risk population first (AI-policy, government-relations, executive staff) — the single control that structurally defeats Frameless BitB AitM. Framework: M1032; NIST SP 800-63B (AAL3); Microsoft Entra passkey/FIDO2 deployment guidance.
  • Deploy Conditional Access token protection (sign-in session binding) so an issued token can only be redeemed from the device it was issued to. Framework: M1032; Microsoft Entra Conditional Access "Token protection."
  • Require compliant-device / managed-browser Conditional Access for Microsoft 365 access, closing the gap where a stolen cookie is replayed from an unmanaged attacker browser. Framework: M1018.
  • Add shortened-URL expansion and newly-registered-domain scoring at the mail/web gateway — stage 2 always arrives as a shortened URL, and TA419's domains are registered through NameSilo and fronted by Cloudflare CDN to hide the backend host, so registrar/CDN-pattern and domain-reputation scoring both apply. (Proofpoint publishes first-seen dates per domain, not registration dates, so age-based scoring should be tuned on your own WHOIS feed rather than an assumed domain age.) Framework: M1021; CIS web-content-filtering control.
Long-term / structural — 1 to 3 months
  • User training on the "benign conversation-starter" pretext specifically — this campaign's defining trait defeats "don't click suspicious links" training because stage 1 has no link. Train on verifying unsolicited outreach via an independent channel before replying. Framework: M1017.
  • Expand token-protection and passkey enforcement tenant-wide, retiring SMS/voice/push MFA fallback where feasible since both remain relayable by an AitM proxy. Framework: M1032; NIST SP 800-63B.
  • Operationalize recurring re-ingestion of TA419 IOC updates and re-run this pack's identity hunts on a recurring cadence given the campaign's monthly infrastructure rotation. Framework: M1047.

What to verify after deployment

  • Confirm the 19 domains return a block/deny verdict at the web proxy and the 3 sender addresses are rejected at the mail gateway (test against the blocklist directly, not by browsing to the live phishing domains).
  • Confirm CAE is active: Entra ID → Security → Conditional Access → Insights and reporting should show "Continuous access evaluation" enabled.
  • Confirm token-protection policy state via Microsoft Graph PowerShell (Get-MgIdentityConditionalAccessPolicy) shows the session control attached.
  • Re-run Q5-Q8 (§8) 7 and 30 days after rollout to confirm the anomaly pattern has not recurred for enrolled users.
  • Confirm passkey/FIDO2 enrollment rate via Entra ID → Authentication methods → Registration report.

Deployable Playbooks

MITRE: T1557/T1539 → M1032, M1018   Estimated deploy time: 2-4 hours for immediate tier   Prerequisites: Entra ID P1/P2, Microsoft Graph PowerShell SDK

Step 1 — Revoke sessions for a suspected-compromised user

What it does: invalidates all refresh tokens and active sessions for one user. Why it works: an AitM-captured session cookie is worthless once the underlying refresh token is revoked (M1018).

# Requires: Connect-MgGraph -Scopes "User.RevokeSessions.All"
Revoke-MgUserSignInSession -UserId "REPLACE_WITH_USER_UPN_OR_ID"

# Verify:
Get-MgAuditLogSignIn -Filter "userPrincipalName eq 'REPLACE_WITH_USER_UPN'" -Top 5

Step 2 — Enable Conditional Access token protection

What it does: binds an issued token to the device/session it was granted to. Why it works: an AitM proxy capturing the token cannot replay it from a different device (M1032).

# Portal path:
# Entra admin center > Protection > Conditional Access > Policies > New policy
#   Target resources: Office 365 (or all cloud apps)
#   Session > Token protection > Require token protection for sign-in sessions

# Verify (Graph PowerShell):
Get-MgIdentityConditionalAccessPolicy | Where-Object { $_.SessionControls.PersistentBrowser -ne $null -or $_.SessionControls.AdditionalProperties.tokenProtection -ne $null }

Step 3 — Block the published IOC set at the mail/web gateway

What it does: prevents delivery/resolution of TA419's known infrastructure. Why it works: removes the lure and the landing page from reachability (M1021).

# Generic pattern -- adapt to your gateway's CLI/API (example shown for a generic blocklist import):
REPLACE_WITH_GATEWAY_CLI import-blocklist --type domain --file ta419_domains.txt --action block
REPLACE_WITH_GATEWAY_CLI import-blocklist --type sender --file ta419_senders.txt --action block

# Verify: attempt a controlled, non-browsing DNS lookup for one listed domain from a managed network path
# and confirm the gateway logs a block/deny entry.

Step 4 — Enroll high-risk users in FIDO2/passkey authentication

What it does: issues origin-bound, phishing-resistant credentials. Why it works: the credential cannot be relayed through a look-alike domain, structurally defeating Frameless BitB (M1032).

# Portal path:
# Entra admin center > Protection > Authentication methods > Policies > FIDO2 security key > Enable
# Target the high-risk group (AI-policy / government-relations / executive staff) first.

# Verify:
Get-MgReportAuthenticationMethodUserRegistrationDetail -Filter "userPrincipalName eq 'REPLACE_WITH_USER_UPN'"
