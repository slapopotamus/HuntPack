Executive Summary

What happened: Flare published research on 2026-09-24 describing TWEAKOS, a Windows infostealer paired with a Telegram-bot command-and-control channel and a built-in stolen-account marketplace. The operation surfaced after its own source code was posted to Pastebin, which exposed a hardcoded Telegram bot token and two hardcoded admin IDs shared by both the stealer and the backend bot. Cyber Security News, Cyber Press, Security Boulevard, and Cryptika independently corroborated the core mechanics on 2026-09-25 and after.

Observed tradecraft: TWEAKOS is two components sharing one bot token. The stealer harvests Discord authentication tokens from Local Storage LevelDB files for Discord, Discord PTB, and Chrome's default profile, validates each candidate against the Discord API, and exfiltrates working tokens to the operators. Separately, it social-engineers the victim for a Telegram phone number and login code, uses the Telethon library to mint a brand-new session file, and sends that session to two operator accounts, granting access without ever resetting the victim's password. Persistence needs no admin rights: the packaged build drops itself as SystemHelper.exe in the user Startup folder, and the script build adds an HKCU Run value named SystemHelper. A referenced follow-on payload, WindowsSecurityChecker.exe, was not recovered by researchers. Operators can also push a per-victim blocker_{uid}.vbs script that displays a repeating full-screen Russian-language warning to coerce payment or compliance.

Detection strategy: No file hashes and no dedicated malicious C2 domains or IPs were published for this campaign; every operator-facing network endpoint named in the reporting (Telegram's Bot API, Discord's API) is a legitimate, heavily-used public service. This pack's detection value is therefore behavioral: the two no-admin persistence mechanisms (Q01/Q02/Q03), the coercion script's execution pattern (Q05), a packaging fingerprint for the frozen Python binary (Q04), and clearly-labelled enrichment correlations against the two legitimate APIs (Q06/Q07) that must never be treated as blockable infrastructure on their own.

Operational consequence: A confirmed hit does not mean the endpoint alone is compromised: a stolen Discord token or a hijacked Telegram session is valid until revoked, independent of any local remediation. Response must include out-of-band account recovery (revoke Discord tokens, terminate the victim's active Telegram sessions from a trusted device) in addition to endpoint cleanup, because deleting the local artifact does not undo the account theft.

Defender priority: Hunt the two no-admin persistence patterns fleet-wide, treat any hit as an account-compromise event (not just a malware event) and drive Discord token revocation plus Telegram session termination in parallel with endpoint remediation.

Affected surface and telemetry

Surface: Windows endpoints running Discord, Discord PTB, or Chrome; Windows endpoints where users sign into personal Telegram accounts; the user Startup folder and HKCU Run hive; wscript.exe/cscript.exe script-execution surface. Exposure: user context only — no privilege escalation or admin rights are required or observed anywhere in this campaign.

Coverage boundaries

  • No portable Falcon event proves direct LevelDB file reads; H08 is a documented gap.
  • No file hash exists for any TWEAKOS component; every filename-based query can be defeated by a rename.
  • The backend database, marketplace, and pricing logic (C08, C09, C10) are operator-side and out of scope for endpoint hunting.
  • Account-level remediation (Discord token revocation, Telegram session termination) is outside Falcon's scope entirely and must be tracked as a separate response action.

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first — every "Open in Falcon" button below uses this selection.
Query strategy: Q01–Q03 are the strongest, lowest-effort persistence keepers. Q05 is a distinctive, low-FP coercion-script catch. Q04 is an unconfirmed packaging inference — keep it hunt-only. Q06/Q07 are enrichment correlations against legitimate infrastructure and must never be promoted to a standalone alert or a block rule.

All queries are STATIC-ONLY. Validate event population, fields, semantics, and volume in your tenant before operational use.

Q01 · SystemHelper.exe written to the Startup folder
CONF highFP mediumCOST low

Looks for: a file named SystemHelper.exe written into a user Startup folder path. Accomplishes: catches the packaged-build persistence variant at install time, before the first theft cycle runs.

Trace: H01 · IOA-1

// HUNT: SystemHelper.exe written into a user Startup folder (packaged-build persistence)
// HYPOTHESIS: H01
// USE: hunt
// MITRE: T1547.001
// CONF: high
// FP: medium
// COST: low
// TIMEFRAME: 30d
// REQUIRES: PeFileWritten with FileName, FilePath, ComputerName, UserName, SHA256HashData — ⚠ validate in tenant: some sensor versions expose the write-target directory as TargetDirectoryName instead of FilePath
// FALSE POSITIVES: any legitimate vendor utility that happens to share the generic name "SystemHelper.exe"
// TUNING: exclude hosts and hashes matching a known-vendor, Authenticode-signed "SystemHelper.exe" once your fleet baseline confirms one exists
// VALIDATION: STATIC-ONLY
#event_simpleName = PeFileWritten
| test(@timestamp >= now() - 2592000000)
| FileName = /^SystemHelper\.exe$/i
| FilePath = /\\Start Menu\\Programs\\Startup\\/i
| table([@timestamp, ComputerName, UserName, FileName, FilePath, SHA256HashData])
| sort(@timestamp, order=desc, limit=1000)
Q02 · HKCU Run value named SystemHelper
CONF highFP mediumCOST low

Looks for: a new HKCU ...\CurrentVersion\Run value literally named SystemHelper. Accomplishes: catches the script-build persistence variant, the other half of the no-admin persistence pair.

// HUNT: HKCU Run key value named SystemHelper (script-build persistence)
// HYPOTHESIS: H02
// USE: hunt
// MITRE: T1547.001
// CONF: high
// FP: medium
// COST: low

Q04 · Frozen-Python temp extraction from an unsigned binary
CONF low (inference)FP highCOST medium

Looks for: a process running from a PyInstaller-style _MEI<digits> temp-extraction folder with no Authenticode signature. Accomplishes: a packaging-level fingerprint for the frozen Python stealer build. // HUNT: Unsigned process executing from a PyInstaller-style _MEI temp-extraction path
// HYPOTHESIS: H04
// USE: hunt (unconfirmed inference, not a sourced TWEAKOS artifact)
// MITRE: T1204.002

Hardening — Tiered and Deployable

TWEAKOS requires no exploit and no admin rights: every stage depends on the victim running an untrusted file and then typing a login code into it. User education and no-admin-persistence hardening close most of this chain without any product-specific fix.

Immediate — this week
  • Train users that no legitimate service ever needs their login code read back to a program or a stranger — M1017 (User Training). The entire Telegram account-theft technique (C04) depends on the victim voluntarily supplying a one-time code; this single behavior change defeats it regardless of any technical control.
  • Enable Telegram two-step verification (cloud password) and Discord multi-factor authentication organization-wide where these services are sanctioned for business use — M1032 (Multi-factor Authentication). Raises the cost of both theft paths, though TWEAKOS's Telegram flow already attempts to solicit a cloud password if 2FA is present, so this must pair with the training control above.
  • Run Q01/Q02/Q03 fleet-wide as an immediate baseline sweep to establish current exposure before any tuning work begins.
Near-term — pilot first, 1–4 weeks
  • Deploy Q01–Q07 as scheduled hunts, with FP-medium/high queries (Q01, Q02, Q03, Q04, Q06, Q07) in hunt/detect-only mode pending the §11 baseline.
  • Restrict or monitor personal Discord/Telegram installation on managed endpoints where these are not business-required — M1042 (Disable or Remove Feature or Program). Directly reduces the population of endpoints exposed to Discord-token or Telegram-session theft.
  • Enable script-control/AMSI logging for wscript.exe/cscript.exe fleet-wide — M1040 (Behavior Prevention on Endpoint). Improves both detection and forensic capture speed for the short-lived blocker_<id>.vbs coercion script (C07).
  • Document an account-recovery runbook for Discord token revocation and Telegram session termination so responders can act the moment Q01–Q05 fires, since deleting the local artifact does not undo the account theft (§1).
Strategic — 1–3 months
  • Formalize a managed-endpoint policy on personal chat-app usage (installation, profile isolation from work identities, or removal) — M1042. TWEAKOS specifically targets the overlap between personal Discord/Telegram use and corporate endpoints.
  • Extend application allow-listing to the user Startup folder and HKCU Run hive where feasible — M1038 (Execution Prevention). Structurally closes both no-admin persistence variants in this campaign, not just the two named artifacts.
  • Recurring user-awareness campaign on login-code and account-takeover social engineering — M1017, repeated rather than one-time, since this technique class recurs across many unrelated stealer families beyond TWEAKOS.

Deployable Playbooks

Playbook A · SystemHelper.exe persistence sweep and validation

  1. Run Q01, Q02, and Q03 unfiltered across the fleet for a 30-day lookback; record every host, hash, and registry value returned.
  2. For each hit, pull the parent process tree and command line via ProcessRollup2 to establish how SystemHelper.exe arrived (download, removable media, email attachment, browser).
  3. Correlate each hit's timeframe against Q06/Q07 on the same host as enrichment context only; do not treat a Discord/Telegram API contact alone as confirmation.
  4. Where corroborated, begin account-level response in parallel with endpoint remediation: initiate Discord token revocation (N1) and Telegram session termination (N2) immediately, do not wait for full endpoint forensics.
  5. Remove the persistence artifact (Startup file or Run value) and the executable; preserve a copy and its hash for the §10 IOC appendix before deletion.
  6. Re-run Q01–Q03 after remediation to confirm no recurrence within one week.
  7. Retain hit list, hashes, account-recovery confirmation, and owner sign-off.

Playbook B · Suspected active coercion screen (blocker_<id>.vbs)

  1. Do not let the user act on the on-screen message (no payment, no contacting the listed Discord); the backend deletes the local script shortly after triggering it, so evidence capture speed matters.
  2. Immediately capture the running wscript.exe/cscript.exe process, its command line, and the referenced .vbs file from disk if still present.
  3. Run Q05 with a short lookback (last 24 hours) across the fleet to check for other affected hosts from the same operator campaign.
  4. Isolate the host from a user-interaction standpoint (lock screen access is not sufficient if the malware persists); investigate for the full TWEAKOS chain (Q01–Q03) since the coercion stage implies the operator already has an established channel to this victim.
  5. Proceed to account-level response (N1/N2) as in Playbook A, since a coercion trigger implies the operator already holds stolen credentials for this victim.
Design state: both playbooks are STATIC-ONLY guidance. Validate every query against your own tenant and complete a benign-baseline period before relying on them operationally.
