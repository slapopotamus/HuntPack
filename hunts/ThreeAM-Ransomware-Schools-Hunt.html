Executive Summary

A 3AM (ThreeAM) ransomware affiliate worked inside a UK school estate from 10 to 19 September 2026. Bitdefender, which investigated, published its analysis on 3 November 2026. The machine list held 47 systems: about 21 servers (8 of them domain controllers), 10 Windows 10 workstations, one Windows Server 2012 R2 domain controller and the rest Windows 11. The affiliate stole backup credentials first, made two backdoor domain administrators, joined three previously separate Active Directory domains with two-way trusts, pushed its access to about 40 machines, tried and failed to remove the security agents, then ran the Rust ThreeAM encryptor. About 37 of roughly 50 reachable machines were encrypted, at 12 to 13 seconds per machine.

Initial access was not established. Bitdefender states plainly that it does not know how the attacker got in. Two earlier events (Restricted Admin mode enabled on four machines in January 2026 and a hand-typed session in June 2026) may or may not be related and are not part of the September timeline. Bitdefender also redacted every victim host, IP address and domain as placeholders, so this pack ships no network indicators and no victim names.

The AI angle, stated at the strength the source supports. Bitdefender calls the operation a hybrid: some phases look like a human at the keyboard, others behave like an agentic loop in which a language model reads each result and retries. The evidence is behavioural: probe-confirm-label-revise habits, numbered script revisions, retry delays of 40 to 101 seconds whatever the size of the change, and errors typical of commands written from memory. Bitdefender could not access the attacker's machine, cannot name a model, says a person copying output between a shell and a chat window cannot be excluded, and says one investigation is an anecdote and not a trend. This pack does not claim a confirmed AI-operated attack, and every detection works the same whether a model or a person produced the commands.

Almost everything the affiliate used was built into Windows or public: PowerShell, WMI, reg, schtasks, netdom, dnscmd, nltest, wbadmin, a public Veeam credential script, Mimikatz and an Impacket-style tool. That is why this pack leans on behaviour and ships every indicator as detect only.

Defender priority: alert on any new domain trust (Q13), any reg save of the SECURITY, SYSTEM or SAM hives (Q6), any new Domain Admin account created from a server (Q11) and wmiexec-style ADMIN$ output files (Q7). Then harden the backup layer: per-domain backup accounts, isolated backup servers and immutable copies no domain account can delete. Bitdefender found the attacker hit backup first (credential theft) and last (deletion).

Hardening: Tiered

Immediate (this week)
  • Alert on new domain trusts. Enable the Authentication Policy Change audit subcategory on domain controllers and alert on 4706, 4707 and 4716. MITRE M1047, T1484.002. Bitdefender calls a new trust a rare change that is cheap to alert on. Playbook step 4.
  • Isolate the backup layer. Backup servers off the production domain or in a dedicated management domain, console and REST ports reachable only from admin jump hosts, MFA on the console. MITRE M1030, M1032, T1555. Veeam security best-practice guidance (vendor best-practice, formal benchmark not checked here: ⚠ best-practice, no formal benchmark). Playbook step 5.
  • Scope backup service accounts per domain. One account per domain, never one account with rights in several. Bitdefender found stolen backup credentials were the first move and the cross-domain accounts were what let the attacker build trusts. MITRE M1026, M1018. Playbook step 5.
  • Immutable recovery copies. At least one copy no domain account can delete (hardened Linux repository or object-lock storage) plus an offline copy. Bitdefender: the attacker hit backup first and last. MITRE M1053, T1490. Playbook step 5.
  • Turn on script block logging. It records the decoded form of the Base64 PowerShell the affiliate used. MITRE M1047, T1059.001, CIS Windows benchmark Administrative Templates, Windows PowerShell. Playbook step 7.
Near term (1 to 4 weeks, pilot first)
  • ASR rules in Audit, then Block: Block credential stealing from LSASS, Block process creations originating from PSExec and WMI commands, Use advanced protection against ransomware. MITRE M1040, M1043, T1003.001, T1047. Microsoft ASR documentation. The PSExec/WMI rule breaks SCCM-style client push unless excluded, so audit first. Playbook step 1.
  • LSA protection (RunAsPPL). MITRE M1025, M1043, T1003.001, CIS Windows benchmark Lsa protection setting. Needs a reboot and compatible drivers and security products. Playbook step 2.
  • Restrict remote execution and administrative shares to management hosts. Bitdefender: WMI, remote registry, scheduled-task creation and ADMIN$ were the attacker's movement fabric. MITRE M1030, M1037, M1042, T1021.002, T1047. Disable the RemoteRegistry service where unused. Playbook step 3.
  • Protected Users and tiered administration for every account able to create trusts or join domains (Domain Admins, Enterprise Admins). No cached or reusable credentials, no domain-admin logon to member servers or workstations. MITRE M1026, M1043, M1018, T1078.002. Playbook step 6.
  • Block interpreters and shells where nothing needs them: portable Python from Temp, PowerShell on workstations that do not use it (Constrained Language Mode or WDAC/AppLocker). MITRE M1038, T1059.006. Bitdefender recommendation.
  • EDR anti-tampering and uninstall protection on every agent; alert on Defender exclusion changes (Q19). The affiliate's av_remove scripts were blocked by anti-tampering in this case. MITRE M1047, M1038, T1562.001. Vendor best-practice for your EDR (⚠ best-practice, no formal benchmark).
  • Disable the browser password manager by policy on terminal servers and shared hosts. A Chrome Login Data file was copied from a terminal server. MITRE M1054, T1555.003. Playbook step 8.
Strategic (1 to 3 months)
  • Keep the administrative accounts of separate domains separate and never keep privileged credentials for several domains in one place (Bitdefender). Put trust creation and domain-admin membership behind change control with approval. MITRE M1026, M1018, T1484.002.
  • Agent on every machine. The staging host was unmanaged, so nobody can say who or what drove the commands. Inventory unmanaged hosts, enrol or remove them. MITRE M1047.

  • Credential Guard on supported member servers and workstations, and SID filtering reviewed on every trust. MITRE M1043, M1025.
  • Segment the school estate: deny lateral SMB, WinRM and RDP between school networks by default, allow only from admin jump hosts. MITRE M1030.
