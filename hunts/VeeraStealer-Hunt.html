01

Executive Summary

VeeraStealer is a Windows infostealer described in the CYFIRMA Weekly Intelligence Report published 2026-11-19 ("Active Malware of the Week"). Per that report it collects browser credentials and authentication cookies, saved Wi-Fi profiles (exported in cleartext with netsh wlan export profile key=clear) and local files, captures the screen, profiles the host and its security tools, runs from memory with process injection, and persists through scheduled tasks and the Run registry key. It talks to two external endpoints, only one of which is named: ip-api.com, a shared geolocation service.

This is a single-source, thin-evidence pack. CYFIRMA's entry is a short write-up plus a YARA rule, not a teardown: it gives no sample metadata, no unpacking or configuration detail, no C2 protocol, no delivery chain and no C2 domain, and it does not attribute the malware to any actor. Searches for the name and for the sample hash found no independent coverage (see s2). The pack therefore builds its value on behavior: nine CQL queries around the Wi-Fi export command line, the WindowsUpdate logon-task pattern, Run-key persistence, the sample hashes and the ip-api.com lookup, plus a short honest IOC set. Every importable indicator ships as detect.

Most of the strings in CYFIRMA's YARA rule are sandbox noise (stock Windows and Google binaries, one analyst run's random temp files, a stock Windows mutex, a generic RAS string). They were deliberately left out; see s4.

Defender priority: hunt Q1, Q3 and Q9 first (Wi-Fi export with key=clear, a root-level WindowsUpdate logon task, and the two together). Treat any hit as credential exposure: the browser-saved passwords, session cookies and Wi-Fi keys on that host are compromised until proven otherwise. Never block netsh, schtasks or ip-api.com.

Native Audit-Log Hunts

CQL cannot see most of this stealer's behavior. These native checks cover the gaps; none was observed in a sample by this pack, they are derived from the source's description.

  • Mutex (GUID form). Falcon has no mutex telemetry. On a suspect host, enumerate handles (Sysinternals handle.exe -a filtered for the GUID, Process Explorer, or Volatility mutantscan on a memory image). Search for the exact GUID in s4. Do not alert on stock MSCTF.* mutexes.
  • Task creation. Security event 4698 (needs Audit Other Object Access Events, playbook 2) and Microsoft-Windows-TaskScheduler/Operational. Look for a root-level task named WindowsUpdate with a logon trigger and an action in a user-writable path.
  • Process command lines. Security event 4688 with command-line auditing (playbook 2), or Sysmon event 1.
  • Run keys. Sysmon event 13 on ...\CurrentVersion\Run and RunOnce.
  • Browser credential access. Sysmon event 11 / file-access auditing (4663 with a SACL) for reads of the browser Login Data and Cookies stores by a process that is not the browser. Falcon CQL has no equivalent here.
  • Wi-Fi export artifacts. The export command writes XML profile files into the working directory, commonly named Wi-Fi-<profile>.xml (⚠ validate naming on your build). Search user-writable paths for XML containing a keyMaterial element (playbook 3). Also the WLAN-AutoConfig operational log.
  • Staging pattern. The source's sandbox run shows a stealer staging .db and .png files with 32-hex names under a random v<hex> folder in the user's Temp directory. Those exact names will not recur; hunt the shape (a new random-hex folder in Temp holding 32-hex-named .db files and a screenshot PNG, written by a non-browser process) with Sysmon event 11.
  • Screen capture, reflective load, injection. No reliable CQL signal. Rely on EDR behavioral prevention and, on a suspect host, memory acquisition and review for unbacked executable regions.
  • Network. Proxy or DNS-server logs for ip-api.com from servers or hosts that never use geolocation services, then pivot to the process (Q8).
