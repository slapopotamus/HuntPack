Executive Summary

Two unrelated WordPress plugins, WPC Product Bundles for WooCommerce (CVE-2026-93836, versions up to 8.6.6) and Ninja Forms (CVE-2026-94504, versions up to 3.15.3), carry stored cross-site scripting flaws that are being exploited to deliver one shared JavaScript implant from imgcdn1[.]com. Patchstack first saw it on 2026-10-04 against WPC Product Bundles and on 2026-10-05 through Ninja Forms, and reported it on 2026-10-06. The XSS is only the front door: the payload runs inside a logged-in administrator's browser, rides that authenticated session, scrapes the nonces WordPress requires, and then uses WordPress's own plugin installer to drop a fake plugin.

One successful execution leaves the attacker with four independent ways back in: a visible administrator account, an administrator hidden from the Users screen by a must-use plugin, a magic login URL that authenticates as the site's oldest administrator, and an unauthenticated file manager inside the fake plugin. Removing the vulnerable plugin, or even the fake one, closes none of the last three. Patchstack also notes that the installer backdates the files it writes, so a search for recently changed files misses them.

Honest endpoint scope. The exploit, nonce theft, plugin upload, administrator creation and database option writes all happen inside the browser, WordPress and PHP. Falcon endpoint telemetry cannot see them. What Falcon can see is narrower: the administrator workstation looking up the C2 domain, file-integrity events for the dropped PHP files if a FIM policy covers wp-content, shells spawned by the web or PHP worker, and command lines that name the campaign's artifacts. Everything else needs WordPress audit logs, database queries, web server logs, a WAF or a file-integrity tool, and Section 7 and Section 15 say so plainly.

Defender priority: update both plugins, then treat any site where an administrator opened a WooCommerce order or Ninja Forms submission since 2026-10-04 as potentially compromised. Updating stops new injections but does not clean an existing infection. Enumerate administrators directly in the database, inspect the mu-plugins directory by content rather than date, and rotate credentials and salts.

Decision log

  • CVE numbers. CVE-2026-93836 and CVE-2026-94504 are the only CVE identifiers shipped. Both appear in the Patchstack article, BleepingComputer, ReconBee and the SecurityOnline panel. Other Ninja Forms CVE identifiers circulate in low-quality aggregator posts and search snippets; none of them appears in any saved snapshot, and one that surfaced in a search snippet described a different, earlier Ninja Forms version range, so none is shipped.
  • CVSS discrepancy. Patchstack lists CVSS 7.1 for both flaws; SecurityOnline lists 7.2. The pack reports "7.1 to 7.2, high" rather than choosing one.
  • "Authenticated" wording. BleepingComputer and ReconBee say the flaws "require an authenticated session to exploit". Patchstack calls both unauthenticated stored XSS. These reconcile: the attacker injects the payload without logging in, but the script only does damage when an authenticated administrator views the stored content. The pack follows Patchstack.
  • WPC Product Bundles fix version. Patchstack and BleepingComputer name 8.6.7. The vendor changelog lists a vulnerability fix in 8.6.7 and a separate stored-XSS sanitization fix in 8.7.3. The pack recommends moving to the current release, not stopping at 8.6.7.
  • Single-source indicators ship as detect. Every hash, the domain and the plugin artifacts originate in the Patchstack analysis. BleepingComputer and ReconBee repeat the domain but do not independently verify it. Under the two-source rule nothing ships at prevent, and no row in the Falcon import CSV is prevent.
  • Hashes that cannot exist. Patchstack states the two must-use plugins are obfuscated with a fresh key per site, so no fixed hash is published and none is invented here. They are listed by path and detected by behavior.
  • No coined name. The sources give the campaign no label. The pack uses descriptive wording and the fake plugin identity "WP Smart Thumbnails" exactly as the sources name it.
  • Fetched-content check. No fetched page contained instructions directed at an automated reader. Pages carried only ordinary site navigation, ads and unrelated headlines, which were ignored.

07

Native Audit-Log Hunts

Most of this campaign is invisible to the Falcon sensor. These checks run on the WordPress host, the database and the web server, and are the primary hunt for the application-layer steps. Commands come from the Patchstack detection section unless marked as derived guidance.

1. Enumerate administrators in the database, not in wp-admin

SELECT u.user_login, u.user_email, u.user_registered
FROM wp_users u
JOIN wp_usermeta m ON m.user_id = u.ID
WHERE m.meta_key = 'wp_capabilities'
  AND m.meta_value LIKE '%administrator%';

Compare to Users, All Users. Any account present in SQL but absent in the interface is hidden by a dropped must-use plugin. An @wordpress.org address on a local account, or a routine word such as support, updater, maintenance or backup, is a further signal. Adjust the wp_ prefix to your table prefix. Use raw SQL: WP-CLI loads must-use plugins, so wp user list can be filtered by the same hooks.

2. Check the campaign's own options

SELECT option_name FROM wp_options
WHERE option_name IN ('fz_emer_done_v1', 'fz_emer_login_tokens');

fz_emer_login_tokens present means at least one backdoor login token is live. Deleting the options alone is not enough while the must-use plugins remain.

3. Inspect the mu-plugins directory and the fake plugin

ls -la wp-content/mu-plugins/
ls -la wp-content/plugins/wp-smart-thumbnails/ 2>/dev/null
find wp-content/mu-plugins -type f -name 'class-wp-query-*.php' -o -name 'class-wp-token-validate.php'
grep -rl "dyiv://" wp-content/plugins 2>/dev/null

File modification times are not reliable here, because the installer backdates what it writes. Sort by content and by whether the file belongs to your known-good baseline. The mu-plugins directory should normally be empty or hold only files your host or team placed there. Both campaign must-use plugins are obfuscated, so a plain-text grep for hook names will not find them.

4. Search web server logs

grep -E "imgcdn1|/fz/x\.js|/fz/c\.php" /var/log/apache2/*access* /var/log/nginx/*access*
grep -E "_wplogin=" /var/log/apache2/*access* /var/log/nginx/*access*
grep -E "wp-smart-thumbnails" /var/log/apache2/*access* /var/log/nginx/*access*
grep -E "woosb_ids|nf_ajax_submit" /var/log/apache2/*access* /var/log/nginx/*access*

Requests carrying _wplogin to wp-login.php and direct requests to wp-smart-thumbnails.php outside the plugin screens are usable signals (Patchstack). The last pattern is broad: nf_ajax_submit is a normal Ninja Forms action, so triage hits by looking for markup in the submitted values. POST bodies are usually not in access logs, so a WAF or audit log is needed to see the payload itself.

5. Find stored payloads before an administrator opens them (derived guidance)

wp db query "SELECT meta_id, post_id FROM wp_postmeta WHERE meta_value LIKE '%imgcdn1%'"
wp db query "SELECT meta_id, order_item_id FROM wp_woocommerce_order_itemmeta WHERE meta_value LIKE '%imgcdn1%'"

This searches the places the sources say the payload is stored (order metadata and form submissions). Table names vary with prefix and WooCommerce storage mode; treat it as a starting point. Remove matching rows without opening them in wp-admin.

6. Review administrator-created accounts and plugin installs around order or submission views

Patchstack advises investigating any administrator account created around the time an administrator viewed WooCommerce orders or Ninja Forms submissions. This needs a WordPress audit-log plugin or equivalent; the stock log does not record it.

7. Administrator workstation (browser)

Search proxy and DNS logs for imgcdn1[.]com. On a workstation known to have opened affected content, check browser Local Storage for keys beginning __xp_v9_ (Patchstack). Treat the administrator's WordPress session as compromised.

CrowdStrike LogScale CQL Hunt Queries

Pick your tenant's cloud first — every "Open in Falcon" button below uses this selection.

Seven endpoint queries cover only the endpoint-visible slice. Q5 and Q6 depend on a Falcon FIM or critical-file policy that includes wp-content, which is not on by default (marked "validate in tenant"). Q7 depends on inbound-accept telemetry. XSS execution, nonce theft, hidden-administrator creation and the database option rows have no Falcon query; see Section 7 and Section 15.

Q1 · imgcdn1[.]com DNS lookup (payload and C2 host)
CONF HIGHFP LOWCOST LOW

Looks for: any DNS lookup of the single domain that serves every stage: the browser implant, the C2 check-in and the plugin ZIP. The lookup is made by the administrator's browser, so expect hits on admin workstations first. Works on Windows, macOS and Linux sensors.

// HUNT: DNS lookup of imgcdn1[.]com, the host serving the stored-XSS implant and its C2
// MITRE: T1071.001, T1105, T1059.007
// CONF: high
// FP: low
// COST: low
// REQUIRES: DnsRequest on admin workstations (Windows, macOS) and on web servers (Windows, Linux)
// FALSE POSITIVES: threat-intel sandboxes or DNS-sinkhole testing that deliberately resolves the domain
// NOTE: the implant runs in the ADMINISTRATOR'S BROWSER, so the lookup normally comes from an admin workstation, not the web server
#event_simpleName=DnsRequest
| DomainName=/(^|\.)imgcdn1\.com$/i
| groupBy([aid, ComputerName, ContextBaseFileName, DomainName], function=[count(as=Lookups), min(@timestamp, as=FirstSeen), max(@timestamp, as=LastSeen)], limit=20000)
| sort(FirstSeen, order=asc)
| table([aid, ComputerName, ContextBaseFileName, DomainName, Lookups, FirstSeen, LastSeen])
Q2 · Web-server egress to rare external addresses
CONF LOWFP HIGHCOST MEDIUM

Looks for: low-count outbound web connections from the web or PHP worker, a follow-on indicator if a second-stage fetch happens server-side. FP: plugin and core update checks, payment and shipping APIs and CDNs are normal; baseline before alerting (see the TUNING line in the card).

// HUNT: Web-server or PHP worker making outbound web connections to rare external addresses
// MITRE: T1105, T1071.001
// CONF: low
// FP: high
// COST: medium
// REQUIRES: NetworkConnectIP4 from Linux (httpd, apache2, nginx, php-fpm) and Windows (w3wp.exe) web servers
// FALSE POSITIVES: WordPress core and plugin update checks, payment gateway and shipping APIs, license servers, CDN and font fetches, outbound mail APIs
// TUNING: baseline for 14 days in investigate mode, then exclude every destination the site legitimately calls, for example by adding: | !in(RemoteAddressIP4, values=["REPLACE_WITH_BASELINED_API_IP"]) and keep only the rare tail (Conns <= 5)
// NOTE: Patchstack describes the fetches as browser-side, so this is a second-stage and follow-on hunt, not a primary detection
#event_simpleName=NetworkConnectIP4
| ContextBaseFileName=/^(httpd|apache2|nginx|php-fpm[0-9.]*|php-cgi[0-9.]*|lsphp[0-9]*|w3wp\.exe)$/i
| in(RemotePort, values=[80, 443])
| !cidr(RemoteAddressIP4, subnet="10.0.0.0/8")
| !cidr(RemoteAddressIP4, subnet="172.16.0.0/12")
| !cidr(RemoteAddressIP4, subnet="192.168.0.0/16")
| !cidr(RemoteAddressIP4, subnet="127.0.0.0/8")
| groupBy([aid, ComputerName, ContextBaseFileName, RemoteAddressIP4], function=[count(as=Conns), min(@timestamp, as=FirstSeen), max(@timestamp, as=LastSeen)], limit=20000)
| Conns <= 5
| sort(Conns, order=asc)
| table([aid, ComputerName, ContextBaseFileName, RemoteAddressIP4, Conns, FirstSeen, LastSeen])
Q3 · Shell or downloader spawned by a web or PHP worker
CONF MEDIUMFP MEDIUMCOST LOW

Looks for: the classic web-shell follow-on. The fake plugin's file manager cannot execute commands itself but can write a second shell. FP: image and PDF plugins that shell out; exclude their helper commands (see TUNING).

// HUNT: Shell, downloader or recon utility spawned by a web-server or PHP worker process
// MITRE: T1505.003, T1059
// CONF: medium
// FP: medium
// COST: low
// REQUIRES: ProcessRollup2 on Linux (apache2, httpd, nginx, php-fpm) and Windows (w3wp.exe) web servers

Hardening: Tiered & Deployable

Authorities: MITRE ATT&CK mitigations (the why), the WordPress.org Hardening WordPress and wp-config documentation (snapshots 07, 08), and the CIS Apache HTTP Server and NGINX Benchmarks for the web tier. No formal CIS WordPress benchmark was consulted for this pack, so WordPress controls cite the WordPress.org documentation and are marked where they are best practice only.

Immediate (this week)
  • Update Ninja Forms to 3.15.4 or later and WPC Product Bundles to the current release. Patchstack names 8.6.7; the vendor changelog lists a further stored-XSS sanitization fix in 8.7.3. MITRE M1051 (Update Software), T1190. Verify: wp plugin list --fields=name,version,update.
  • Clean stored payloads and assume prior compromise. Search order and submission data for the domain string (Section 7, check 5), remove matches without opening them in wp-admin, then run the administrator, option and mu-plugins checks (checks 1 to 3). Updating does not clean an existing infection (BleepingComputer, Patchstack). MITRE M1047 (Audit).
  • Sinkhole imgcdn1[.]com for administrator workstations and web servers at DNS or the web proxy. MITRE M1037 (Filter Network Traffic), M1031 (Network Intrusion Prevention). Verify: Q1 returns only the sinkhole lookups and a resolver query returns the sinkhole address.
  • Block the backdoor login and the fake plugin at the web server. Reject any request whose query string contains _wplogin= and deny the wp-smart-thumbnails plugin path (playbook step 3). MITRE M1050 (Exploit Protection), T1078. Verify: curl -I "https://site.example.com/wp-login.php?_wplogin=x" returns 403.
  • Stop reviewing orders and form submissions as an administrator. Give order and submission reviewers a role without install_plugins (for example Shop Manager). The implant needs administrator rights to install the plugin. MITRE M1026 (Privileged Account Management), M1018. Source: WordPress.org hardening guidance on least privilege (snapshot 07). Verify: wp user list --role=administrator --fields=user_login contains only people who must administer.
Near term (1 to 4 weeks)
  • Set DISALLOW_FILE_MODS in wp-config.php. It blocks plugin and theme installation and update from the admin area, which removes the step the implant uses to land the fake plugin. Trade-off: updates must then come through WP-CLI, Composer or CI. MITRE M1054 (Software Configuration), M1042. Source: WordPress.org wp-config documentation (snapshot 08). Verify: wp config get DISALLOW_FILE_MODS returns 1. Pilot on one site first.
  • Make plugin and mu-plugins directories non-writable by the web user. Files owned by a deploy account, directories 755 and files 644, web user read-only (WordPress.org File Permissions guidance, snapshot 07). The installer cannot write its must-use plugins if PHP cannot write the directory. MITRE M1022 (Restrict File and Directory Permissions). Verify: sudo -u www-data touch wp-content/mu-plugins/t fails. Pilot first, because dashboard auto-updates stop working.
  • Restrict wp-login.php and wp-admin to a VPN or office range. This does not stop the XSS, which fires from an allowed administrator's browser, but it stops attackers from using the magic login URL and a created account from their own network. MITRE M1030 (Network Segmentation). CIS Apache HTTP Server and NGINX Benchmarks cover access restriction. Verify: external request to wp-login.php returns 403.
  • File-integrity monitoring on wp-content/plugins and wp-content/mu-plugins (Falcon FIM policy, AIDE or auditd) so Q5 and Q6 have data. MITRE M1047 (Audit). Verify: create a test file in a lab copy and confirm an event.
  • Deploy a WAF rule or virtual patch for markup in woosb_ids quantity values and in Ninja Forms AJAX submissions, in detection-only mode first. MITRE M1050. ⚠ best-practice: OWASP Core Rule Set covers generic XSS, tune for these fields.
  • Add a WordPress audit-log plugin that records user creation, role changes and plugin installs, and ship it to your SIEM. MITRE M1047. ⚠ best-practice, no formal benchmark.
  • Be clear what MFA does not fix. The implant never reads the session cookie; it rides the live session, so MFA and HttpOnly cookies do not stop it (Patchstack). Keep MFA for the credential-theft cases it does address (M1032) but do not count it as a control for this attack.
Strategic (1 to 3 months)
  • Immutable, CI-driven WordPress deployment. Read-only application filesystem, plugins and mu-plugins deployed from a reviewed repository, so an unreviewed PHP file cannot persist. MITRE M1022, M1054. ⚠ best-practice, no formal benchmark.
  • Content-Security-Policy for wp-admin, Report-Only first. A policy that blocks third-party script origins would stop a script tag pointing at an attacker domain. WordPress admin uses inline scripts, so expect a long tuning phase. MITRE M1021 (Restrict Web-Based Content). ⚠ best-practice, no formal benchmark.
  • Plugin vulnerability feed with a patch SLA. Subscribe to a WordPress vulnerability intelligence source and hold an SLA for exploited flaws measured in days. Patchstack notes the domain appeared roughly ten days after public disclosure of both flaws. MITRE M1051, M1016 (Vulnerability Scanning).
  • Reduce the plugin estate and the number of administrators. Remove unused plugins (WordPress.org guidance) and keep administrator accounts to the minimum, reviewed quarterly against a database query, not the Users screen. MITRE M1018, M1026.
  • Harden the web tier to CIS. Apply the CIS Apache HTTP Server Benchmark or CIS NGINX Benchmark and a CIS Linux benchmark for the host OS. Verify with the benchmark's own assessment tooling.

Step 3: Block the backdoor login, the fake plugin and (optionally) restrict admin access at the web server

RewriteRule ^ - [F,L]
RewriteRule ^wp-content/plugins/wp-smart-thumbnails/ - [F,L]

</Files>

# --- NGINX ---
location ~* ^/wp-content/plugins/wp-smart-thumbnails/ { return 403; }
location = /wp-login.php {
    if ($arg__wplogin) { return 403; }
    allow 192.0.2.0/24;
    deny all;
    include fastcgi_params;
    fastcgi_pass unix:/run/php/php-fpm.sock;
}
