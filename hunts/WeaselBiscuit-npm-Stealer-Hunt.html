Executive Summary

WeaselBiscuit is a previously undocumented, self-contained JavaScript infostealer disclosed 2026-09-18 by OpenSourceMalware (researcher Paul McCarty, aka 6mile, with co-founder Jenn Gile), found bundled inside a cluster of 13-17 malicious npm packages first seen between 2026-09-12 and 2026-09-16. Unlike a typosquat that rides an npm install lifecycle hook, WeaselBiscuit has no preinstall/postinstall script at all — it fires when the package is actually imported or required by an application, or manually started, which is the single most important operational detail in this pack and the reason several install-time controls that work against other npm stealers (e.g. npm config set ignore-scripts true) do not stop this one. On import, the package auto-spawns a detached Node.js loader process, writes its PID to a local .pid marker, and retrieves a Base64-encoded second stage from a hardcoded Npoint.io dead-drop URL, executing it in memory via new Function — the payload never touches disk. The second stage resolves its C2 configuration from a second, shared Npoint URL, which in every recovered sample points to the same plain Express HTTP control plane at 103.170.217.184:8787.

Once live, WeaselBiscuit profiles the host (hostname, user, OS, CPU/RAM, local and public IP with a nested api.ipify.org → ip-api.com geolocation lookup) and uploads every readable, nonempty file under Chrome's Local Extension Settings LevelDB store — the directory where extensions like MetaMask cache signing/session state — on Windows, macOS, and Linux. On operator command only, it can also capture clipboard contents (Get-Clipboard / pbpaste) and, Windows-only, log keystrokes via a temporary PowerShell script written to %TEMP%\kb-monitor\keyboard-monitor-*.ps1. Each install is tagged with a numeric campaign identifier baked into the package name and every upload (10, 12, 79, 95, 99 confirmed at the payload level; 44 appears only in package naming — see §2).

The researcher explicitly frames this as behaviorally, not conclusively, DPRK-linked: the code borrows structural tradecraft from the DPRK's Contagious Interview tooling (BeaverTail and OtterCookie) — the Npoint dead-drop pattern, the nested public-IP/geolocation lookup, and a numeric per-install campaign marker resembling the PolinRider cluster — but is deliberately stripped down: no wallet-draining code, no browser-credential decryption, no seed-phrase sweep, no InvisibleFerret/Python second stage, no screenshots, and no Socket.IO/remote shell. OpenSourceMalware itself rates DPRK attribution "Low to moderate" and calls the DPRK-strain hypothesis "an analytic hypothesis, not a confirmed attribution." This pack treats that caveat as binding: nothing here is shipped at Prevent-tier severity on the strength of attribution, and every indicator below traces to a single primary-research lineage (see §2).

Defender priority: because there is no lifecycle hook to block, the highest-leverage control is never letting the package into the dependency tree in the first place (pre-merge SCA/vetting), backed by runtime detection of a detached Node child process reaching an Npoint dead-drop or the known C2 — not an install-time script block, which does nothing against this specific threat.

Research decisions

  • Package-count discrepancy across (and within) sources. The GitHub README lists "16 packages we've found so far" and enumerates exactly 16 names. The OpenSourceMalware blog's own intro paragraph says "11 npm packages" but its table lists the same 16 names as the README — an apparent editing artifact where the count grew as research continued but the intro sentence wasn't updated. The Hacker News headline and body say "13 npm packages" and name exactly 13 of those 16 (omitting laycot, @vibecheck-polid/process-runtime-utils, and @railone/image-utils). A 17th name, swnwall@1.2.10, appears in both [01] and [03] only inside the campaign-structure/resolver table, never in either source's headline package list. This pack ships the full union of 17 distinct names (§10) rather than picking one source's count, and reports the discrepancy here rather than silently reconciling it.
  • The 7th Npoint resolver's identifier is genuinely unconfirmed. https://api.npoint.io/24c12c4b66a29747764f is hardcoded inside id79-client's code but returned HTTP 404 when the researcher retrieved it, so its embedded stage identifier is listed as "Unknown" in the README/blog prose. The campaign-infrastructure YARA rule's own comment labels this same UUID // ID 44 — almost certainly the researcher's own inference by elimination (six @biz44/id*-client packages map to six numeric IDs; five of six resolvers were independently confirmed with identifiers 99/10/79/12/95, leaving 44 as the remaining candidate) — but that inference is not stated as confirmed in the prose itself. This pack ships that resolver at low confidence/severity with the ambiguity spelled out, rather than asserting "44" as confirmed.
  • Confirmed vs. clustered package linkage. Only four packages (process-tailwind@1.1.99, engin1@1.3.99, swnwall@1.2.10, id79-client@1.1.79) have an individually-documented, direct Npoint-resolver delivery link in the source material. The remaining thirteen names were "grouped together" by the researcher's own automation "as they shared IOCs" — a real and useful signal, but a different (weaker) evidentiary tier than the four confirmed names. §4 and §8 (Q1 vs. Q2) keep these two tiers separate rather than treating all seventeen names as equally confirmed.
  • Malware-sample handling. The GitHub repository hosts live, attacker-authored files (a deobfuscated second-stage JS sample and its raw counterpart) as research artifacts. Per this pack's build instructions, the deobfuscated sample was fetched and read as inert plain text only — never executed, imported, or evaluated in any interpreter — solely to confirm specific literal strings (route paths, the kb-monitor temp-directory name, the identifier field) against the primary artifact rather than taking the prose write-up on faith. The raw (non-deobfuscated) payload file and the two logo/attack-chain images in the repository were not fetched; they add no citable technical detail beyond what [01]/[03]/[04]/[05] already establish.
  • Prompt-injection check. All five fetched sources — including the README, all three YARA rule files, and the deobfuscated malware sample text — were reviewed for embedded instructions directed at an AI agent (hidden text, comments claiming authorization, "note to the AI," redirection to fetch additional URLs, or instructions to skip a step or execute something). None was found in any of the five snapshots. See §18 for the full statement.

Native Audit-Log Hunts

The largest coverage gaps in this pack — SaaS-hosted CI compute, the pre-eval Base64/new Function step, and the pre-import registry-side detection problem (§5) — have no Falcon-sensor answer at all. These native, non-CQL checks are the only available coverage for those surfaces, and a useful supplement everywhere else.

npm / dependency-tree audit (all platforms)

  • Run an SCA scan (Socket.dev, Snyk, npm audit equivalent, or an internal registry-side scanner) across every repository's package.json/package-lock.json/yarn.lock for the 17 named packages in §10 — by name and, where known, version.
  • Because there is no lifecycle hook to gate, npm config get ignore-scripts auditing (useful against other npm stealers) provides no protection against WeaselBiscuit specifically — do not rely on it as a compensating control here.
  • Grep the dependency tree for any package whose index.js or top-level module unconditionally spawns a detached child process on import — a generic static-analysis heuristic that would catch this family and future clones of it.

Windows Endpoint Security / Sysmon (where Falcon FileOpenInfo/FileReadInfo licensing is unavailable)

  • Sysmon Event ID 11 (FileCreate) / 15, filtered for *kb-monitor\keyboard-monitor-*.ps1 under any user's %TEMP%.
  • Sysmon Event ID 1 (ProcessCreate), filtered for a node.exe parent spawning powershell.exe with Get-Clipboard in the command line.

Linux / macOS endpoint (auditd / Endpoint Security Framework)

  • Linux auditd watch rule on the Chrome extension-settings path, independent of Falcon licensing for FileOpenInfo/FileReadInfo:
    -w /home/*/.config/google-chrome/*/Local\ Extension\ Settings -p r -k weaselbiscuit_ext_read
  • macOS Endpoint Security Framework file-open events on the equivalent Chrome profile path, or as a fallback: log show --predicate 'eventMessage contains "Local Extension Settings"' --last 1h
  • macOS: watch for a node-parented pbpaste child process (ps -ef | grep pbpaste spot-check, or an ESF process-exec hook) — the source material confirms pbpaste as the macOS clipboard-capture mechanism but names no Linux-specific clipboard tool, so Linux clipboard capture is unconfirmed by any cited source and should not be assumed present.

Filesystem spot-check for the .pid marker (all platforms)

  • No generic Falcon file-write event maps cleanly to an arbitrary non-executable file write, so this is a manual/RTR check rather than a CQL query: search under every node_modules/<package>/ directory matching the §10 package list for a .pid file, and correlate its contents (a PID) against currently running or recently-exited node processes.

Hardening — Tiered

Read this before reusing another npm-stealer pack's hardening list against this threat. WeaselBiscuit has no npm lifecycle hook — the code runs when the package is imported/required by application code, not when npm install runs. npm config set ignore-scripts true, the single most effective control against a preinstall/postinstall-hook stealer, does nothing against WeaselBiscuit. Controls below are chosen accordingly: the leverage point is stopping the package from ever entering the dependency tree, plus runtime/network detection of the behavior that follows import.

Immediate — this week

1. Require a pre-merge SCA/dependency-review gate for any new or updated npm dependency before it can reach application code that will actually run (not just pass CI's install step). MITRE M1013 (Application Developer Guidance), M1033 (Limit Software Installation). Authority: NIST SP 800-218 (SSDF) practice PW.4; OpenSourceMalware's own recommendation to screen the dependency tree against the named-package list (§10).
Verify: a PR that adds a net-new npm dependency cannot merge without a passing SCA scan and a human reviewer sign-off; spot-check by attempting to add one of the §10 package names in a test branch.
Rollback: revert the branch-protection rule requiring the SCA check to pass before merge — only do this if the gate is blocking unrelated legitimate work, and fix the gate's false-positive rate instead of disabling it where possible.

2. Default-deny egress allowlisting for developer workstations and CI runners, at minimum blocking 103.170.217.184. MITRE M1037 (Filter Network Traffic). Authority: NIST SP 800-204C; CIS Benchmark network egress-control guidance for the self-hosted case.
Verify: curl -m 5 http://103.170.217.184:8787 from a workstation/runner times out or is denied; review firewall/VPC Flow Logs for the denied attempt.
Rollback: remove the specific deny rule if it collides with an unrelated legitimate destination sharing infrastructure — unlikely for a dedicated non-cloud-hosted IP, but verify ownership before assuming otherwise.

Near term — 1 to 4 weeks, pilot first

3. Run Q1-Q3 and Q8 in Detect/hunt-only mode fleet-wide for a 14-day burn-in, reviewed by two analysts before any promotion decision. MITRE M1040 (Behavior Prevention on Endpoint). Authority: this pack's own Detection Validation Gates (§11); no formal CIS/vendor benchmark exists specifically for "detached Node child process behavior," so this control is grounded in the pipeline's own validated-query methodology rather than an external benchmark. ⚠ best-practice, no formal CIS/MITRE-mitigation entry specific to this exact behavior pattern
Verify: Falcon shows Q1/Q3/Q8 running on schedule with logged hit counts for the burn-in window; a two-analyst sign-off record exists before any query is promoted.
Rollback: disable the scheduled search if it generates unmanageable noise during burn-in — re-tune the TUNING exclusions (§8) rather than abandoning the hunt entirely.

4. Restrict file-system permissions on Chrome's Local Extension Settings directory on workstations known to hold cryptocurrency wallet browser extensions, and/or segregate wallet-extension use into a dedicated browser profile isolated from general development/testing browsing. MITRE M1022 (Restrict File and Directory Permissions). Authority: ⚠ best-practice, no formal CIS/MITRE-mitigation entry specific to browser-extension LevelDB store permissions — grounded in the primary source's own observation that this directory's contents are "financially relevant" even without dedicated wallet-draining code.
Verify: a non-owner OS account cannot read the target Chrome profile's Local Extension Settings directory; confirm via a permissions audit script appropriate to the OS (icacls on Windows, ls -l/stat on macOS/Linux).
Rollback: revert to the OS default permissions on that directory if the restriction breaks legitimate multi-user browser profile sync or an IT-managed browser-extension deployment tool.

Strategic — 1 to 3 months

5. Evaluate sandboxed/ephemeral dev containers or VMs for evaluating any newly-added third-party npm dependency before it ever touches a developer's primary workstation, CI secrets, or a wallet-bearing browser profile. MITRE M1048 (Application Isolation and Sandboxing). Authority: NIST SP 800-218 (SSDF) PW.4; general container/VM-isolation guidance for untrusted code evaluation (no npm-specific CIS benchmark covers this directly).
Verify: a test dependency-evaluation workflow runs entirely inside an ephemeral container/VM with no access to the developer's real credentials, wallet extensions, or persistent filesystem; confirm the container is destroyed after evaluation.
Rollback: revert to direct workstation-based dependency evaluation if the sandboxing workflow proves too slow for the team's release cadence — prioritize this control for the highest-risk repos (those touching production secrets or crypto-adjacent code) first if a full rollout isn't feasible.

6. Train developers on npm supply-chain tradecraft signals specific to this family: short, generic-sounding utility package names with little publishing history, numbered/scoped package families (e.g. @biz44/id10-client .. id99-client), and packages that spawn a detached background process on import with no clear product justification. MITRE M1017 (User Training).
Verify: a tabletop exercise asking developers to evaluate a mocked-up package listing (mixing real and simulated WeaselBiscuit-style names) against real popular packages measures catch rate.
Rollback: none required — training/process control with no endpoint state change.
