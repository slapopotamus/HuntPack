01

Executive Summary

What happened. On 2 November 2026 at 02:06 UTC an unidentified attacker used compromised credentials to reach the update distribution infrastructure (CDN) of OPSSHIELD, the maker of cPGuard, a server security product for cPanel and Linux hosting servers. The attacker used that access to push a malicious script through the legitimate auto-update channel in cPGuard versions 5.88.12 through 5.88.19. OPSSHIELD says it detected the attack within 12 hours, secured the compromised account, cleared its infrastructure credentials and stopped further distribution. How the credentials were obtained is still under investigation.

What the script does. Per the vendor, it collected /etc/shadow and /etc/passwd, root's MariaDB/MySQL configuration (my.cnf), root's shell history and root's SSH authorization and known-hosts files, staged them in a hidden directory under /var/tmp, uploaded them to OPSSHIELD's own licensing server under a compromised account for the attacker to retrieve later, and left a backdoor shell. OPSSHIELD confirmed the attacker retrieved some of that data and estimates 32 collected files, each tied to one customer server. This is a preliminary count of confirmed retrieval, not the number of affected servers.

Scale, stated plainly. BleepingComputer reports that an OPSSHIELD spokesperson said 2,946 servers were affected and that a billing system database was also copied. Neither figure appears in the vendor advisory, The Hacker News or SecurityOnline, so both are single-sourced here and are not used by any query. The BleepingComputer snapshot is also a model-generated extraction, not a verbatim copy (see Section 2).

Correction to a common summary. Some coverage says the script took "root SSH keys". The vendor's list is root's SSH authorization and known-hosts files. Private keys under /root/.ssh appear only in the vendor's rotation advice ("replace SSH private keys stored under /root/.ssh"), as a precaution. Rotate them anyway, but do not report private-key theft as confirmed.

Highest-value defensive angle. The product is the delivery vehicle, so a clean version number today proves nothing: the vendor says a server that installed an affected update must be treated as potentially compromised even if it now runs 5.88.25 or later, because credentials copied before cleanup may still work. Run the install_log check, hunt the named hidden paths and the credential-sweep and upload behavior, then rotate credentials. The vendor does not recommend a routine rebuild; it may if you find other signs of compromise.

Defender priority: on every cPGuard server run grep 'Successfully updated' /opt/cpguard/logs/install_log; any entry from 5.88.12 to 5.88.19 means treat the host as compromised. Update with cpgcli update --start, confirm 5.88.25 or later with cpgcli --version, then reset root and every password-enabled local account from a trusted environment and rotate database passwords, S3 keys, DigitalOcean tokens, secrets in root's shell history and the SSH private keys under /root/.ssh.

Decisions and conflicts

  • Artifacts. All four atomic artifacts (script name, backdoor shell, collection directory, loot archive) were verified by hand against the saved vendor snapshot and The Hacker News snapshot. The backdoor shell path is also in the SecurityOnline snapshot. The Hacker News derives its list from the vendor, so these are not independent sources: every artifact ships as detect, never prevent.
  • No hashes, IPs or malicious domains were published by any source. None are invented; the Falcon CSV carries labelled REPLACE_WITH_ placeholders.
  • Versions are not IOCs. 5.88.12 through 5.88.19 (affected) and 5.88.25 (fixed) live in prose and the version table only. Versions 5.88.20 to 5.88.24 are described by no source as either affected or fixed.
  • Time zone. The vendor's example install_log lines use a day-first date (02-11-2026 02:46:04) with no stated zone; do not assume UTC.
  • Unpublished: the upload hostname and method, the update process names, how the script is launched, whether the backdoor shell is a script or a binary, and whether the support-access private key was exposed.
  • Scale conflict. The vendor's "32 files" is retrieval from its licensing server and one extraction of the BleepingComputer text garbles it as "from each customer". Treat 32 as a confirmed floor, not a scope.
  • Injected instructions. No fetched page contained text directing an AI agent to act. Nothing was dropped on that ground.
  • Naming. No source assigns an actor, campaign or malware name. The pack uses only "cPGuard" and "OPSSHIELD".

07

Native Audit-Log Hunts

These are read-only checks for each cPGuard server. The vendor says a missing or incomplete log does not show a server was unaffected, and the corrective update removes the named files.

7.1 Update history (the vendor's own check)

grep 'Successfully updated' /opt/cpguard/logs/install_log
grep -E 'Successfully updated to 5\.88\.1[2-9]' /opt/cpguard/logs/install_log

Any entry from 5.88.12 to 5.88.19 means the server installed an affected update. The vendor's example lines show five entries on 02-11-2026 (day-first, zone unstated).

7.2 Installed version

cpgcli --version

Must report 5.88.25 or later. A fixed version does not clear a host that installed an affected one earlier.

7.3 Named artifacts

# Filesystem sweep (read-only)
ls -la /var/tmp/.cpg91511 /var/tmp/.cpg91511_sh 2>/dev/null
find /var/tmp /tmp /root /opt/cpguard -maxdepth 3 \( -name '.cpg*' -o -name 'cpguard-v*-i*.sh' \) 2>/dev/null
stat /etc/shadow
# Remember: the corrective update removes these files, so a clean result does not show the script never ran.

7.4 Logons since the compromise (credentials may have been used)

last -F root | head -50
grep -E 'Accepted (password|publickey)' /var/log/secure /var/log/auth.log 2>/dev/null | tail -200
cat /root/.ssh/authorized_keys

Look for logons you cannot explain since 2026-11-02 and for unknown keys. An OPSSHIELD support-access key is legitimate if support access was granted; OPSSHIELD is shipping an update to remove those keys.

7.5 Database and cloud audit

Review MariaDB/MySQL logs for root logins from unexpected sources, and review S3 and DigitalOcean audit logs since 2026-11-02 for the keys and tokens that were present on the server or recorded in root's shell history (the vendor names S3 access keys and DigitalOcean tokens).

Hardening: Tiered

Immediate (this week)
  1. Update and verify cPGuard. Run cpgcli update --start on every server, then cpgcli --version and confirm 5.88.25 or later (OPSSHIELD advisory; MITRE M1051 Update Software). Verify: cpgcli --version. Note that updating does not make a host that ran the script safe.
  2. Rotate every exposed credential from a trusted environment. Reset root and all password-enabled local accounts, change reused passwords elsewhere, rotate database passwords, S3 keys, DigitalOcean tokens and secrets found in root's shell history, replace the SSH private keys under /root/.ssh and remove the old public keys from every system that trusts them (OPSSHIELD advisory; M1027 Password Policies, M1026 Privileged Account Management). Verify: passwd -S root, key fingerprints, and cloud provider key-age reports.
  3. Restrict outbound traffic from hosting servers. Default-deny egress with an allowlist so a root process cannot upload a loot archive to an arbitrary host (M1037 Filter Network Traffic; CIS Linux Benchmark host firewall section). Caveat: a vendor licensing host that is already allowed (as here) is not blocked by this, so it limits unknown destinations only. Verify: nft list ruleset or iptables -S.
  4. Review root's authorized_keys. Remove unknown keys; remove the OPSSHIELD support-access key unless you actively use support access (OPSSHIELD is shipping a removal update). Verify: cat /root/.ssh/authorized_keys.
Near term (1 to 4 weeks, pilot first)
  1. Stage security-tool updates. Run updates on a canary group and hold the rest for a defined period before they apply, where the product allows deferral. ⚠ best-practice, no formal benchmark; no source says cPGuard exposes a deferral setting, so confirm in OPSSHIELD documentation. Reduces blast radius of any future poisoned update; the 12 hour detection window here is the span a hold would have to cover.
  2. Audit access to credential files. auditd watches on /etc/shadow, /root/.ssh, /root/.my.cnf and root history, plus exec watches under /var/tmp (M1047 Audit; CIS Linux Benchmark auditd section). Gives a file-read record that endpoint telemetry lacks. Playbook 3. Verify: auditctl -l.
  3. Mount /var/tmp noexec,nosuid,nodev. Stops direct execution of a binary dropped there (CIS Linux Benchmark separate /var/tmp partition and mount options; M1022). Limit: a script run as sh /var/tmp/x is not stopped, and some cPanel components expect to execute from temp directories, so pilot. Playbook 4. Verify: findmnt /var/tmp.
  4. Stop leaving secrets where a script can read them. Keep passwords out of shell history (HISTCONTROL=ignorespace, no secrets on command lines) and use scoped, short-lived cloud credentials instead of long-lived keys in files (M1027; T1552.003). Verify: search history for key-shaped strings after rotation. ⚠ best-practice, no formal benchmark for the history control.
Strategic (1 to 3 months)
  1. Treat root-level security agents as supply-chain risk. Inventory every product that auto-updates as root, require vendor release signing or checksum verification where offered, and track vendor incident notices (M1016 Vulnerability Scanning for the inventory process). ⚠ best-practice, no formal benchmark.
  2. Remove standing secrets from servers. Move to a secrets manager and short-lived credentials so a one-time file sweep yields nothing durable (M1026). Verify with a secret-scan of home directories.
  3. Forward logs off host. Send auth, audit and product logs to central storage so evidence like install_log and logons survive cleanup (M1047). The vendor warns a missing log does not clear a host.
